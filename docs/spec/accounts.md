# Spec: `accounts`

## Purpose

`accounts` owns the user record: who a user is, and how they appear to others. Registration creates the record through `auth`, other modules read display data through batch calls, and a user renames themselves here. It deletes an account once `auth` has confirmed the deletion, and exports a user's data into an archive they download, both across every module, through the personal data contract (D16, D31).
A user also sets and removes their avatar here, whose image `files` keeps (D117, D120). <!-- part: files -->

## Owns

| Table | Holds |
|---|---|
| `users` | `id`, `email`, `name`, `email_verified`, `created_at`, `updated_at`, `version`. `email` holds the normalized address and has the unique index `users_email_key`. `email` and `name` are personal data (DATA-23). |
| `exports` | `id`, `user_id`, `state`, `ready_at`, `size_bytes`, `expires_at`, `created_at`, `updated_at`, `version`: one row per export a user requested (ACCOUNTS-020). `user_id` references `users` with `ON DELETE CASCADE`. `state` is the Postgres enum `export_state`: `pending`, `ready` or `failed` (DATA-04). `ready_at` and `size_bytes`, the archive's, are set once it is ready. Only the export's job and its expiry change a row. |
| `export_entries` | `id`, `export_id`, `position`, `path`, `size_bytes`, `stored_bytes`, `crc32`, `created_at`: each JSON document of an export's archive, at its position among them, with its path in the archive, its size, the size of its deflated bytes, and the CRC-32 (cyclic redundancy check) of the document. `export_id` references `exports` with `ON DELETE CASCADE`, and `(export_id, position)` is unique. Rows are never updated, and `app` holds no `UPDATE` on it (DATA-02, DATA-19). |
| `export_chunks` | `id`, `export_id`, `position`, `offset_bytes`, `bytes`, `created_at`: the deflated bytes of the document at `position`, in chunks of at most 1 MiB, each at its offset among them. `bytes` is personal data (DATA-23). `export_id` references `exports` with `ON DELETE CASCADE`, and `(export_id, position, offset_bytes)` is unique. Rows are never updated, and `app` holds no `UPDATE` on it (DATA-02, DATA-19). |

## Interface

- `create(uow, &EmailAddress, &DisplayName)`: inserts a user and returns `Creation::Created` with the user's ID, or `Creation::EmailInUse` when the unique index refuses the email (ACCOUNTS-004).
- `find_by_email(uow, &EmailAddress)`: the ID of the user with this email, if there is one. `auth` uses it to sign in.
- `address(uow, UserId)`: the user's email and whether they proved it, as `Address`, or none once the account is gone, and `verify_email(uow, UserId)`, which makes the record's `email_verified` true. `auth` reads the first as it authenticates each request, while email is on, and calls the second once the user confirms their code (AUTH-025, AUTH-031). Callers pass the caller's ID, or the user's whom a job runs for (DATA-16).
  `invitations` uses it to find an invitee's account. <!-- part: invitations -->
- `profile(uow, &Principal)`: the caller's own record, as ACCOUNTS-001 gives it. <!-- part: invitations -->
- `profiles(uow, &[UserId])`: names and emails for a batch of users. Callers pass only IDs that came from a query filtered by tenant, such as a workspace's member list (DATA-16).
  Each profile also holds the link to the user's avatar (ACCOUNTS-011). <!-- part: files -->
- `matching(uow, &[UserId], &Search)`: the IDs among a batch, passed under the same terms, of the users whose name or email contains the search (API-20).
- The domain type `DisplayName` (D25). `EmailAddress` is in `platform::types`.
- `Deletion`, which the composition root builds from every module's personal data contract, in the order it registers them, and whose `delete(uow, &Principal)` deletes the caller's account in the unit of work of `auth` that confirmed it, and reports whether it did, or why not, which `auth` answers with codes of its own (ACCOUNTS-012 to ACCOUNTS-016, AUTH-023).
- `Exports`, which the composition root builds from every module's personal data contract, in the order it registers them, and whose `register` registers the export's job and its expiry (Design: Exporting).
- `Contract`, the personal data contract for `users` and the user's exports, which the composition root registers last (D31).

## Design

### Renaming

The patch's name is parsed into a `DisplayName` before the unit of work opens. The unit of work's first statement locks the user's row `FOR UPDATE`. The update then writes the name with the versions that `If-Match` names in its `WHERE`, so a stale `ETag` changes nothing and answers 412 (DATA-18, PLATFORM-071), and the row's trigger moves its `version` and `updated_at` (DATA-02). A rename writes, records and publishes even when the name is the one stored, as a workspace's rename does (WORKSPACES-008).

### Events

A user's name shows wherever they appear to others: in each workspace's member list (WORKSPACES-004), and on the user's own other devices. So a rename publishes `user.updated` to the user's own streams, and `member.updated` in every workspace they belong to, whose members with `members.read` read the member again, since the payloads carry IDs alone (API-19, D7). The workspaces come from `access::workspace_ids`, read in the rename's own unit of work once it holds the lock on the user's row, which a membership's insert waits for, since its foreign key reads the row `FOR KEY SHARE` (DATA-20). So a membership that commits before the rename's read is among the workspaces it publishes in, and one that commits after the rename does, since it waited, is read by its members with the new name.
A change to the user's avatar publishes the same two events, since the avatar shows wherever the name does (ACCOUNTS-008, ACCOUNTS-010). <!-- part: files -->

<!-- part: files -->
### Avatars

`files` keeps each avatar: its row in `avatars`, and its bytes in the bucket under the prefix `avatars/` ([files spec](files.md#avatars)). `accounts` owns setting and removing it, its entries in the user's log, and its events, since an avatar is part of how a user appears, as their name is, so both changes reach clients the same way (D120).

1. The handler refuses a body whose `Content-Length` declares more than ACCOUNTS-009's limit, then reads the body, in one of the replica's turns, which it holds until the avatar is stored (PLATFORM-074). `files::upload_avatar` finds its kind from its bytes, has the scanner scan it, and writes its object, outside any transaction (DATA-21).
2. It then runs what `accounts` gives it, which opens the unit of work. Its first statement locks the user's row, as a rename's does, so two changes of one user's record take turns (DATA-20), and the next moves the record's `version`, with the versions that `If-Match` names in its `WHERE` (DATA-18). `files::record_avatar` then deletes the user's avatar row, if any, and inserts the new one. The entry is recorded, the events are published, and the unit of work commits, which counts the upload as stored (FILES-013). A stale `ETag` answers 412 once the object is written, which FILES-011 then deletes.

An object written by an upload whose unit of work never commits, and the object of a replaced or removed avatar, are left to FILES-011, as every unreferenced object is. Removing an avatar locks the user's row, and moves their `version` when there was one to remove, so every change to what ACCOUNTS-001 gives moves its `ETag`.

An avatar is public, so a client shows it with an `<img>` that sends no credential, to the user's fellow members and anyone they show it to, and its link never expires. An avatar's ID changes with each image, so a client and a shared cache that hold one image never take it for the next.

ACCOUNTS-009's limit is fixed, beside `FILE_MAX_BYTES`, whose default is ten times it, since every member list downloads each member's avatar: a client shrinks a photo to the size it shows, such as 512 pixels square, which a JPEG or a WebP holds in about 100 kilobytes, and a PNG in at most about 800 (D121). The API reads no image's dimensions, since it never decodes one (D109).
<!-- end part: files -->

### Email verification

`email_verified` starts as `false`, and nothing enforces it in this slice, though ACCOUNTS-001 returns it. What it decides, once the full `auth` module arrives, is in the [auth spec](auth.md#email-verification).

### Deleting an account

`auth` confirms a deletion, as AUTH-023 says, opens the unit of work, and calls `Deletion::delete`, which:

1. Holds the user's row `FOR NO KEY UPDATE`, against every other change of it. When another deletion of the account deleted the row while this one waited for it, this deletion finds none, and is done (ACCOUNTS-019).
2. Has `access` lock every membership of the user, `FOR UPDATE`, and refuse the deletion while a workspace they own has another member (ACCOUNTS-012, ACCESS-008). It then locks every export of the user's, `FOR UPDATE`, waiting for no lock, and refuses with ACCOUNTS-016's 409 while one is locked (Exporting).
3. Runs each module's personal data contract, in the order the composition root registers them, each erasing what its module keeps of the user, as the table below says (D31). The deletion is immediate, with no grace period (D16).
4. Runs the contract of `accounts` last, which reads the user's email, enqueues the email of ACCOUNTS-015, locks the user's row `FOR UPDATE`, and deletes it, waiting for no lock (ACCOUNTS-016). The foreign keys then delete, or set to null, every row that still names the user (DATA-05).

| Contract | What it erases |
|---|---|
| `workspaces` | Has `access` end each membership of the user, with its access-change signal (ACCESS-006), then deletes each workspace they owned, whose only member they were, with everything in it, through its foreign keys, and the jobs enqueued for it (DATA-23). In each other workspace they belonged to, it records `member.left` and publishes it (ACCOUNTS-014). |
| `access` | Any membership of the user that remains, each with its access-change signal (ACCESS-006): none, once the contract of `workspaces` has run. |
| `files` | The user's files and avatar, whose bytes FILES-011 deletes. A file they uploaded to a workspace that stays keeps its row, and its foreign key sets its `uploader_id` to null as the user's row goes (ACCOUNTS-017). <!-- part: files --> |
| `invitations` | Nothing of its own: an invitation the user sent stays, the workspace's, and its foreign key sets its `inviter_id` to null as the user's row goes. An invitation addressed to their email is the workspace's too, and stays (ACCOUNTS-018, D31). <!-- part: invitations --> |
| `auth` | The user's identities, their sessions, each with its access-change signal, which closes its streams (SEC-06), their device tokens, and their verification codes. |
| `audit` | Nothing of its own: the foreign keys delete the user's own log, and anonymize the entries of other logs that name them, as the user's row goes (AUDIT-006). |
| `platform` | The jobs enqueued for the user. Their events and idempotency records go with the user's row, through their foreign keys. |
| `accounts` | The user's row, last, as step 4 says, which its foreign keys carry to their exports (Exporting). |

What the user made in a workspace they share with others is the workspace's, as their export leaves it out (D31): it stays, and keeps nothing that names them (ACCOUNTS-014). The deletion records nothing in the user's own log, which goes with the account; its entries in the logs of the workspaces they shared remain. A user who shared no workspace leaves no row that names them behind: but for the job of ACCOUNTS-015's email, which names no one, until it is sent, and the rate-limit buckets that counted their requests, which hold only keyed hashes and expire on their own (DATA-23), nothing else is left but the request's log line and trace, which hold their ID alone (OBS-04).
The bytes of their files and avatar stay in the bucket until FILES-011 deletes them, as every object that no row names. <!-- part: files -->

The steps take their locks in the order that every other operation takes them on the same rows, so no operation waits for the deletion while the deletion waits for it (DATA-20):

- A rename or an avatar's change locks the user's row `FOR UPDATE` before anything else, and then may lock other rows, such as a workspace's through the foreign key of an event it publishes there. The deletion holds the user's row first, `FOR NO KEY UPDATE`, which such a change waits for, before it locks anything else.
- That mode doesn't conflict with `FOR KEY SHARE`, which the foreign key of every insert that names the user reads. So an operation that locks one of the user's rows and only then inserts a row that names them, such as a refresh, which rotates its session and then records its entry, or a sign-in, which locks the identity and then starts a session, never waits for the deletion's first lock.
- An operation in a workspace first locks its caller's membership (PLATFORM-009), and joining a workspace locks its owner's (ACCESS-008). So the deletion locks the memberships next, then the user's exports, which an export's job locks first, and no operation locks after a membership, then deletes the user's rows that operations lock before they name the user, waiting for any operation that holds one.
- Its last step upgrades its lock on the user's row to `FOR UPDATE`, which waits for the operations that hold the row `FOR KEY SHARE`: each of them has inserted a row that names the user, and waits for none of the deletion's locks. Once the deletion holds that lock, no new row can name the user.

A request of the user's own that started before that lock can still have added a row that names them after the deletion passed its table, such as the membership of a workspace they created, and a further request can lock that row and then wait for the user's row. So, once it holds the user's row, the deletion waits for no lock: the deletion of that row, which its foreign keys carry to the rows that name the user, ends at the first lock another request holds. A membership that remains, whose foreign key, `workspace_memberships_user_id_fkey`, keeps it from going with the user, refuses it too. Both answer ACCOUNTS-016's 409, and the unit of work rolls back, rather than holding the user's row while it waits for another request.

### Exporting

An export copies what each module keeps of the user into an archive that the user downloads, as the General Data Protection Regulation's rights of access and portability ask (Articles 15 and 20): every module's records of them, as JSON, and the bytes of what they uploaded, where a module keeps any (D31). It runs in a job, since a user with many records or files would outlast a request.

1. The request counts in the user's bucket `export` (ACCOUNTS-021), then a unit of work inserts the export, `pending`, which expires 7 days later, records `export.requested`, enqueues `accounts.export` for the caller, and commits (ACCOUNTS-020).
2. The job opens its unit of work through `Database::for_snapshot_job`, under `REPEATABLE READ`, so every module's part reads the user's data as of one moment, and the archive holds no membership of a workspace whose content it lacks, nor bytes whose record it lacks ([platform spec](platform.md#personal-data)). It locks the export's row, and ends unless it is still `pending` (ACCOUNTS-023).
3. It runs each module's personal data contract, in the order the composition root registers them, a deletion's order, the contract of `accounts` last. A contract whose module keeps content of workspaces finds those whose only member is the user through `access::sole_workspaces`, by the user's own memberships, and reads their content by their IDs (DATA-16). Each adds its documents through `personal_data::ExportArchive`, which deflates a page of records at a time through `Workers`, and hands the deflated bytes, in chunks of at most 1 MiB, to the store of `accounts`, which inserts them into `export_chunks`, and each document, once written, into `export_entries` (PLATFORM-084). A contract reads a kind of record that may be numerous a page of 1,000 at a time, so a run holds a page of records, and a document's last chunk, in memory, however many records the user keeps, beside what grows with the archive's size, which is small beside it: the IDs of the workspaces whose only member is the user, and, to lay the archive out, each entry's path, sizes and checksum, a hundred bytes or so, as each download holds them too.
4. It sets the export `ready`, with `ready_at`, and `expires_at` 7 days later (D127), and `size_bytes`, the archive's, which `archive::Layout` gives from the entries; records `export.completed` in the user's own log, through the scope that the job's `JobContext` gives, with no actor, since no request of theirs acts (DATA-22); enqueues the email of ACCOUNTS-025; publishes `export.completed`; and commits.
5. A failed run rolls back whole, so the next attempt starts over. The run of the last attempt that fails makes the export `failed` in a unit of work of its own, once the run's has rolled back (ARCH-11), records `export.failed`, and publishes it, so the user sees it end and requests another once their bucket allows (ACCOUNTS-021). A last attempt that ends without its handler's answer, cut off by its time limit or by its replica's stop (PLATFORM-017), leaves the export `pending`, which `accounts.expire_exports` makes `failed` once 24 hours have passed since its request, since every attempt of its job, and every wait between them, ends within about 2 and a half hours (PLATFORM-014).

The archive is never stored whole (D126). Its download lays it out from what the job stored: `archive::Layout` places, for each entry, the headers that the ZIP format gives it, then the entry's bytes, then the central directory that lists them all, and gives, for any range of the archive, the pieces it is made of (PLATFORM-083). The download's service reads the export, the caller's, ready and not expired, and its entries, then resolves `Wanted` against the archive's size and the export's ID (PLATFORM-081), records `export.downloaded` when it serves bytes, which a `HEAD` doesn't, and commits, before it streams them: the generated headers, and each document's deflated bytes from `export_chunks`, read a few chunks at a time, each read in a transaction of its own that writes nothing (ARCH-11). A read that fails then, as when the export expired and went meanwhile, ends the body short of its `Content-Length`, which its client takes for a cut download. An archive is the same bytes at every download, since its entries, their checksums and the time in their headers, `ready_at`, are stored, so a client that lost a download resumes it with a `Range` (ACCOUNTS-026, OPS-06).
With `files`, the files' contract also records, for each file whose bytes the archive holds, the file's entry in `exported_files`, which `files` owns, with the file's object's key, its size and the CRC-32 that its upload recorded, so the archive copies none of the files' bytes, and stores each as it is, since the kinds that `files` accepts are compressed already, or small; while its export lasts, that row keeps the object from the deletion of unreferenced objects, whose row may since have gone, as when the user deleted the file (FILES-011, FILES-026). The download streams each file's bytes from the bucket, which never change. <!-- part: files -->

The download is a route of the user's own, which authenticates its caller by a credential, the Bearer header or the access cookie, so the archive, which holds everything the user keeps, reaches only a session of theirs.
Unlike a private file's download, it takes no signed URL, which a leaked link would let anyone use for an hour (FILES-022). <!-- part: files -->
 Its email says only that the export is ready, and until when, so a mailbox that someone else reads gives them nothing (ACCOUNTS-025).

`accounts.expire_exports` deletes the expired exports a batch of 1,000 at a time, every hour, with their entries, their chunks and every other row of theirs, which their foreign keys delete; spanning every user by nature, it selects exports by their expiry alone (DATA-16). An expired export answers 404 from the moment it expires, before the job deletes it (ACCOUNTS-022). Deleting an account deletes its exports through the foreign key of `exports`, as the user's row goes (ACCOUNTS-013).

A running export's job holds its export's row from its first statement until it commits, and the user's row `FOR KEY SHARE` from its first insert of a row that names them, such as an event's or its entry's, and it enqueues the export's email. A deletion's last step, which waits for every operation that holds the user's row so, would wait for the job, and erase the user once the job committed, after `platform`'s contract deleted the user's jobs, leaving the export's email to a deleted account. So the deletion locks the user's exports right after their memberships, waiting for no lock, and refuses while a job holds one, with ACCOUNTS-016's 409, before any contract erases anything; the client sends the deletion again once the export is built. An export whose job hasn't started goes with its job, which `platform`'s contract deletes, and its row with the user's. A job whose run starts once the deletion holds its export waits for it, at its first statement, then fails, since under `REPEATABLE READ` a lock meets a serialization failure where a transaction that committed after its snapshot deleted the row; the deletion deleted its job too, so the failed run leaves nothing, and the job never runs again (PLATFORM-017).

### What an export holds

Each contract's documents are in the archive under the folder of its module, such as `audit/log.json`, each an array of records, one to a line (PLATFORM-084). A document is written even when it has no record, so every archive has the same documents. A time is in RFC 3339, in UTC, and an ID is a UUID, as the API answers them.

| Contract | What it exports |
|---|---|
| `workspaces` | `workspaces/workspaces.json`: each workspace whose only member is the user, with its `id`, `name`, `created_at` and `updated_at`. |
| `access` | `access/memberships.json`: each membership of the user's, with its `workspace_id`, `role`, `created_at` and `updated_at`, in every workspace they belong to. |
| `files` | `files/files.json`: each of the user's own files, with its `id`, `name`, `media_type`, `size_bytes`, `visibility`, `created_at` and `path`, the path of its bytes in the archive, `files/own/<id>/<name>`; `files/avatar.json`: the user's avatar, if they have one, with its `id`, `media_type`, `size_bytes`, `created_at` and `path`, `files/avatar/<id>.<extension>`; and `files/workspace_files.json`: each file of each workspace whose only member is the user, with its `id`, `workspace_id`, `name`, `media_type`, `size_bytes`, `visibility`, `uploader_id`, `created_at` and `path`, `files/workspaces/<workspace_id>/<id>/<name>`. In a path, a name has each character that a path or a common file system refuses in a file's name, `/`, `\`, `:`, `*`, `?`, `"`, `<`, `>` and `\|`, replaced with `_`. <!-- part: files --> |
| `invitations` | `invitations/invitations.json`: each invitation of each workspace whose only member is the user, with its `id`, `workspace_id`, `email`, `role`, `expires_at`, `created_at` and `updated_at`. An invitation that others sent to the user's email is the workspace's that sent it, and an invitation the user sent to a workspace that has another member is that workspace's, as a deletion leaves them (D125). <!-- part: invitations --> |
| `auth` | `auth/identities.json`: each of the user's ways to sign in, with its `method`, `created_at` and `updated_at`, and never a password's hash; `auth/sessions.json`: each session, with its `id`, `device_id`, `created_at`, `updated_at`, `authenticated_at`, `access_token_expires_at`, `refresh_token_expires_at` and `expires_at`, and never a token's hash; `auth/device_tokens.json`: each device token, with its `id`, `created_at` and `expires_at`, and never its hash or its email's; and `auth/verification_codes.json`: each code that the user holds, one at most for each purpose, with its `id`, `purpose`, `created_at` and `expires_at`, and never its hash (SEC-03). |
| `audit` | `audit/log.json`: each entry of the user's own log; and `audit/workspace_logs.json`: each entry of the log of each workspace whose only member is the user, with its `workspace_id`. Each entry holds its `id`, `action`, `resource_type`, `resource_id`, `actor_user_id`, `target_user_id`, `details` and `created_at`, and `client_ip` and `user_agent` when its client, the actor or, for an entry without one, the user whose log holds it (AUDIT-006), is the user, and only then, since another user's address and agent are theirs (AUDIT-003, SEC-18). |
| `platform` | Nothing: its events, jobs and idempotency records are bookkeeping, of data that the modules that own it export (DATA-23). |
| `accounts` | `accounts/profile.json`: the user's record, with its `id`, `email`, `name`, `email_verified`, `created_at` and `updated_at`. An export's own rows are the export, and no part of it. |
