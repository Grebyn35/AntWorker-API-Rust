# Spec: `audit`

## Purpose

`audit` records who did what: every module writes entries through it, inside the unit of work of the change, and its `SecurityEventSink` records refused requests (D1, D6). A workspace's owner and admins read its log, each the entries whose permission their role holds, with their IP addresses and user agents, and a user reads their own log and every entry of a workspace's log whose target they are, while deleting a user anonymizes the entries that name them (D166, AUDIT-006). An entry is kept for the deployment's retention, after which an hourly job deletes it, and the database refuses to delete any entry recorded in the last 90 days (D168). The action catalog arrives with the full module's next part.

## Owns

| Table | Holds |
|---|---|
| `audit_entries` | `id`; `scope`, `user` or `workspace`; `user_id`, the user whose log holds an entry of the user scope; `workspace_id`, the workspace whose log holds one of the workspace scope; `actor_user_id`, `target_user_id`, `action`, `resource_type`, `resource_id`; `details`, IDs and non-personal fields only; `permission`, which reading an entry of the workspace scope takes beside `audit.read`, or null for one that whoever reads the log reads, and for every entry of the user scope (Reading a workspace's log); `trace_id` and `created_at`. |
| `deletable_audit_entries` | A view of `audit_entries`, which holds no rows of its own: the `id` and `created_at` of each entry recorded more than 90 days before its transaction began, through which retention deletes entries (AUDIT-005, Retention). |
| `audit_entry_clients` | The client of an entry recorded in a request: `id`, `entry_id`, which is unique; `user_id`, the user whose deletion deletes it: the entry's actor, or, for an entry without one, the user whose log holds it; `client_ip`, which every request has; `user_agent`, null for a request that sent none; and `created_at`. Both `client_ip` and `user_agent` are personal data (DATA-23). |

## Interface

- `record(uow, scope, Entry)`: writes one entry in the given unit of work. The scope names the log and the actor, and comes only from a proof: `Principal::audit_scope`, the user's own log with the user as the actor, or that of `Authorized<P>`, the workspace's log with the member as the actor. `AuditScope::attempt(user_id)` names the log of an account that an unauthenticated request acted on, such as a failed sign-in, or that a subcommand that an operator runs acted on, such as the removal of a second factor (AUTH-072), with no actor.
  `Principal::founder_scope(workspace_id)` names the log of the workspace the caller just created, with them as the actor, before any `Authorized<P>` can name it, and only a user's creation of a workspace may call it, which clippy enforces. <!-- part: workspace_creation -->
  `Principal::invitee_scope(workspace_id)` names the log of the workspace whose invitation the caller accepts or declines, with them as the actor, though they aren't yet, or won't be, its member, so no `Authorized<P>` can name it (INVITATIONS-005, INVITATIONS-017), and only accepting and declining may call it, which clippy enforces. <!-- part: invitations -->
  `AuditScope::setup(workspace_id)` names the log of the workspace that the subcommand `setup-workspace` just created, with no actor, since an operator is no user, and only that subcommand's operation may call it, which clippy enforces (WORKSPACES-023). <!-- part: workspace_setup -->
  `Superadmin::owner_scope(workspace_id)` names the log of the workspace that a superadmin just created, with them as the actor, before any `Authorized<P>` can name it, and only a superadmin's creation of a workspace may call it, which clippy enforces (WORKSPACES-031). <!-- part: superadmins -->
  `Principal::leaver_scope(workspace_id)` names the log of a workspace that the caller leaves as their account is deleted, and only the personal data contract of `workspaces` may call it (ACCOUNTS-014).
- `Retention`, which registers the periodic job `audit.expire_entries`, with the deployment's `AUDIT_RETENTION_DAYS` (AUDIT-011).
- `SecurityEventSink`, implemented for `platform::authz`.
  Its `refused_superadmin` records the refusal of a caller who is no superadmin at a superadmin's route (SUPERADMINS-004). <!-- part: superadmins -->
- `Contract`, the personal data contract for `audit_entries` and `audit_entry_clients` (D31), which exports the user's own log and the log of each workspace whose only member is the user, with the client of each entry the user acted in ([accounts spec](accounts.md#what-an-export-holds)), and whose erasure the foreign keys carry out (AUDIT-006).
- `Action` and `Resource`, the types of an entry's action and of the kind of resource it happened to. Each module declares its actions, named `<resource>.<past-tense verb>`, such as `member.removed`, and its kinds of resource, such as `workspace`, as constants in its own `audit.rs` (ARCH-03): clippy bans their constructors everywhere else. `Action::read_with::<P>(name)` declares an action that a workspace's log shows only to a reader whose role holds `P`, and `Action::new(name)` one that it shows to whoever reads the log, or that only a user's own log records (Reading a workspace's log).

## Design

### Recording an entry

`record` inserts one row through the unit of work's executor, so the entry commits with the change (AUDIT-001), and, in the same statement, the row of its client. The client IP and the user agent come from the unit of work, which opens with its request's (platform spec, "Unit of work"); a job's unit of work holds neither, and records no client, and nor does an operator's subcommand's (AUTH-072). The trace ID is that of the span the entry is recorded in (OBS-07). An `Entry` holds the action, the resource's type and ID, the target user if any, and `details`, a JSON object a module builds from IDs and non-personal fields (SEC-18).

`AuditScope` is a `platform` type whose fields are private: only the proofs build one with an actor, so no module can record an entry as someone the request didn't prove it is (AUDIT-002). A job's run records its entries, of the changes it makes to a module's data (DATA-22), through `JobContext::audit_scope`, in the own log of the user it runs for, with no actor and no client, since no request of theirs made them. An entry of the user scope sets `user_id` and leaves `workspace_id` and `permission` null; one of the workspace scope sets `workspace_id`, and leaves `user_id` null, which the check `audit_entries_scope_check` enforces. An entry of the workspace scope records the permission that its action declares, if any (Reading a workspace's log). `scope` is a Postgres enum (DATA-04), while `action` and `resource_type` are text: each module declares its own actions and resources in its `audit.rs`, so adding one changes no type that every module's entries share.

### Keys and grants

`user_id` references `users` with `ON DELETE CASCADE`, since a user's own log belongs to their account. `actor_user_id` and `target_user_id` reference `users` with `ON DELETE SET NULL`, so deleting a user anonymizes the entries of other logs that name them (D6, D31). `workspace_id` references `workspaces` with `ON DELETE CASCADE`, since a workspace's log belongs to the workspace, through a migration of its own that follows the one creating `workspaces`. The migration that creates the tables revokes `UPDATE` and `DELETE` on both from `app`, which the first migration's default privileges would otherwise grant, and the one that creates `deletable_audit_entries` revokes `INSERT` and `UPDATE` on it, leaving `app` `SELECT` and `DELETE` (AUDIT-005).

An entry's client IP and user agent are its actor's, or, for an entry without one, such as a failed sign-in, are kept as long as the log of the user that holds it. They live in `audit_entry_clients`, whose `entry_id` references the entry with `ON DELETE CASCADE`, and whose `user_id` references that user with `ON DELETE CASCADE`, so deleting the user deletes the client of every entry that was theirs, while the entry stays. Postgres carries out a foreign key's action with the privileges of its table's owner, so the deletion of a user, which `app` may make, anonymizes the entries without `app` holding `UPDATE` or `DELETE` on either table, and no request can change an entry any other way (AUDIT-005). A column of the entry itself couldn't go so: a foreign key's action sets to null only its own columns.

Each log's entries are read the latest first through the index on its user, or its workspace, and the entry's time and ID, and the entries whose target is a user through the index on the target and the entry's time and ID (Reading one's own log), each of which indexes its foreign key too (DATA-05).

An entry names a user only in the three columns that reference `users`, or, in that user's own log, which goes with them, as its resource, so these actions leave no entry that names a deleted user (AUDIT-006): an action on a member names the workspace as its resource, and the member as its target, such as `member.removed`, and an action whose resource is a user, such as `user.renamed`, is recorded only in that user's own log.

### Reading a workspace's log

The route authorizes its reader with `audit.read` (D166). The reader's role decides what the page holds, and `access` decides from it (SEC-08): `access::permissions` gives the names of the permissions the role holds, and the query keeps the entries whose `permission` is null or one of them, so the log keeps from a reader what a permission keeps from them, as the workspace's stream keeps its events by the permission each requires (D2, SEC-19), though the log, unlike the stream, holds entries from before the reader joined, refusals, which no event announces, and changes that publish no workspace event, as a workspace's creation; `access::holds::<AuditReadClients>` decides whether the query joins each entry's client (AUDIT-010). Both read the role that the proof carries, which the policy locked for the unit of work (PLATFORM-009), so a page and its reader's authorization agree.

An action that a workspace's log records declares the permission of the workspace event that its change publishes, such as `members.read` for `member.removed` and `workspace.transferred`, whose events reach the members who may list members; an action whose change publishes no workspace event, as a workspace's creation, declares `workspace.read`. `access.denied` declares none, so whoever reads the log reads a refusal. An entry whose `permission` is null is read with `audit.read` alone, which also covers an entry that a replica of the previous release records while a deploy runs both releases, since its code writes no `permission` (DATA-10).

The query runs through the index on the log's workspace and the entry's time and ID, and the filters narrow the rows it reaches (DATA-17).

### Reading one's own log

A user's own read is the union of two reads, each limited to the page's rows and in the list's order, through its own index: the entries of their own log, by `user_id`, and the entries of the workspace scope whose `target_user_id` is theirs, which no entry of their own log is, so none appears twice. Each filters by the caller's ID alone, which D6 asks of the second: what was done to a user is theirs to see, whatever the workspace (DATA-16). The page joins only the clients whose `user_id` is the caller's, which are the clients of their own log's entries, and of the entries of a workspace's log that they acted in themselves, such as their leaving, as their export holds them (AUDIT-010, the accounts spec's "What an export holds").

### Retention

Each log keeps an entry for `AUDIT_RETENTION_DAYS` after it was recorded, 365 days by default (D6, D168). The setting takes 90 days at least, the floor of `deletable_audit_entries`, so a deployment's retention never asks to delete an entry that the view keeps, and 3,650 at most, ten years.

The periodic job `audit.expire_entries` runs hourly, and deletes through `deletable_audit_entries` the entries recorded before the retention, in batches of at most 1,000, the oldest first, through the index on `created_at`, until a batch deletes fewer; each entry's client goes with it, through its foreign key (AUDIT-011). It spans every log by nature, so it selects entries by their age alone (DATA-16). No entry is ever updated, so none that a batch selects becomes younger while the batch waits (DATA-20). Scheduled maintenance isn't audited (DATA-22), and publishes nothing.

`owner` owns the view, which shows each entry recorded more than 90 days before its transaction began. Postgres deletes through such a view only the rows it shows, with the privileges of its owner on `audit_entries`, so `app`, which holds `DELETE` on the view and none on the table, deletes no entry recorded in the last 90 days, whatever statement it runs, and can't replace the view, which it neither owns nor could create (AUDIT-005, DATA-12). A compromised API process can so delete entries older than 90 days, which a retention longer than that still keeps, and no younger one (D168).

A row lock taken through the view asks for `UPDATE` on it, which would let `app` change the entries it shows, so a batch can't skip the rows that another transaction holds, such as an account's deletion, which sets the actor of entries to null. It waits for no lock but the millisecond that is the least `lock_timeout` Postgres takes, as `auth.expire_unfinished` does, so that transaction never waits for the job while the job waits for it, and the run ends there, leaving the rest to a later run (DATA-20).

### Recording a refusal

A refusal happens before the refused operation has written anything. The `SecurityEventSink` implementation records it in its own short transaction: a member's refusal in the workspace's log, and a non-member's in the caller's own log, so a workspace's log never reveals who probed it. A rank refusal inside an operation reaches the sink through `authz::refuse`, and the operation's own unit of work rolls back (PLATFORM-010). A member's refusal whose workspace's log went with the workspace while the refused request ran (WORKSPACES-017) is refused by the foreign key of the entry's log, `audit_entries_workspace_id_fkey`, which the sink reads by its name (ERR-05): the caller is no member of the workspace any more, so the sink records the refusal in their own log, in a second transaction, as it records a non-member's, with `Refusal::own_scope`. A refusal that goes to its caller's own log, which went with their account meanwhile, such as a read that waited for its own caller's deletion, is recorded nowhere: `audit_entries_user_id_fkey` refuses it, and nothing is left to hold it. Either way the request still answers as refused (AUDIT-004).

A caller who is no superadmin, refused at a superadmin's route, is recorded as `access.denied` too, in their own log, as a non-member's refusal is, with the deployment as its resource, which has no ID; a caller whose account went meanwhile has no log left to hold it (SUPERADMINS-004). <!-- part: superadmins -->
