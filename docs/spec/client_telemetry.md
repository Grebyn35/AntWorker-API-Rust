# Spec: `client_telemetry`

## Purpose

`client_telemetry` holds the telemetry of each user's clients, such as a desktop client's traces, logs and metrics: whether the user consents to their clients' sending it, which the module stores, and the telemetry proxy, through which a consenting user's client sends its spans, its log records and its metrics to the deployment's collector, and which enforces the consent on the server (D7, D122).

## Owns

| Table | Holds |
|---|---|
| `telemetry_consents` | One row for each user who chose whether their clients send their telemetry: `id`, `user_id`, which is unique, `consented`, `created_at`, when they first chose, `updated_at`, when they last did, and `version`. `user_id` references `users` with `ON DELETE CASCADE`. A user without a row never chose. |

## Interface

- `Contract`, the personal data contract for `client_telemetry` (D31), which exports the user's consent, and whose erasure deletes it (CLIENT_TELEMETRY-003).

## Routes

| Method and path | Access | Behaviors |
|---|---|---|
| `GET /v1/users/me/telemetry-consent` | user | CLIENT_TELEMETRY-001 |
| `PUT /v1/users/me/telemetry-consent` | user | CLIENT_TELEMETRY-002 |
| `POST /v1/users/me/telemetry/traces` | user | CLIENT_TELEMETRY-004 to CLIENT_TELEMETRY-013, CLIENT_TELEMETRY-016 |
| `POST /v1/users/me/telemetry/logs` | user | CLIENT_TELEMETRY-004 to CLIENT_TELEMETRY-013, CLIENT_TELEMETRY-016 |
| `POST /v1/users/me/telemetry/metrics` | user | CLIENT_TELEMETRY-004 to CLIENT_TELEMETRY-010, CLIENT_TELEMETRY-013 to CLIENT_TELEMETRY-016 |

`PUT /v1/users/me/telemetry-consent` accepts an `If-Match` (API-13, PLATFORM-071).

The proxy's three routes take a batch of telemetry, the body of a request of the OpenTelemetry Protocol (OTLP) over HTTP, in place of a JSON body (PLATFORM-090).

## Design

### The consent

A user consents to nothing until they choose to, so no client of theirs sends their telemetry before then (D7). The consent is the user's, for every client they sign in to, and each of their clients reads it once the user has signed in: neither `GET /v1/users/me` nor a session's response holds it, since `accounts` and `auth` don't know the part (D122). A client then follows each `telemetry_consent.updated` that reaches its streams, whose payload holds the consent, since the event reaches only the user's own streams (SEC-19), so a choice made on one device reaches the others without a read; a client tells the event of its own choice by its trace ID ([realtime spec](realtime.md#design)). The capabilities' member `client_telemetry` tells a client whether its deployment forwards its telemetry, and is absent from an API that doesn't have the part at all ([system spec](system.md#capabilities)).

The consent is always written whole, so a choice is a `PUT` of it (API-03). A choice writes, records and publishes even when the consent is the one stored, as a rename does (ACCOUNTS-007), so the caller's own log holds each choice they made, which tells them when they consented (DATA-22).

### Its version

A user who never chose has no row, and their consent reads as `false` at version 0. Their first choice inserts the row of the consent that no one chose, `consented` false at version 0, which the same unit of work then updates, so the trigger moves its version to 1 (DATA-02), and an `If-Match` of `"0"` names the consent until a choice commits. No row stays at version 0: a choice that its `If-Match` refuses rolls the insert back with the rest.

### A choice's unit of work

1. Its first statement inserts the row of the consent that no one chose, unless the user has a row. Its foreign key reads the user's row `FOR KEY SHARE`, which waits for a deletion of the account that holds the row `FOR UPDATE`, the deletion's last step, and then refuses the row once the deletion has committed (ERR-05).
2. The next locks the user's row of `telemetry_consents` `FOR UPDATE`, so two choices of one user take turns (DATA-20), and finds none once a deletion that committed meanwhile took it with the account.
3. The update writes the choice with the versions that `If-Match` names in its `WHERE` (DATA-18).

A refusal of the first two answers 401, as CLIENT_TELEMETRY-002 says, and of the third 412. The entry is recorded, the event is published, and the unit of work commits.

A choice locks its row of `telemetry_consents` before its entry and its event name the user, so a deletion of the account deletes that row in the contract's erasure, waiting for a choice that holds it, as the deletion's lock order asks of such a row ([accounts spec](accounts.md#deleting-an-account)). A choice that inserted the row holds the user's row `FOR KEY SHARE` from then on, which the deletion's last step waits for, as the same order says. A choice that waits for the erasure answers 401 once the deletion commits, as CLIENT_TELEMETRY-002 says.

### The proxy

The proxy makes the API the OTLP/HTTP endpoint of its users' clients, so a client holds no address and no credential of the collector: its exporter posts each batch to the API, with its user's session, as the client sends any other request (D175). Its routes are under `/v1/users/me/`, as the caller's own resources are (API-02): a batch is its caller's, counts in its caller's budget, and needs its caller's consent. An exporter takes each route as the endpoint of its signal, such as the `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` of OpenTelemetry's SDKs, since the three paths aren't the protocol's `/v1/traces`, `/v1/logs` and `/v1/metrics` under one base.

A request and its success are the protocol's: the two media types, gzip, and a 200 that holds the full success in the request's media type (CLIENT_TELEMETRY-004). A failure is a problem, as every route's is (API-07), where the protocol asks for its own `Status` message, and its status says what the protocol's does: an exporter sends a batch again after a 429 or a 503, once `Retry-After` has passed, and after no other failure.

The API doesn't parse a batch. It forwards the bytes, and the collector decides what it keeps of them ([below](#what-the-collector-keeps)), so the API holds no decoder of the protocol's messages, and a batch that isn't the protocol's request is refused by the collector (CLIENT_TELEMETRY-009). It answers the full success itself, rather than relaying the collector's body, so its answer is the same whatever collector a deployment runs.

A client sends nothing while its user doesn't consent ([the consent](#the-consent)), and the API forwards nothing of a batch that one sends anyway (CLIENT_TELEMETRY-005, D7).

### A batch's steps

1. The pipeline counts the request in its client IP's bucket, authenticates it, and counts it in its user's bucket, as it does any request (PLATFORM-054).
2. The route reads the body, up to 1,048,576 bytes, and inflates one that came as gzip, up to as many (CLIENT_TELEMETRY-006). A replica reads at most 8 batches at once, each in a turn that it holds until the collector has answered, so the batches in its memory take at most 8 times that, twice over while they inflate, whatever the concurrency limit lets in, and a user's batches hold one of those turns between them, so one user's slow bodies leave the others' batches their turns (PLATFORM-090).
3. Without `CLIENT_TELEMETRY_ENDPOINT`, the request ends with 503 (CLIENT_TELEMETRY-010).
4. The service reads the caller's consent, as CLIENT_TELEMETRY-001 does, and refuses a caller who doesn't consent (CLIENT_TELEMETRY-005).
5. It counts the bytes in the caller's budget, then in the replica's (CLIENT_TELEMETRY-007, CLIENT_TELEMETRY-008).
6. It forwards the batch, and answers as the collector took it (CLIENT_TELEMETRY-004, CLIENT_TELEMETRY-009).

The route reads the body before the service decides anything, since a handler calls one service function (ARCH-08), which takes the bytes; what a caller who doesn't consent sends is read within the same bounds, and dropped. The service reads the consent in a short transaction that writes nothing, before the budgets count: the read decides whether they count the batch at all (ARCH-11), so the batch of a caller who doesn't consent counts in none. No unit of work follows, since the proxy writes nothing but the budgets' counts. A withdrawal that commits after the fourth step doesn't stop the batch: the proxy reads the consent once.

### The budgets

A user's budget bounds what one account can send, and the replica's what every account together can, such as the accounts that one person registers (D176). Both count a batch's bytes once inflated, which is what the collector takes in.

Both are buckets in the database, as every limit is (PLATFORM-089). The user's counts for the user's ID, so it is one budget whichever replica a batch reaches. The replica's counts for an ID of 16 random bytes that the replica draws as it starts, so each replica's budget is its own: the deployment forwards at most that many bytes in each window of each replica that it runs, and a replica that starts again starts a new budget. One budget for the whole deployment would be one row that every batch of every user updates, each waiting for the last one's commit; a replica's row is updated by the batches that the replica reads, at most 8 at once.

Each setting is at least 1,048,576, the largest batch, so no batch is larger than a whole window. A batch that a budget refuses stays counted in it, as a refused request does in a bucket (PLATFORM-055), so the window refuses what comes after it too: an exporter waits for `Retry-After` before it sends again. A batch that the replica's budget refuses has counted in its user's first, and one that the collector doesn't take has counted in both.

By default, a user's budget is the largest batch, and a replica's four times a user's, so that a deployment that raises a user's budget alone raises the replica's with it (CLIENT_TELEMETRY-008, D180). A window of a replica's budget holds at most two of one user's windows, each of which starts with the user's first batch after the last one ended (PLATFORM-055), so one user's clients count at most twice the user's budget in it: at the defaults, no one user's batches fill a replica's budget, and those of four users who each send all that one may do. A replica's budget that a setting puts at twice a user's or below is one that a single user's clients can fill, which a deployment may choose, to bound what its stores take in before all else. A deployment raises the replica's budget with the users whose clients send, and with the disk of Tempo and Loki, whose intake of the clients' spans and log records the budget bounds: [observability.md](../operations/observability.md#what-the-clients-telemetry-adds) works that bound out.

### What the collector keeps

The collector takes the batches that the API forwards on a receiver of their own, and passes them through pipelines of their own, which [observability.md](../operations/observability.md#how-telemetry-flows) describes (D177). It keeps the spans, the log records and the metrics of the services that its [configuration of clients' telemetry](../../deploy/observability/collector/clients.yaml) lists, which is `app-desktop` in the template, and a fork lists each of its clients there. It keeps of the resource of a span or of a log record only the attributes that CLIENT_TELEMETRY-011 names, so a store holds nothing that an SDK adds about the user's machine, such as its host's name. A batch from a service that isn't listed answers 200 all the same: the API doesn't read the batch, and the collector answers the full success for what it drops (CLIENT_TELEMETRY-012).

The protocol forbids a resource that names an attribute twice, and the collector's receiver takes one. The collector's conditions read the first value of an attribute that a resource names twice, and Loki labels the stream by the second, so the collector writes the attributes that it keeps anew, from the first value of each: a resource that names a listed client first and the API second is stored as the client's alone (CLIENT_TELEMETRY-012).

### The clients' metrics

A client's metrics become series of every installation together, not of each one (D179). A series for each installation would be one more in Prometheus for each installation and each of its metrics, with the installation's ID as a label, which OBS-11 keeps out of the API's own metrics, so the collector adds every installation's points into one series for each set of the attributes' values that it keeps, and a metric keeps nothing of its resource but the client's name (CLIENT_TELEMETRY-014).

Points can be added up only when each holds what its client measured since its last one, which the protocol calls delta temporality, and which OpenTelemetry's SDKs send with `OTEL_EXPORTER_OTLP_METRICS_TEMPORALITY_PREFERENCE=delta`. The collector drops a point that holds what its client measured since it started (CLIENT_TELEMETRY-015). It sets the time of each point to the moment it takes it, since the sum takes points in the order of their times, and each client's clock sets its own. A series counts from its first point since the collector started, or since an hour passed without one, and Prometheus scrapes the series from the collector, which serves each one between its points too, so that a count that seldom grows still shows its increase; [observability.md](../operations/observability.md#how-telemetry-flows) describes the path, with a managed backend too.

The collector keeps the metrics that its configuration lists, each with the attributes that the file lists for it and the values that it lists for each attribute, so the series that the clients can make are those that the lists allow: every value that stayed as a client wrote it would be one more series (CLIENT_TELEMETRY-015). The template lists `http.client.request.duration`, the metric that OpenTelemetry's conventions define for a client's HTTP requests, which counts them and how long each took, by the response's status, or by `error.type` for a request that got none. A fork lists the metrics of its clients in the same way, each attribute with the values it can take, a counter of a client's own, which the conventions don't define, among them.

A client reports the numbers itself: the lists bound which series exist, and not what they count. So the clients' series inform, on the dashboard of clients' telemetry, and no alert reads them (OBS-14).

### Operating it

The request metric says how the proxy's batches end, by route and status, with the error code of a 5xx (PLATFORM-067), and `platform.rate_limit_refusals` which budget refused one. `client_telemetry.forwarded` counts the bytes of the batches that the collector took (CLIENT_TELEMETRY-013), which the replicas' budgets bound. Tempo and Loki take in no more of the clients' spans and log records than those batches hold, since the collector drops what its configuration doesn't list. The bytes of the clients' metrics say nothing of what Prometheus stores of them, which is the series that the collector adds up, at each scrape. The Clients' telemetry dashboard shows how the batches end, the bytes forwarded, what the collector refuses or fails to pass on of the clients' batches, the points that it leaves out of its sums, and the clients' own series, and the API platform dashboard shows each budget's refusals among the rate limits' ([observability.md](../operations/observability.md#the-questions-it-answers)).

Two alerts open a ticket (OBS-14): `ClientTelemetryNotForwarded`, for batches that the collector neither takes nor refuses, which the proxy answers with 503, while it takes none, and `ClientTelemetryBudgetSpent`, for batches that a replica's budget refuses. Their runbooks say what each means, and what to do: [ClientTelemetryNotForwarded](../operations/runbooks.md#clienttelemetrynotforwarded) and [ClientTelemetryBudgetSpent](../operations/runbooks.md#clienttelemetrybudgetspent). A user's own budget that refuses raises none: it bounds one account, and the API platform dashboard shows it. The collector's own alert names the clients' receiver and exporters when they lose telemetry ([runbooks.md](../operations/runbooks.md#collectordroppingtelemetry)).
