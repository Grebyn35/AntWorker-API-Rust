# Spec: `platform`

## Purpose

`platform` holds the mechanisms every module uses: the unit of work, the proofs that authentication and authorization produce, background jobs, sending email, events and the real-time hub, the HTTP stack, errors, configuration and telemetry. It contains no product rules (ARCH-02). [architecture.md §4](../architecture.md#4-crates) lists its areas.

This spec covers what the modules built so far need. The telemetry proxy and the remaining areas are specified when the modules that use them are built.

## Owns

| Table | Holds |
|---|---|
| `events` | Published events, kept for replay |
| `jobs` | The job queue: one row per job that waits, runs or is dead-lettered, with its kind, payload, scope, trace context, attempts and lease. A job's row goes when it succeeds. |
| `job_schedules` | One row per periodic job, holding its lease and next run |
| `idempotency_records` | One row per user and idempotency key whose operation committed, with its fingerprint and its result |
| `rate_limit_buckets` | Rate-limit counters, keyed by a hash-based message authentication code (HMAC) |
| `_sqlx_migrations` | The applied migrations, recorded by `migrate` |

## Interface

- **Database:** `Database`, the pool of connections as the role `app`, which `serve` connects once at startup. Connecting runs the startup checks (PLATFORM-001, PLATFORM-030), and `begin` opens a unit of work.
- **Unit of work:** `UnitOfWork`, opened with the request's `Client`, or with a job's `JobContext` through `for_job` (Design: Unit of work), with `executor`, `commit`, `enqueue`, `publish_to_user` and `publish_to_workspace`, `order_with_events`, which an operation that adds a membership calls (Design: Events and the real-time hub), and `claim` and `commit_with` for an idempotency key.
- **Events:** `UserEvent<T>` and `WorkspaceEvent<P, T>`, the declarations of the events a module publishes, in its `events.rs`, each with `T`, the type of its payload, and registers with its routes through `Routes::events`, which adds them to the event catalog ([realtime spec](realtime.md#the-event-catalog)); `events::signal`, which sends an `AccessChange` when its unit of work commits (D35); `events::listen`, which `main.rs` runs as a step of startup, with `startup.area` `listener` (OPS-03), and which opens the listener, listens there, and then reads the last position given, from which the hub loads, so every event that commits after startup is one it loads; and `Hub`, the real-time hub, which the composition root starts once on that connection, and whose `subscribe` opens a caller's stream, a `Subscription` that yields that it opened, each event for it, and the reason the hub closed it (Design: Events and the real-time hub).
- **Mail:** `MailConfig`, the email settings that `ServerConfig` holds (PLATFORM-024); `Email`, a module's email, rendered, to one recipient; and `Mail`, built once from the settings, whose `send` enqueues an `Email` in a unit of work, whose `is_on` says whether email is on, and whose `register` registers the job `platform.send_email`, which sends what `send` enqueued over the Simple Mail Transfer Protocol (SMTP) (Design: Sending email).
- **Jobs:** `Job`, the trait of a queued job's payload, which names its kind, its most attempts and its time limit; `JobScope`, the user or workspace a job runs for, which only a proof builds, through its `job_scope`, but the scope of no one, which only `platform`'s scheduler builds; `JobFailure`, which says whether a failed run may be retried; and `Jobs`, the registry of every queued and periodic job's handler, whose `run` runs the dispatcher and the scheduler until shutdown (Design: The job queue).
- **Request context:** `Client`, the request's client IP (PLATFORM-053) and user agent.
- **Rate limits:** `RateLimits`, which a route takes from the request and hands its service, whose `check` counts the request in a bucket that the module names, and refuses it once the bucket is full, for a per-action limit such as AUTH-006 (PLATFORM-011). `RateLimiter`, whose `count` counts in a bucket, does the counting for it and for the pipeline's IP limit and its user limit.
- **Request bodies:** `Json<T>`, the extractor of a JSON body (PLATFORM-049), `MergePatch<T>`, the extractor of a `PATCH` route's JSON Merge Patch (API-03), `Idempotent<T>`, which a keyed route extracts instead, the body with its request's `IdempotencyKey` (PLATFORM-037), and `FieldErrors`, which collects every field that a request type's conversion into domain types refuses (PLATFORM-051), or every query parameter (PLATFORM-045).
  `Upload` is the body of an upload route, whose `read` gives the bytes, with their key, in one of the replica's turns, digesting a keyed upload's bytes through `Workers` (PLATFORM-074, CODE-05), and `disposition_name` reads the name an upload gives in `Content-Disposition` (PLATFORM-075). <!-- part: files -->
- **Files:** `Download`, the response that serves a stored file's bytes, or a range of them, so that a browser can't run them (SEC-11, PLATFORM-081); `Wanted`, what a download's request asks of the bytes, which a handler extracts and the service resolves against the file's size with `serve`, into `Served`, every byte, one `ByteRange` or none (PLATFORM-081); `SignedUrls`, whose `sign` gives a download's path signed for a session, until a time (PLATFORM-080); `FileBytes`, which documents an upload's body and a download's as a binary string (API-17); and `Storage`, the client of the bucket that holds files' bytes, which `StorageConfig`, in `ServerConfig`, describes (PLATFORM-076), with `put`, `get`, which streams an object's bytes, or a range of them, `delete` and `list`, which gives each object as `Listed`, its key and when the bucket wrote it, each failing with `StorageError`, and `ObjectKey`, an object's random key (Design: Storage); and `Scanner`, the client of the malware scanner, which `ScannerConfig`, in `ServerConfig`, describes, whose `scan` gives a `Verdict`, `Clean` or `Found` with the signature's name, or fails with `ScanError` (PLATFORM-079, Design: Scanner). <!-- part: files -->
- **Idempotency:** `UnitOfWork::claim` and `commit_with`, which keep an operation's result under its key (API-12).
- **Preconditions:** `IfMatch`, the extractor of an update's `If-Match`, which gives the `Version`s it names, the type of a row's `version`, whose `etag` is the value of the `ETag` header that names it (PLATFORM-071, Design: Preconditions).
- **Resources:** `ResourceResponse<T>`, the response that answers a resource: `ok`, or `created` with the path that reads it, which `Location` carries, and `tagged` with the version of an editable resource, which `ETag` names (API-04, PLATFORM-071); and `path_id`, the ID of a row that a path parameter names, or `None` for one that isn't a UUID (PLATFORM-072).
- **Lists:** `Query<T>`, the extractor that parses a request's query parameters into `T`, the type that documents them, from which a route reads `Page`, a list's `limit` and `cursor` (API-06), and `Search`, its `search` (API-20), and whose fields it documents with the schemas of `Limit`, `Cursor` and `Search`, which carry each parameter's limits (API-17); and `List<T>`, the body of a page of items, with its next cursor (API-05).
- **CPU-heavy work:** `Workers`, the turns of the instance's CPU-heavy work, such as a password's hash, whose `run` runs a work on a blocking thread, inside a span of its own, once a turn is free (PLATFORM-060, Design: Workers).
- **Tasks:** `bootstrap` and `migrate`, run by the binary's subcommands of the same names (ARCH-14).
- **Routes:** `Routes`, through which every module registers its routes and their documentation (API-14, API-17), and its events (REALTIME-008), and `http::app`, which wraps them in the request pipeline, with the API reference in development (PLATFORM-052).
  A module adds an upload route through `workspace_upload` or `user_upload` (PLATFORM-074), and a download route through `workspace_download` or `user_download`, which take a signed URL (PLATFORM-080), or `public_download`, each documenting what a download serves (PLATFORM-081). <!-- part: files -->
- **Errors:** `Category`, and `Problem<E>`, the one conversion of an error into a response (ERR-07).
- **Lifecycle:** `Readiness`, `ShutdownSignals` and `serve`, which runs the server until a shutdown signal and then shuts it down (OPS-05, OPS-06), and `probe`, which the `health` subcommand runs (PLATFORM-063).
- **Proof types:** `Principal`, `Authorized<P>`, `Memberships` and `JobContext`, and `AuditScope`, the log and the actor of an audit entry, which only a proof builds with an actor ([audit spec](audit.md#recording-an-entry)). `Authorize<P>`, the extractor of a workspace route, proves nothing until its `open` (Design: Unit of work).
  Its `check` refuses a caller as `open` would, with no unit of work left open (PLATFORM-073). <!-- part: files -->
- **Traits that modules implement** (ARCH-13):
  - `SessionVerifier`, implemented by `auth`, with `verify`, and `lasting`, which says which of a set of sessions still last, for the hub's re-check.
    Its `session` proves the principal of a session that still lasts by its ID, for a signed URL. <!-- part: files -->
  - `AccessPolicy`, implemented by `access`, with `authorize`, and `memberships`, which gives each of a set of users their `Memberships`: every workspace they belong to, with the permissions their role holds there and the transaction that added the membership.
  - `SecurityEventSink`, implemented by `audit`.
  - The personal data contract.
- **Traits that modules use:** `Permission`, `ErrorCode`, and `Job`.
- **Calls:**
  - `authz::refuse(uow, &Authorized<P>)`: for a refusal inside an operation, rolls its unit of work back, records the refusal as a security event, and gives the 403 `request.permission_denied` (PLATFORM-010).
- **Services:**
  - the job registry and scheduler
  - the outbound HTTP clients (SEC-10)
  - the clock and the random source (CODE-06)
  - the metric declarations: `Counter`, `Histogram` and `Gauge` (OBS-11)
  - the list of telemetry names (OBS-05)

A `Range` of several ranges, or one it can't serve, such as one that starts past the last byte or names another unit, is ignored, and the download answers 200 with every byte, as RFC 9110 allows. An `If-None-Match` that is `*`, or names the entity tag, weak or strong, answers 304 with no body. `HEAD` answers as a `GET` without `Range` does, without the bytes, since RFC 9110 has a server ignore `Range` on every other method. <!-- part: files --> | SEC-11, SEC-12, OPS-06, D112 | `platform_081_` |

## Design

### Database roles

`bootstrap` connects with `DATABASE_ADMIN_URL`, as an administrator such as the bundled Postgres superuser or a managed provider's admin role. The three database URLs must name the same database.
- It creates the roles `owner` and `app` with `LOGIN` and no other attribute. A role that already exists is given `LOGIN` and keeps its other attributes, because changing some of them takes a superuser, which a managed provider's admin role isn't. PLATFORM-001 refuses an `app` role whose attributes are unsafe.
- It sets each role's password from its URL. The password travels as a verifier, the stored form of a password in SCRAM-SHA-256 (Salted Challenge Response Authentication Mechanism with SHA-256). The API computes the verifier on a blocking thread (CODE-05), so the clear text never reaches the server, where statement logs could record it. The administrator connection logs none of its statements, because they carry the verifiers (OBS-04).
- It sets the `app` role's `statement_timeout` to 30 seconds and its `idle_in_transaction_session_timeout` to 15 seconds (DATA-19), and its `default_transaction_isolation` to `read committed` (DATA-20). Set on the role, these hold whatever the server or the database defaults to.
- On the database, it revokes `TEMPORARY` from `PUBLIC`, grants `CONNECT` to both roles, revokes `CREATE` on the schema `public` from `PUBLIC`, and grants it to `owner` only. A database created by a Postgres older than 15 grants `PUBLIC` that `CREATE`, which would let `app` create tables.

The first migration grants `app` `SELECT`, `INSERT`, `UPDATE` and `DELETE` on every table `owner` creates, revokes `EXECUTE` on new functions from `PUBLIC`, and lets `app` read the migrations table. Roles belong to the whole Postgres server, so every database on a server shares them, test databases included. Two deployments whose databases share a server would share the roles: one's `bootstrap` would set their passwords to its own, and its URLs would reach the other's tables. So a deployment's Postgres server holds no other deployment's database, as [deploy.md](../operations/deploy.md#choosing-the-services) requires of a managed one and of [another platform's](../operations/deploy.md#on-another-platform) (D75). In production, `bootstrap` checks it before it changes a role: another database that `owner` or `app` owns, or holds a privilege on, as each database that `bootstrap` ran on grants them `CONNECT`, is another deployment's, and `bootstrap` refuses, naming the first by name (PLATFORM-003). Development and the tests keep all their databases on one server, the tests' sharing the roles by design, so it checks nothing there.

Two `bootstrap` runs at once can't both be relied on: they update the same roles, and one can fail with "tuple concurrently updated", since nothing serializes them: `bootstrap` takes no lock, and an advisory lock would serialize only the runs on one database, while roles belong to the whole server. The reference deployment runs `bootstrap` once per deploy, and one deploy at a time (OPS-14), so its runs never overlap. The tests' runs on one server take turns at a lock of the test support, and each managed deployment of the end-to-end tests has a server of its own ([ci.md](../operations/ci.md)).

### Migrations

`migrations/` holds one file per change, named `<timestamp>_<module>_<description>.sql` (DATA-09), and the `app` crate embeds them as `MIGRATIONS`. `migrate` takes an advisory lock on the database, compares every applied migration with its file before it applies anything, then applies each missing migration in its own transaction together with its record. It never applies a down migration, and it refuses a migration marked `-- no-transaction`, which would run outside a transaction, so a failure part way through it would leave a trace (PLATFORM-005).

### Connections

`Database::connect` opens a pool of up to `DATABASE_MAX_CONNECTIONS` connections as `app` ([`.env.example`](../../.env.example) gives its default). An operation waits up to 5 seconds for a free connection. The startup checks run on the first connection: the role (PLATFORM-001), then the schema (PLATFORM-030). The role check covers objects the role owns in every database of the server.

A database URL is the only source of its connection's settings (OPS-01). It sets the user, password, host and database itself, and the port too, or the port is 5432. It may set only the query parameters that `.env.example` lists for `DATABASE_URL`. The Postgres driver also reads libpq's environment variables, so the ones that `.env.example` lists, which could change a connection the URL describes, must be unset, even to an empty value. Every subcommand that reads a database URL refuses to start while one is set.

The certificates a verified connection trusts are the one input the URL doesn't decide alone. With `sslmode` set to `verify-ca` or `verify-full`, a connection trusts the certificates in the URL's `sslrootcert`, if any, together with the system's: the operating system's certificate store, or instead the files that `SSL_CERT_FILE` and `SSL_CERT_DIR` name when either is set. The driver adds `sslrootcert` to the system's certificates instead of replacing them. Those two variables are how an operator chooses the certificates a container trusts, such as in an image with no certificate store, so the API leaves them to the TLS library.

The driver reads the system's certificates each time it opens a verified connection: a short blocking read on the async runtime, which CODE-05 allows here. It happens when the pool, or the readiness check of PLATFORM-061, opens a connection, not on every query. Certificates compiled into the binary would avoid the read, but the list the driver offers for that, `webpki-roots`, is licensed CDLA-Permissive-2.0, which CODE-13 doesn't allow.

Pools, connections and transactions stay inside `platform::db`, and code elsewhere reaches the database through a unit of work (DATA-15). The test support is the one other place that names them (TEST-05): it creates and drops test databases, arranges tests with statements no unit of work may run, and reads stored state as `owner` or as the administrator. It gets its connections from `platform::db::testing`, which only the `test-support` feature compiles and only the tests enable, so the API never hands out a connection, or the connection options whose `Debug` output includes the password (SEC-01).

### Unit of work

A unit of work is one transaction on the `app` pool. It opens after authentication, the rate-limit checks and parsing, so no transaction waits on a slow client, and no request holds a pooled connection while it waits for a second one:
- On a workspace route, it opens together with `Authorized<P>`. The handler extracts `Authorize<P>`, which holds the caller's `Principal` and the workspace ID from the path, and calls its `open` once the body is parsed, since axum runs the body's extractor after every other: the transaction opens, `AccessPolicy::authorize` runs inside it, and `open` returns the open unit of work with the proof, which the handler hands the service, or the refusal (PLATFORM-009). A route with a per-action limit hands the service its `Authorize<P>` instead, and the service calls `open` once the limit has counted, as on a user route.
  An upload route, whose body a parsed extractor would read before anything could refuse the caller, first calls `check`, which authorizes the caller as `open` would, refusals and their records included, in a short transaction that writes nothing, then reads the body, and opens the unit of work last, which authorizes the caller again (PLATFORM-073, ARCH-11). <!-- part: files -->
  `authorize` reads the caller's membership `FOR SHARE`, so a removal or a role change of that membership waits until the operation commits or rolls back, and the operation runs under the role it was authorized with. An operation that changes another member's row changes it only where the caller outranks that member, in the statement that changes it, so a row it may not change is skipped without being locked (access spec, "Removing a member"). No two operations then wait on each other's rows, since no two members each outrank the other (SEC-09, DATA-20).
- On a user or public route, the service opens it from the `Database`, with the request's `Client`, once any per-action limit it checks has counted. A read that decides which limit counts, such as a sign-in's of its device token, comes first, in a transaction of its own that writes nothing and ends before the limit counts (ARCH-11).
- A job handler opens it with `for_job`, from the job's `JobContext`.
- The hub opens its own reads, which act for no request and no job, with `unattributed`, which only `platform` calls, and holds none while it waits for the hub's task (Events and the real-time hub).

The service performs the writes and commits. A unit of work dropped without a commit rolls back, and nothing retries it. Every query in it filters by tenant itself (DATA-16). The unit of work sets no database context, because there is no row-level security (D4). A unit of work that opens for a request holds the request's `Client`, whose client IP and user agent the audit entries it records keep (AUDIT-003); a job's holds none.

### Request authentication

`Principal` reads the access token from the `Authorization` header when the request has one, which must hold `Bearer` and a token, and otherwise from the cookie `__Host-access_token` (AUTH-015). A request that the cookie authenticates and whose method isn't safe also passes the cross-site check (PLATFORM-059) before it is verified.

`SessionVerifier` hashes the presented access token with SHA-256 (SEC-03), and reads the session through the unique index on `sessions.access_token_hash`. It checks the expiry in SQL against `now()`. It returns a `Principal` holding the user's ID and the session's ID. A missing or unknown token answers 401 `request.unauthenticated`, and an expired one 401 `request.access_token_expired`. The request is then counted in its user's bucket (PLATFORM-054).

A download route that takes a signed URL marks its requests so, through the layer its builder adds, and `Principal` reads such a request's `expires`, `session` and `signature` before any header or cookie (PLATFORM-080). It computes the HMAC of the request's path, the session and the time, under `HMAC_KEY` with the kind `signed_url`, and compares it with the signature in constant time. `SessionVerifier::session` then reads the session by its ID, which the signature proves the API gave, and proves its principal while it lasts, as `lasting` decides (AUTH-018), comparing the time with the database's clock in the same statement (DATA-03). The time a link signs comes from that clock too, so every replica agrees on when a URL stops working. The handler then authorizes the principal as it does any caller, so a signed URL gives only what its session's user may still do (D113). `SignedUrls::sign` gives a path with the three parameters, signed until the time it is given, which the module takes from the database's clock: the service of `files` gives the moment an hour from now ([files spec](files.md#links)). A route that takes no signed URL doesn't document the three parameters, so a query that holds one answers 400 `request.invalid_query` there (PLATFORM-045). <!-- part: files -->

### Client IP

Each request's `Client` holds its client IP and its user agent. The client IP is the connection's peer, unless the peer is listed in `TRUSTED_PROXIES`, as addresses or ranges (PLATFORM-053). A proxy appends to `X-Forwarded-For` the address it received the request from, so the addresses on the right were written by trusted proxies, and the first untrusted one, read from the right, is the client that the outermost trusted proxy saw. An address further left could have been written by anyone. The reference deployment lists the private address ranges, since only its own containers reach a replica, on its private networks, and the addresses its proxy trusts in turn, such as a content delivery network's, which `TRUSTED_PROXIES` in [settings.env.example](../../deploy/settings.env.example) gives both.

### Refusals

`AccessPolicy::authorize` answers one of three things:
- not a member, which becomes 404 `request.not_found`
- a member without the permission, which becomes 403 `request.permission_denied`
- the member's role, from which `Authorized<P>` is built

A path whose workspace ID isn't a UUID names no workspace: it answers 404 `request.not_found`, as a path that no route serves does, and nothing records or counts it. A refusal is reported to the `SecurityEventSink`, which records it in its own short transaction, because the refused operation has written nothing. A member's refusal goes to the workspace's log, and a non-member's to the caller's own log. A rank refusal found inside an operation goes through `authz::refuse`: the operation's unit of work rolls back, and the refusal is recorded the same way (PLATFORM-010). A refusal names the caller, the workspace, the permission, whether the caller is a member, and the request's `Client`, and the sink records it with the trace ID of the span it is reported in. A sink that fails to record fails the request as an internal error, so no refusal goes unrecorded (DATA-22).

`Permission` is the trait of a permission type, which gives its name, such as `members.read`. The builder `workspace::<P>` registers a route whose handler extracts `Authorize<P>`, and documents the operation's access as `workspace` and its permission as `x-permission`, which TEST-08's generated test reads. A route of `superadmins` (D62) will be authorized the same way, by a proof of its own: a builder `superadmin` whose handler extracts that proof, which a trait of its own, implemented by `superadmins`, checks inside the unit of work, and whose refusals reach the same sink. Neither `Authorized<P>` nor any workspace route changes for it.

### Rate limits

Three kinds of bucket count requests:
- the IP limit's bucket, `ip`, which the pipeline counts before authentication, of every request but the health probes and a listed origin's preflight
  A request whose path is under `/v1/public/`, the prefix of public downloads, of files and avatars ([files spec](files.md#visibility)), counts in the IP limit's bucket `public` instead. <!-- part: files -->
- the user bucket of every authenticated request, which `Principal` counts once it has verified the session
- the bucket of a per-action limit, which a module counts through `RateLimits::check`, such as the sign-in email's (AUTH-006)

A check counts the request before the operation's unit of work opens, in one statement on a pooled connection, outside any transaction, so the count commits at once and survives whatever happens next (PLATFORM-011). The statement inserts the bucket, adds one to its count, or starts a new window when the last one has ended, and returns the count and the window's end, all by the database's clock (PLATFORM-055). A bucket's key is an HMAC-SHA-256, under `HMAC_KEY`, of its kind and of what it counts, so the table holds no IP address, email or user ID (PLATFORM-057). A check is one call that counts and decides in one statement, so a fork could move the counts to a shared store, such as Valkey, by changing the rate limiter alone ([architecture §1](../architecture.md#1-system-context)). The IP and user limits count in Postgres too, as every limit does, so each holds across the fleet whatever replica a request reaches (D20), at the cost of a write on every request, which `just load-test` measures (OPS-16). Counting them in each replica's memory instead would make each limit one per replica (SEC-13).

A request that finds its bucket full stops there with 429 `request.rate_limited`. A check that fails, as when the database doesn't answer, fails the request as an internal error: the request couldn't have been served without the database anyway. The pipeline keeps each bucket that counted a request, and writes on the response, whatever answered it, other than a 5xx, the headers of the one that decided it, with `Retry-After` on a 429 (PLATFORM-056). The rows of ended windows stay until the hourly sweep deletes them (PLATFORM-019); a check that finds one starts a new window, so they change no decision.

### The job queue

**Enqueueing.** A module declares each queued job in its `jobs.rs` (OPS-09), as a payload type that implements `Job`, which names its kind, `<module>.<name>`, or `platform.<name>` for a job that an area of `platform` declares, such as `platform.send_email`, its most attempts, 10 unless it names another number, and its time limit, 5 minutes unless it names another. `uow.enqueue(scope, &job)` inserts a `jobs` row in the unit of work's transaction (PLATFORM-012), with the payload as JSON, the scope, and the trace context of the current span (OBS-07). The scope comes from the proof the unit of work acts under, the only place one is built: `Authorized<P>` gives its workspace and member, `Principal` its user, and a `JobContext` the scope of the job that enqueues; scheduled maintenance has none, the scope that only the scheduler builds. A payload type changes only by adding fields that may be absent, as a migration expands a table, so a replica of the previous release still runs a job the new release enqueued; a change that can't be made that way is a new kind. A kind is retired, or renamed by becoming a new kind, only in the release after one that still runs it and enqueues no more of it (DATA-10): the dispatcher claims only the kinds its registry holds, so a waiting job of a kind that no replica holds never runs, never dead-letters, and holds up `platform.job_delay`.

**The dispatcher.** Every replica of `serve` runs one, so jobs spread over the replicas, and no setting turns them off (D13). It claims runnable jobs, waiting ones whose `run_at` has passed, of the kinds its registry holds (PLATFORM-016), with `FOR UPDATE SKIP LOCKED`, in one statement outside any transaction that gives each a lease of 60 seconds and a new claim ID, adds one to its attempts, and commits at once. It runs at most 4 jobs at a time, claims again as soon as one ends, and polls once a second while it finds none, so a job runs within about a second of its commit. It polls rather than waiting on the listener: a notification would save at most that second, and a replica would still poll for what it missed while its listener reconnected.

**A run.** A run happens outside any transaction (DATA-21). The handler receives the payload and a `JobContext`, the job's ID, attempt and scope, and opens a unit of work with `for_job` when it needs one. While it runs, the dispatcher renews its lease every 20 seconds, by its claim ID, so a replica that lost its claim renews nothing. A run that passes its kind's time limit is cancelled, and fails (PLATFORM-017). When a run ends, the dispatcher writes its outcome by its claim ID, so a stale run changes nothing:
- A success deletes the row (PLATFORM-014): nothing of a job outlives it but its telemetry.
- A failure that the handler calls permanent, or the failure of the last attempt, moves the job to the dead-letter state, with the failure's message.
- Any other failure keeps the failure's message and sets `run_at` to the next attempt. The `n`th retry waits a random time between half of and all of the lesser of 10 seconds times 2 to the power `n − 1`, and an hour, so retries spread out rather than arrive together (PLATFORM-014).

A replica that stops without releasing its claims leaves their leases to run out, and another replica then runs the jobs again: a job runs at least once, so every handler is idempotent, or its spec says why it can't be, as an email that may arrive twice (Sending email).

**Scope.** A job runs with the scope it was enqueued under, and its handler's queries filter by it, as a request's do by its proof (PLATFORM-013, DATA-16). It doesn't ask `AccessPolicy` again: a job carries out what an authorized operation committed, such as sending the email that the operation's change calls for, which a later change to its actor's role doesn't undo. A handler whose work depends on access as it stands when it runs reads that in its own unit of work.

**Periodic jobs.** The registry declares each with its name, its interval and its time limit, and `serve` inserts its `job_schedules` row, due at once, unless it exists. Every 10 seconds, each replica's scheduler claims the due rows of the names its registry holds with `FOR UPDATE SKIP LOCKED`, giving each a lease and a claim ID, runs the job, renews its lease as the dispatcher does, and then sets its next run one interval after this run began (PLATFORM-015). A failed run waits for its next interval, rather than retrying sooner. A row whose name no registry holds, left by a job that a release removed, is never claimed.

**Sweeps.** `platform` registers four periodic jobs, each hourly, each deleting in batches of at most 1,000 rows, in a transaction each (PLATFORM-019):
- `platform.expire_rate_limit_buckets`: the buckets whose window started more than a day ago, the longest window any limit allows, so none it deletes still counts.
- `platform.expire_idempotency_records`: the records older than 24 hours, which `claim` already treats as absent.
- `platform.expire_events`: the events older than 24 hours, the most a replay reaches (Events and the real-time hub).
- `platform.expire_dead_letters`: the dead letters older than `JOB_DEAD_LETTER_RETENTION_DAYS`.

Scheduled maintenance isn't audited (DATA-22).

**Shutdown.** On a shutdown signal, the dispatcher and the scheduler claim nothing more, while runs in flight go on as the HTTP server drains. Both share one deadline, the requests' own: the shutdown delay and the drain after the signal. At it, each run still going is cancelled, and its claim released, its attempt uncounted, so another replica runs it at once (PLATFORM-018).

**Alerts** (OBS-14). `JobsDelayed` pages when `platform.job_delay` stays above 10 minutes for 5: every email waits, and from step 5 every sign-up's code with them. `JobsDeadLettered`, a ticket, fires on any dead letter; its runbook lists the dead letters with their failures. A dead letter keeps its payload for investigating it (PLATFORM-014), which the runbook's query leaves out unless the investigation needs it, since it may hold personal data. Nothing retries a dead letter, since each job's remedy is the operation that caused it, done again, such as the request that sent an email. `PeriodicJobFailing`, a ticket, fires when a periodic job keeps failing, as its rule's summary and [its runbook](../operations/runbooks.md#periodicjobfailing) say.

### Sending email

**Settings.** `ServerConfig` holds the email settings as a `MailConfig`, which `serve` reads with its own, and checks as PLATFORM-024 says. `.env.example` gives each email setting's type, default and meaning (DOC-07). `EMAIL` has no default, so no deployment is without email by accident: a forgotten setting fails startup rather than leaving every password reset unanswered. In a deployment, `SMTP_PASSWORD` is read through `SMTP_PASSWORD_FILE`, as every secret is (SEC-01). A setting for timeouts, connection pooling or retries would be one nobody plausibly needs to change (D9), so those are constants: a connection or a reply times out after 10 seconds, and a send after 30.

**Emails.** A module declares the emails it sends in its `emails.rs` (ARCH-03), each as a type that holds its recipient and exactly the values its templates need, and renders each into an `Email`: its recipient, its subject, built in code from the same values, its plain-text part and its HTML part. Each kind of email has a plain-text template and an HTML template in the module's directory under `crates/app/templates/`, which `askama` compiles into the binary, checking each value a template names against the type that renders it. The HTML templates escape every value; the plain-text ones escape none, since a plain-text part isn't interpreted. The templates name the product, which `just rename` rewrites (ARCH-15). Emails are in English only, and carry no link: the API serves clients whose addresses it doesn't know, such as the desktop client. `Email`'s `Debug` shows none of its values, which are personal data (OBS-04).

**Sending.** The composition root builds one `Mail` from the settings, registers its job, and hands it to each module that sends email. `send(uow, scope, email)` enqueues a `platform.send_email` job in the unit of work, under the scope of its proof (PLATFORM-013), whose payload holds the email and a `Message-ID` of a new random UUID at `EMAIL_FROM`'s domain, never a secret; with email off, it does nothing (PLATFORM-022). The payload holds the email as rendered, so a job that one release enqueued sends the same email when a replica of another release runs it, whatever either's templates. `is_on` says whether email is on, which the capabilities endpoint reports. The job's time limit is 60 seconds, and its 12 attempts space their retries over about 2 to 3.5 hours (The job queue), so a mail server down for a few hours delays an email rather than losing it. Its handler sends the email, and needs no database access.

A job runs at least once, so an email may arrive twice: when a replica stops after the server accepted the email and before the job's success was written, its second run sends a copy. No protocol makes a send exactly once; the copy carries the same `Message-ID`, by which a receiving system recognizes it (PLATFORM-025, OPS-09).

**Transport.** With email on, `Mail` holds one `Transport`: `lettre`'s SMTP transport on Tokio, with a pool of connections, whose TLS is `rustls` with its `ring` provider (SEC-16), verifying the server's certificate against the system's certificates, as a verified database connection does (D38). Building it with TLS reads those certificates' files through `rustls-native-certs`, a blocking read, once, while `serve` starts and before it accepts a request (CODE-05).

Each send runs in a client span of its own, `smtp send`, with the server's address and port (OBS-06). Its failure holds the server's reply code, or the kind of the failure, such as a refused connection or a timeout, and never the reply's text, which may quote the recipient's address, so neither the logs nor a dead letter hold more than the job's payload already does (OBS-04, ERR-04). A reply from 500 to 599 is permanent (PLATFORM-021); any other failure is retried.

**Development.** `just services` starts Mailpit beside Postgres, with its SMTP server on `127.0.0.1:1025` and its web page on `127.0.0.1:8025`, where every email the API sent shows. `just setup` writes `.env` with email on and pointing at it, so nothing leaves the machine and nothing needs configuring (PLATFORM-023). The tests send to the same Mailpit, each test to addresses of its own, and read what arrived through its API. The tests of sending send an email of their own, through a route that only the tests serve, so that they don't depend on any module's emails (TEST-04).

### Events and the real-time hub

- Each module declares its events in its `events.rs`, each with its name (API-19), its scope, for a workspace event the permission it requires, and the type of its payload, a struct of IDs and non-personal fields that derives its schema, as it declares its audit actions. `publish_to_user` and `publish_to_workspace` take only the payload type the event declares. The module's `routes()` registers its events through `Routes::events`, which adds a frame's schema for each of them to the routes' document, among its components, marked with the extension `x-event`; `http::document` merges the modules' documents, and then builds `Frame` from every schema so marked, and names it in the stream's `x-itemSchema` ([realtime spec](realtime.md#the-event-catalog)).
- **Publishing.** `uow.publish_to_user` and `uow.publish_to_workspace` insert an `events` row in the unit of work's transaction: its scope (a user or a workspace), its name (API-19), the permission it requires, its payload of IDs, and its trace context (OBS-07). The commit of a unit of work that published takes a transaction-level advisory lock, gives its events the next positions of a sequence, with `created_at` the time it does, sends `pg_notify` on `events` with the last of them, and commits. Postgres releases the lock only once the commit is visible, so the positions follow the order of the commits, and every lower position has committed or rolled back. Postgres already makes the commits of transactions that notify one at a time: each holds a lock on its notification queue from just before its commit until after it, so that notifications arrive in commit order. The advisory lock lengthens that step by one statement, and serializes nothing that wasn't. The rows, with their foreign-key checks, are inserted before the lock is taken, so a unit of work that holds it waits on no row, and can't deadlock with one that holds a row it references. No trigger is involved (DATA-07).
- **The hub.** Each replica runs one hub, a task that owns the listener: it listens there on `events` and `access_changed`, and checks the connection for readiness (Readiness and shutdown). Postgres delivers the notifications in commit order. For a notification on `events`, the hub loads the events after its head, the last position it loaded, up to the position the notification names, 1,000 per query, so it loads each event once (PLATFORM-027), and no event passes a signal that committed before it. A notification whose position the head has passed loads nothing.
- **Delivery.** The hub keeps its streams by user and by workspace. A user event goes to its user's streams, and a workspace event to the streams whose memberships hold its permission in its workspace, and had committed when it did (SEC-19). Each stream has a queue of 256 frames. When one's queue is full, the hub closes it with `lagging`, rather than wait for its client or drop an event it would never get, and the client reconnects and replays (PLATFORM-032).
- **Signals.** An access change sends a signal on `access_changed` with `pg_notify` inside the change's transaction. The signal holds only IDs: the kind of change, the user, the session or the workspace, and the change's transaction, as `pg_current_xact_id()` gives it. It isn't stored (D35). `auth` sends one when a session ends, and `access` when it adds or removes a membership. For a session's end, the hub closes that session's streams; for a membership, each stream of its user whose memberships may not hold it (Subscribing), since closing one that holds it would only make its client reconnect for nothing. A membership's signal that names no transaction, as the previous release's replicas send theirs while a deploy runs both releases, closes every stream of its user, as that release's hub does, and the previous release's hub reads the transaction of a newer signal as a field it doesn't know, and ignores it (DATA-10). Each gets `stream.closed`, and its client reconnects, with a stream that reads the memberships as they then stand. The hub closes rather than re-filters, so every change of access takes the one path of a reconnect, whose replay sends what the closed stream didn't, and the client learns that its access changed.
- **Subscribing.** `Hub::subscribe` counts the stream against its user's limit on the replica (REALTIME-006), and registers it under its user, so a signal for the user from then on reaches it. It then takes a snapshot, `pg_current_snapshot()`, and after it reads the caller's `Memberships` through `AccessPolicy::memberships`, and the position of the event its `Last-Event-ID` names, which may be one the caller may not receive now, such as the last of a workspace they left, outside the hub's task, and hands the memberships and the snapshot to the hub, which keeps the stream under them and answers with its head; it holds no pooled connection while it waits, since the hub's own reads may wait for one. The memberships hold every membership change whose transaction the snapshot holds as completed, as `pg_visible_in_snapshot` reads it, so the hub closes the stream for a change whose transaction it doesn't hold, whether the signal reaches it before the memberships do or after (PLATFORM-031). A change that commits between the snapshot and the read closes the stream though its memberships hold it: a reconnect for nothing, never a stream that misses a change. The events up to that head come from the replay, and those after it from the hub, so the stream misses none and receives none twice:
  - With a `Last-Event-ID` that names an event the API holds, the replay reads the events after its position, up to the head, that the caller may receive: their own, and those of each workspace in their memberships whose permission their role there holds, committed after their membership (SEC-19). The query filters by the caller's ID and their memberships' workspaces, and by position, through indexes on `(user_id, position)` and `(workspace_id, position)`. It reads at most 1,001 rows: a 1,001st means more than 1,000 wait, and the stream sends none of them, but says it truncated (REALTIME-004).
  - Without one, or after a truncated replay, the stream starts at the head, delivers what commits after it, and names where a reconnect resumes it: the newest event at or before the head that its caller may receive, or the nil UUID when there is none (REALTIME-001).
  - A stream that resumes from a position past the hub's head, after a reconnect from a replica whose hub was ahead, skips what it already received.
- **The re-check.** Every `STREAM_RECHECK_SECONDS`, the hub asks `SessionVerifier::lasting` which of its streams' sessions still last, and `AccessPolicy::memberships` for its streams' users, 1,000 of each per query, and closes the streams whose session ended or whose memberships changed (SEC-06). A session lasts while it can still be refreshed, so an access token's expiry doesn't close a stream.
- **A lost connection.** When a check fails or the connection breaks, the hub connects again and listens again, at once and then at every check until it can. The notifications sent meanwhile are lost, and with them the signals, which no one can place among the events, so once it listens again the hub closes every stream with `interrupted`; each client reconnects and replays from its last event with its memberships as they then stand (PLATFORM-033). The hub's head then moves to the log's, since no stream is left to deliver the events in between to. A load or a re-check that fails is owed, and tried again at every check, while readiness follows the connection alone (PLATFORM-061). A load never passes the last position that a notification the hub has handled named, so no event passes a signal that still waits behind it; one that a later notification makes covers what a failed one left, since it loads from the head.
- **Shutdown.** When the shutdown delay ends, `serve` stops accepting connections and calls `Readiness::stop`, at which the hub closes every stream with `shutdown`, so the drain doesn't wait for them, and their clients reconnect to a replica that serves (OPS-06, PLATFORM-062).
- **A member's events.** A workspace event reaches a member only if their membership had committed when the event did, in the replay and live alike (SEC-19). The membership's row keeps the ID of the transaction that added it, `pg_current_xact_id()`, and the event's commit keeps `pg_current_snapshot()`, the transactions that had committed by then; the event reaches the member when the first is among the second, as `pg_visible_in_snapshot` reads it, and the hub reads it the same way. The snapshot is taken in a statement after the advisory lock's, and the commit of an operation that adds a membership takes the same lock (`order_with_events`), so no membership commits between an event's snapshot and its commit. The membership's time of joining, its transaction's start, can't decide it: an event that committed while the joining transaction ran would pass.
- **Capacity.** One task on one connection is enough: the hub delivers events faster than the API publishes them.
  With 1,000 streams open on a replica with the reference deployment's limits, its hub delivered every event that a second replica published, to every stream allowed it, with its lag far within the latency objective, at every rate the publishing requests reached before they hit their own limit: `just load-test streams` measures it before each release, and the release's notes hold the numbers (OPS-16). <!-- part: invitations -->
- **Retention.** Events are kept for 24 hours, as long as a client away longer would need a replay larger than its cap, which the hourly sweep deletes in batches (PLATFORM-019). A `Last-Event-ID` older than that names no event, and its replay is truncated (REALTIME-004).
- **Delivery's telemetry.** The hub delivers each event in a span of its own, linked to the trace context stored with it (OBS-07), and records its lag from the event's `created_at` (PLATFORM-034). Its metrics carry the database's name as `db.namespace`, as `platform.database_reachable` does, so the hubs of the tests, which share a process, record apart. `EventsDelayed`, a ticket, fires when the 99th percentile of the lag stays above 5 seconds for 10 minutes; a hub that hears nothing records no lag, and is `DatabaseUnreachable`'s (OBS-14). A hub that hears but can't load records no lag either, so `platform.events_unloaded` records what it owes, from its head and the last position a handled notification named, when the hub starts, after each load, whether it succeeded or not, and after it reconnects (PLATFORM-035); `EventsStalled`, a ticket, fires when a hub has owed events for 5 minutes, every evaluation finding it above 0 (OBS-14).

### Idempotency

The key's record is written by the operation's own unit of work, so it exists exactly when the operation committed, and no other state needs cleaning up:
1. `Idempotent<T>` reads the header, a string of structured fields as draft-ietf-httpapi-idempotency-key-header-08 defines it (RFC 9651), and refuses one that isn't (PLATFORM-037). The fingerprint is a SHA-256 digest of the method, the path, the query and, where the body has one, the header that names it, each after its length, so no two requests' parts run together the same, then the digest of the body it read, whose length is fixed (API-12).
   An upload's body is named by its `Content-Disposition`. <!-- part: files -->
2. The service opens its unit of work, or a workspace route's `Authorize::open` opens it with the caller's authorization (PLATFORM-009), and its first statement after that authorization is `claim`, with the caller's user ID, the key and the fingerprint. It inserts the record, which the unit of work completes at its commit. A committed record of the same user and key decides instead: its result when the fingerprint matches, which the service returns as its own, so the route maps it as it maps a fresh one, or 422 otherwise.
3. A record that another unit of work has inserted and not yet committed makes the insert wait on that transaction. `claim` waits at most one second, under a `lock_timeout` of its own, which bounds that wait as it bounds a lock's, and then answers 409, so a retry of a request still running is refused rather than held.
4. `commit_with(result)` writes the result into the record and commits, in the same transaction as the operation's writes. A unit of work that claimed a key and commits without its result fails as an internal error, so no keyed operation commits without one. The result is JSON that the next release reads back while the record lasts, so its type grows only by fields that may be absent (DATA-10).
5. A unit of work that rolls back, whether it failed or the process ended, takes its record with it, so a retry runs again.
6. A record older than 24 hours counts as absent: `claim` replaces it. The hourly sweep deletes such records (PLATFORM-019).

A key is compared exactly as sent, once the structured field's own syntax is read, its quotes, its escapes and the spaces around it, with no trimming inside it and no folding of case (D12). It is the caller's own, so a retry from another session of the same user, after signing in again, still finds its record.

### Preconditions

An editable resource's `ETag` is its row's `version`, which the shared trigger raises on every update (DATA-02), as a quoted decimal: `"3"`, which a route's `ResourceResponse` carries once `tagged` with it. `IfMatch` reads every `If-Match` header of the request, as RFC 9110 defines it: `*`, which any version matches, so the update applies as without the header, or a list of entity tags, each of which names the version whose `ETag` it is, character for character, as RFC 9110's strong comparison matches. A weak tag, which that comparison never matches, and anything the API didn't send, such as `"03"`, name none, so the update fails its precondition. A module's update keeps its statement to the versions named (DATA-18); zero rows updated is `request.precondition_failed`, which the module returns, and its unit of work rolls back. The code is listed on every operation that documents an `If-Match` header, as an idempotency key's codes are on every operation that documents its header (ERR-13, D87).

### Lists

`Page` reads `limit` and `cursor` (PLATFORM-046), both before it refuses either, so one response names both. A cursor is the base64url encoding of the first bytes of its route's SHA-256 digest, and the last item's sort key and ID, so a page is the next rows after that key in the route's order, whatever was added since (API-06). A cursor that doesn't decode into the route's key is refused, as `/cursor` with the code `invalid`. `Search` reads `search` (PLATFORM-047), and a repository matches it with `ILIKE`, its pattern escaped, under Postgres's built-in collation `pg_unicode_fast`, whose case mapping is Unicode's in every database, where the database's own locale may fold only the letters `A` to `Z`. Every list is first narrowed to one workspace or one user, so the match reads only that tenant's rows, and needs no index of its own until a load test shows one (OPS-16). The values that a list's route refuses are reported together, once its route group has found no name its documentation doesn't list (PLATFORM-045).

A list whose order and whose searched fields belong to different modules, such as members, whose order is their memberships' and whose names are their accounts', takes the same steps everywhere (ARCH-06). Without a search, the module that owns the order pages its rows through its index (DATA-17), and the other module gives the page's names in one batch. With one, the module that owns the fields first returns which of the tenant's IDs match, and the module that owns the order pages among those.

### Request pipeline

The order of the middleware stack is in [architecture.md §6](../architecture.md#6-request-lifecycle). The health probes are answered before the stack (OPS-05), and the security headers (SEC-12) wrap both.

**Routes and their documentation.** A module's `routes()` returns `Routes`, which only the builders of API-14 add to, and which takes the module's state, such as its service, only in the composition root, so the routes document themselves without a database. A builder takes a route's documentation with its method router, as utoipa-axum's `routes!` makes both from the handler's `#[utoipa::path]`, and the errors of the module that the route can answer. A route serves `HEAD` wherever it serves `GET`, as HTTP asks. To each operation, the builder adds:
- its access level, as the extension `x-access`
- the problems the pipeline can answer on it, and their codes and titles (ERR-13). Every operation lists `request.invalid_query`, `request.payload_too_large`, `request.rate_limited`, whose 429 carries `Retry-After`, `request.timed_out` and `request.overloaded`, whose 503 carries `Retry-After`, and `request.internal_error`; and `request.unavailable`, a 503 with `Retry-After` too, which only the proxy in front of the replicas answers, while none of them can (OPS-05). One whose method isn't safe also lists `request.origin_not_allowed` (PLATFORM-059), one that authenticates its caller `request.unauthenticated` and `request.access_token_expired` (AUTH-009), and one that takes a body `request.invalid_body` and `request.invalid_fields` (PLATFORM-049, PLATFORM-051).
  One that takes a signed URL also lists `request.signed_url_expired` (PLATFORM-080). <!-- part: files -->
- on a download route, which `workspace_download`, `user_download` or `public_download` adds, what PLATFORM-081 serves beside the handler's 200: a 206, with the 200's content and `Content-Range`, and a 304, each with `ETag`, `Accept-Ranges` on the two that carry bytes, and `Cache-Control` on a public download's, and the request headers `Range`, `If-Range` and `If-None-Match` that bring them; and on the first two, the three query parameters of a signed URL (PLATFORM-080) <!-- part: files -->
- the module's errors that the route can answer, which the builder documents the same way
- `RateLimit` and `RateLimit-Policy` on each of its responses but the 5xx, which a request that load shedding refused, or that panicked, never carries (PLATFORM-056)

clippy bans the routing methods of axum and utoipa-axum outside `platform::http`, so a route reaches the router only through a builder, which registers it at the paths its documentation names. A test sends every documented path each method OpenAPI can document that the path's documentation leaves out, and a method no route serves, and expects each to answer 405 with an `Allow` that lists exactly the documented methods. A method router whose fallback serves one of those methods fails it, so a route serves none of the methods OpenAPI can document that its documentation leaves out, however its method router was built (API-14, API-17). `http::app` mounts every module's routes, the fallbacks and the stack. `Routes::openapi` returns the routes' OpenAPI document, which covers the `/v1` routes and holds the router's own problems among its components: `NotFound`, and `MethodNotAllowed` with `Allow`. The binary's `openapi` subcommand writes it to `openapi.json`.

**Checking the document.** A response object in the document stays open to properties it doesn't list, because clients ignore the fields they don't recognize (API-05) and `/v1` may add response fields (API-18). The integration tests send plain HTTP requests to the API in process, and the test support checks every response against the document of the routes that answered it, but for the body of a `text/event-stream`, which the tests of the stream read frame by frame, checking each frame against the entry of the event catalog that its `event` names (REALTIME-008), with every object schema among the document's components closed, except the parts of an `allOf`, which each list only some of the properties of the whole. A field, status or content type the document doesn't list fails the test, and so does a header it lists that the response lacks (API-17). A `HEAD` response is checked against its `GET`, the only operation the document lists for both, since HTTP defines `HEAD` by `GET`. A request that no operation documents must get `NotFound` or `MethodNotAllowed`, except at the health probes and the API reference, which the document leaves out and the check skips (OPS-05, PLATFORM-052), and a CORS preflight, which the CORS layer answers before any route (PLATFORM-058). The tests of `serve`'s shutdown and of the binary's log lines read their responses over a connection of their own, which the check doesn't see. A client generated from the document couldn't send the malformed requests that the pipeline's behaviors need.

**Errors.** `ErrorCode` gives an error its code, its title and its category (ERR-02, ERR-03). A handler returns `Result<T, Problem<E>>`, and `?` turns any `E: ErrorCode` into a `Problem<E>`, whose response is the problem of API-07, with the trace ID of the request's span. A 503 `Problem` carries `Retry-After`, the seconds its error's `retry_after_seconds` gives, 1 unless the error names another, as the document lists for every 503. A 5xx `Problem` also carries its cause chain in a response extension, which the request log writes and removes (ERR-10). The fallbacks answer a path that doesn't exist with 404 `request.not_found`, and a method the path doesn't serve with 405 `request.method_not_allowed`, to which axum adds `Allow` (PLATFORM-043).

**Trace context.** The tracer is OpenTelemetry's SDK, which exports what [Telemetry export](#telemetry-export) says. It samples every request, whatever the flags of an inbound `traceparent` say, so every trace ID a response carries can lead to a trace (OBS-08). The outermost layer of the stack opens the request's server span, as the child of a valid inbound `traceparent`, and writes `server-timing: trace;desc=<traceparent>` with the span's own trace context, because the tracing libraries don't write that header (PLATFORM-041). A 5xx response sets the span's status to error and its `error.type` to the problem's code, or to `_OTHER` when the request log knows no error for it, and a 4xx leaves both unset, as OpenTelemetry's conventions for HTTP servers ask. A span is named after its method and route, such as `GET /v1/capabilities`, and a span whose method is `_OTHER` after the protocol instead, such as `HTTP /v1/capabilities`. The span, the request's log line and its metric give the method as one of the methods HTTP's specifications define (RFC 9110's, `PATCH` and `QUERY`), or as `_OTHER`, so a client can't add values without bound (PLATFORM-067, OBS-11). The API serves no other method, so no method it serves becomes `_OTHER`.

**Limits.** Each route group's timeout and body limit are constants (OPS-07, API-08). The `public`, `user` and `workspace` groups share a timeout of 10 seconds, twice the 5 seconds an operation waits for a pooled connection, and a body limit of 64 KiB, far above the largest JSON body the first slice accepts. A module spec may set others for its routes. The body limit refuses a declared `Content-Length` over it before the body is read, and stops any other body at the limit while it is read; `Json<T>` turns that into the 413 problem (PLATFORM-050).
An upload route, which `Routes::workspace_upload` or `Routes::user_upload` adds, has a timeout of 60 seconds, which the files spec's [Scanning](files.md#scanning) shares out between the body, its scan and its write, and no body limit of its own: its handler reads the body through `Upload` once it has refused what it refuses without the bytes, such as a caller who may not upload (PLATFORM-073), or who isn't authenticated, with the limit its module's setting gives, and `Upload` refuses a body over it as the group's limit would. A replica reads at most 4 uploads' bodies at once, each in a turn that it holds until the handler drops the bytes, so the uploads a replica holds in memory take at most 4 times the largest limit, whatever the concurrency limit lets in (PLATFORM-074). <!-- part: files -->
The concurrency limit is a setting, because a deployment's capacity decides it (OPS-02).

**Query parameters.** A route accepts the query parameters its documentation lists, which come from the type its handler parses them into. That type declares `#[into_params(parameter_in = Query)]`, without which utoipa leaves its fields out of the query, and each of its fields is an `Option<String>`, which the route reads into domain types, so every value it refuses is named in one response (`Query<T>`). The builder answers any other name with 400 `request.invalid_query`, before the handler runs, so a route without query parameters refuses any query string (PLATFORM-045).

**Request bodies.** `Json<T>` reads a JSON body. It requires `Content-Type: application/json`, with or without a `charset` of `utf-8`, reads at most the route group's body limit (PLATFORM-050), and parses the body into `T`, whose `#[serde(deny_unknown_fields)]` refuses a field it doesn't declare (API-08). Each of those failures answers 400 `request.invalid_body`, with the JSON Pointer of the field the parser names in `errors`, when it names one (PLATFORM-049). `MergePatch<T>` reads a `PATCH` route's body in the same way, but requires `Content-Type: application/merge-patch+json`, the media type of a JSON Merge Patch, which `check-openapi` requires a `PATCH` to document (API-03); `T` holds the members a patch may change, and may require one while it is the resource's only editable member (D88). A request type then converts into domain types through `TryFrom`, which tries every field and collects each refusal in `FieldErrors`, so one response names them all (API-10): 400 `request.invalid_fields`, whose `errors` give each field's JSON Pointer, the reason's code, and a message (PLATFORM-051).

**Browsers.** `CORS_ALLOWED_ORIGINS` lists the origins of web clients, such as `https://app.example.com`. Empty, the default, the API serves only clients that set their own headers, and sends no CORS header. With origins listed, the CORS layer, right inside the layer that reads the client and outside the concurrency limit, so that a browser can read even a 503 or a 429, answers a preflight from a listed origin itself, and adds to every response to one `Access-Control-Allow-Origin` with that origin, `Access-Control-Allow-Credentials: true` and `Vary: Origin` (PLATFORM-058). A preflight allows the methods the API serves, and the request headers `Authorization`, `Content-Type`, `Idempotency-Key`, `If-Match`, `Last-Event-ID` and `traceparent`; a response exposes `Location`, `ETag`, `RateLimit`, `RateLimit-Policy`, `Retry-After` and `server-timing`. Startup refuses `*`, a value that isn't an origin, and an origin that isn't `https`, except one whose host is a loopback address in development.

The cross-site check runs right inside the IP limit, so its refusals count and carry the rate-limit headers: a request whose method isn't safe answers 403 `request.origin_not_allowed` when its `Origin` isn't listed (PLATFORM-059). A browser sends `Origin` with every such request, and only a browser sends it, so the check refuses no client that sets its own headers. When a cookie authenticates such a request, `Principal` and the refresh route also refuse one that carries no `Origin`, so a request the cookie authenticates always comes from a listed origin. With `SameSite=Strict`, no other site's page can make a browser send the cookies at all; the check also covers a page of another origin on the same site.

**The API reference.** In development, `http::app` mounts two routes beside the documented ones, inside the stack, so their responses carry their trace context and the IP limit counts them, each in a route group, as a builder's route is, so its group's timeout and body limit apply, and it refuses any query parameter (OPS-07, API-09), but outside the builders of API-14, so the document leaves them out: `/docs/openapi.json`, which answers the document that the composition root built at startup, and `/docs`, which answers a page that loads Swagger UI from a content delivery network, pinned by its version and its Subresource Integrity hash, and shows that document. The page shows what the running code serves, which `just dev` restarts on every change, with no `just openapi` first. The document names no server, so the page sends its requests to the origin that served it, the API's own: they need no CORS, a sign-in through the page sets the session's cookies, which every later request carries (AUTH-015), and they pass the cross-site check, since `.env.example` lists the API's development origins in `CORS_ALLOWED_ORIGINS` (PLATFORM-059). The pipeline holds the document only when `ENVIRONMENT` is `development`, so no other environment has the routes, the page or its third-party script (PLATFORM-052).

**Panics.** A panic hook replaces the default one, which would write plain text to stderr. It writes one `ERROR` line with the panic's message and location, inside the span the panic happened in, and counts the panic in `platform.panics`, on whatever thread it happened (ERR-12). Every subcommand that logs installs the hook. The catch layer answers the panic with the 500 problem, and marks the response so that the request log writes no `ERROR` line of its own, and the panic is logged once (ERR-10).

**Ignored errors.** `errors::ignore` writes one `WARN` line with a `snake_case` name for the failure as `error.type`, and its cause chain, and counts it in `platform.errors_ignored` with the same `error.type` (ERR-11). The pipeline ignores a failure to set a span's inbound parent, which leaves the request in a trace of its own, and a failure to write `server-timing`, which can't happen while the header's value holds only hexadecimal digits and dashes. `Telemetry::finish` ignores a failure to write out what one of the providers holds (PLATFORM-068). In development, the composition root ignores a failure to write the OpenAPI document as JSON for the API reference, which then isn't served (PLATFORM-052).

### Logging

The logging setup writes one line per event to stdout: JSON in production, and text elsewhere (OBS-01). A JSON line holds `timestamp`, `level`, `message`, the event's fields, `service.name`, `service.version` and `deployment.environment.name`, and, inside a span, `trace_id` and `span_id` (OBS-02). `service.name` is the binary's name, so `just rename` renames it with the binary (ARCH-15). `LOG_LEVEL` is never coarser than `INFO`, because every request's completion line is written at `INFO` (PLATFORM-044).

A dedicated thread writes the lines, fed by a queue of 128,000 lines, so an event doesn't wait for stdout. When the queue is full, the event waits for room instead of being dropped (OBS-08): that wait is the one blocking call the logging setup makes on the async runtime (CODE-05). `main` writes out the queue before the process exits, waiting at most about a second for the logging thread, as `tracing-appender` does: a line it hasn't written by then is lost.

With telemetry export on, the same events also become OpenTelemetry log records: the bridge takes the events the lines take, with the same fields and severity, and the trace context of the span each was written in (PLATFORM-066). The records wait in a queue of their own, which drops a record that arrives while it is full (Telemetry export), so stdout drops no line while the process runs, and the logs store holds every record the API exported.

### Telemetry export

With `OTEL_EXPORTER_OTLP_ENDPOINT` set, every subcommand that logs exports its spans, its log records and its metrics over OTLP/HTTP with protobuf bodies, to `<endpoint>/v1/traces`, `/v1/logs` and `/v1/metrics`, the paths the protocol's specification defines (PLATFORM-066). Without it, nothing is exported, and the logs still go to stdout. [observability.md](../operations/observability.md) describes the collector that receives the telemetry.
- **Resource.** Every span, log record and metric carries `service.name`, `service.version`, `deployment.environment.name`, and `service.instance.id`: a version 4 UUID drawn from the operating system's random source when the process starts, so instances running side by side stay apart. The resource holds nothing else.
- **Spans.** A span's attributes are its own fields, all from the list of names (OBS-05): the bridge from `tracing` adds no source location, thread, target, level or timings. Events stay out of spans, since each event is a log record that its trace context links to its span. A number is recorded as a signed integer, because the bridge writes an unsigned one as text, and the collector's sampling compares `http.response.status_code` as a number (OBS-08).
- **Transport.** The three exporters share one blocking HTTP client, which runs on a thread of its own, so no export waits on the async runtime or needs it to run (CODE-05). An `https` endpoint is verified against the operating system's certificate store through rustls with its ring provider, as a verified database connection is (D38, SEC-16). SEC-10 lets the telemetry adapter use its library's client.
- **Batching.** A thread of the SDK exports the queued spans, and another the queued log records, each at least once a second and in batches of up to 512. Each queue holds 2,048 items, and an item that arrives while its queue is full is dropped. At a replica's capacity, the queues keep up: the load test counts as many spans the collector accepted as requests the replica served (OPS-16). A third thread exports the metrics every 15 seconds. An export that hasn't finished within 10 seconds fails.
- **Failures.** An exporter that can't be built fails startup (OBS-10), in the format of OPS-03, since logging doesn't exist yet. An export that fails at runtime is counted, and the process goes on (OBS-10). A wrapper around each exporter counts what it exported in `otel.sdk.exporter.span.exported`, `otel.sdk.exporter.log.exported` and `otel.sdk.exporter.metric_data_point.exported`, as the conventions define them: a failed export's items carry `error.type` `export_failed`, and exported items carry none. The exporter reports every failure the same way, a timeout included.
- **One source of settings.** The SDK and the exporter read `OTEL_*` variables of their own, such as headers, timeouts, queue sizes, the sampler and resource attributes, which would change what the API exports without `platform::config` knowing. `platform::config` reads the endpoint itself, and every subcommand that logs refuses to start while one of the others that `.env.example` lists is set (PLATFORM-065), as it does for libpq's.
- **Shutdown.** `Telemetry::finish`, which `main` calls last, shuts down the tracer, then the logger, then the meter, each after it writes out what it holds, so the last metrics count the exports that failed just before them (PLATFORM-068). The tracer and the logger each have 2 seconds, and the meter takes up to the 5 seconds its SDK allows itself, so writing out telemetry takes at most 9 seconds. Then the log lines are written out (OPS-06).

### Metrics

`platform::telemetry::metrics` holds the declaration types: `Counter`, `Histogram` and `Gauge` (OBS-11). A metric is a `static` that one of their `const fn new` builds from its name, unit, description and label names, and for a histogram its bucket boundaries. The first recording after telemetry is set up creates the instrument from the process's meter provider, and a recording before then is lost: an instrument created earlier would stay tied to no provider for the life of the process, so the metrics a test reads would depend on the order the tests run in (TEST-06). The binary sets telemetry up before any code records. A recording passes an array of label values as long as the declaration's label names, in their order, so a recording can't add a label. A value of `None` leaves its label out of the data point, as the conventions ask of `error.type` on a success. clippy bans getting an OpenTelemetry meter outside that module, and no metric can be created without one.

A name that a semantic convention defines is declared through `convention`, as the telemetry names are (OBS-05). The metric names come from `opentelemetry-semantic-conventions`' `metric` module, which holds the conventions' metric names.

`check-metrics` reads every declaration in the workspace. It fails on an own name that isn't `<module>.<name>` for the module that declares it, and on a label name that isn't one of the list's constants. `just metrics` writes the catalog, [metrics.md](../operations/metrics.md), from the declarations, and `check-metrics` fails while the committed catalog differs from it (OBS-12).

The metrics `platform` records are in the catalog, each with the file that declares it and what it measures, from its declaration. Two of them leave something out:
- `http.server.request.duration`, which the request log records for every request it logs, with the boundaries the conventions advise (PLATFORM-067), leaves out `url.scheme`, which the conventions require: the API receives every request over plain HTTP, behind the proxy that ends TLS, so the label would hold one value.
- `process.memory.usage` reads the kernel's report in `/proc/self/status` every 15 seconds, so it is recorded on Linux only (PLATFORM-070).

### Readiness and shutdown

- The instance keeps the listener, its one connection to the database outside the pool, on which the hub listens, and checks it every 5 seconds. `serve` opens it once connected to the database, and fails startup if it can't listen there. A check fails after 2 seconds without an answer, and a failed check connects again at once, and listens again. The readiness probe reads the last result, so it never waits for the database or for a pooled connection (PLATFORM-061), and a replica whose hub can't hear what commits leaves the rotation (OPS-05).
- `ShutdownSignals` installs the handlers for SIGTERM and SIGINT, or Ctrl+C on Windows, before `serve` connects to the database. A failure to install them fails startup (OPS-03, OPS-06).
- On a signal, `serve` turns readiness to `draining`, waits the shutdown delay so the load balancer stops sending requests, stops accepting connections and has the hub close the open streams, and waits for the requests in flight until the drain deadline. It then returns, and a request still running ends with the process. The jobs' runs drain beside the requests, until the same deadline (PLATFORM-018). The delay and the deadline are settings, because a deployment's health-check interval and grace period decide them (OPS-02). The deadline's default, 60 seconds, is no shorter than the longest timeout of a route, so a deploy cuts short no request that its route would let finish (OPS-06, D108).
  The longest is an upload's (PLATFORM-074). <!-- part: files -->
  Then `main` writes out the logs.
- A failed or recovered check changes readiness before its log line is written, so whoever reads the line finds readiness changed.
- The `health` subcommand is the image's health check (OPS-13). It reads `LISTEN_ADDR` and no other setting, runs no async runtime, and writes nothing but its failure, so a check every few seconds adds nothing to the logs. `lifecycle::probe` connects over plain TCP and writes the request itself: the instance answers on its own address, which needs neither of the outbound clients (SEC-10). It waits 3 seconds for the connection and for each read of the answer, longer than the 2 seconds Windows takes to report a refused connection, and reads at most 4 KiB. A failure of the probe is written in the format of OPS-03, with `startup.area` `health`, because a one-shot subcommand's whole run is its startup; a missing or invalid `LISTEN_ADDR` fails as any setting does, with `config` (PLATFORM-064).

### Clock

`Clock` is a trait with two implementations (ARCH-13): the system clock, and the test clock, which only the `test-support` feature compiles. `now` reads the time, and `sleep` waits. A test clock's `sleep` completes when the test advances the clock past its deadline (TEST-06). Every wait in the workspace but the tests' watch goes through it (CODE-06), the readiness checks and the shutdown delay included.

### Workers

`main.rs` makes one `Workers` per process. `serve` and `seed` hand it to the composition root among the process's resources, which hands it to each service with CPU-heavy work, such as `auth` for its passwords' hashes, and `bootstrap` computes the roles' verifiers through it. A turn is a permit of a semaphore with one per processor, as the standard library's `available_parallelism` counts them, a container's CPU quota included. The semaphore hands its permits out in the order they were asked for. `run` waits for one inside the work's span, so a trace shows the wait, then moves the work and the permit to a blocking thread together, so the permit comes back when the work ends rather than when its caller stops waiting.

A turn per processor bounds the memory: a password's hash holds 19 MiB while it runs (AUTH-014), and more hashes at once than processors would end no sooner, since each takes a processor whole. The wait has no limit of its own: the route's timeout ends it (PLATFORM-042), and the concurrency limit bounds how many requests wait (PLATFORM-039).

### Storage

`Storage` is `object_store`'s client of an S3-compatible bucket, signing with its `ring` feature, which sends through a `reqwest` client of `platform`'s own, whose TLS is rustls with its ring provider, verifying the bucket's certificate against the system's certificates, as a verified database connection does, and against those of `S3_CA_PATH`, for a bucket that a private authority's certificate serves (SEC-16, D38): the library's `aws` feature, which would build its own, brings aws-lc-rs, which SEC-16 bans. Building the client reads those certificates' files through `rustls-native-certs` and `rustls-pki-types`, a blocking read, once, while `serve` composes the API and before it accepts a request (CODE-05). The client's only timeout is the connection's, 2 seconds; how long the bucket has to answer is measured on the clock it is given (CODE-06), each call's wait covering the library's retries, of which it makes 2 within 2 seconds of the first attempt, for the failures that come at once: 4 seconds for a read, a deletion and each page of a listing, so a download answers within its route's 10 seconds, and 15 for a write, which the upload route's 60 seconds leave once a body has come and the scanner has scanned it ([files spec](files.md#scanning)), so a bucket takes a write of the largest `FILE_MAX_BYTES`, 20 MiB, only over about 11 megabits a second. The bucket has the same 4 seconds for each next chunk of an object's bytes, counted from when the download asks for it, so a client that reads slowly never cuts its download short, while a bucket that stops sending ends it. A read of a range asks the bucket for those bytes alone, with S3's `Range`, and the object's size comes from the bucket's answer, whose `Content-Range` gives it, so a download checks a ranged read's object against its row as it does a whole one ([files spec](files.md#downloading)). The client reaches the bucket only when asked, so `serve` starts while the bucket doesn't answer. `StorageError` tells an object that isn't there; a bucket that didn't answer, which is a wait that ran out, the library's failure of a connection, a request, a timeout or an interruption, or an answer of 5xx or 429, which say it can't serve now; and every other failure, a refusal or an answer the client couldn't read. Its cause, for the logs, is written by the client from the call and the status or the kind of failure, never from the library's text, which names the request's URL and with it the key (ERR-04). The library keeps a status in a type it doesn't export, so the client reads it from the error's text, as `status code:` and three digits, which the tests of FILES-012 pin. Each call runs in a client span of its own, named by its S3 operation, such as `S3 GetObject`, with the bucket's address and port and no key (OBS-06), and counts in `platform.storage_requests` by how it ended: `ok`, `not_found`, `failed` or `unavailable`, which the alert StorageUnreachable reads (OBS-14); a read whose stream of bytes then fails, or that the bucket stops sending, counts again, by that failure. The library signs each write over a SHA-256 digest of its bytes, which it computes on the async runtime as the write starts, a blocking call that CODE-05 allows here: about 7 milliseconds for 10 MiB, and 14 for 20 MiB, the largest `FILE_MAX_BYTES`, on a processor with SHA extensions. Writes signed as `UNSIGNED-PAYLOAD`, over HTTPS, would need no digest, but whether Backblaze B2 accepts them is unproven (Open design questions). Tagging is off, since some providers refuse its header, as Backblaze B2 does, and nothing uses it; a deletion is S3's `DeleteObject`, not the bulk `DeleteObjects` the library sends by default, which some providers lack; and no write is conditional, since B2 refuses `If-None-Match` on a write, and each object's key is new.

### Scanner

`Scanner` is a client of ClamAV's daemon, clamd, of `platform`'s own, over a TCP connection of tokio's, since clamd's protocol is a few lines and its crates add nothing a client needs: it sends `zINSTREAM`, the bytes in chunks of at most 1 MiB, each after its length as 4 bytes in network order, and a chunk of no bytes, then reads clamd's answer up to its terminating zero byte, at most 4 KiB. clamd answers `stream: OK`, `stream: <signature> FOUND`, or a line that ends in `ERROR`, such as `INSTREAM size limit exceeded. ERROR` for a stream longer than its `StreamMaxLength`, which every environment's configuration sets to 20 MiB, the largest `FILE_MAX_BYTES` (D107). clamd speaks no TLS, so it runs on the deployment's private network, and nowhere a connection would leave the server (OPS-17).

Each scan opens a connection of its own, which clamd closes after its answer, so no connection waits between uploads, and clamd's queue bounds how many it scans at once. The connection has 2 seconds to open, and the whole scan 30 seconds from its start, each measured on the clock the client is given (CODE-06): enough for a scan of the largest `FILE_MAX_BYTES` of the slowest kind ([files spec](files.md#scanning)). The client reaches clamd only when asked, so `serve` starts while the scanner doesn't answer, and readiness doesn't wait on it, as it doesn't on the bucket: replicas that couldn't reach it would all leave the load balancer, and every route would fail with them, rather than only uploads.

Each scan runs in a client span of its own, named `clamd INSTREAM`, with the scanner's address and port, and counts in `platform.scans`, which the alert ScannerUnreachable reads (OBS-14), once it ends: a scan that its request's timeout drops first has no outcome, and counts in none. `ScanError`'s cause, for the logs, is written by the client from what failed, and names neither the bytes nor the signature: the signature goes to the caller, in `Found`, and clamd's own log writes it.

### Telemetry names

The list in `platform::telemetry` holds one constant per name (OBS-05). A name that a semantic convention defines is declared as `convention("http.route", otel::HTTP_ROUTE)`, a `const fn` that fails compilation when the two names differ. The conventions' constants come from `opentelemetry-semantic-conventions` 0.33.1, which publishes semantic conventions 1.42.0, with its `semconv_experimental` feature for names still in development. A deprecated constant fails clippy.

The list holds the names from the conventions; `trace_id` and `span_id`, the top-level fields of JSON logs (OBS-05), which the conventions' crate has no constant for, so the list declares them without `convention`; the bridge's fields, `otel.name`, `otel.kind` and `otel.status_code`, which `tracing-opentelemetry` reads to name a span and set its kind and status, and which no JSON log line carries; and the own names. Two of them a span carries only once a proof exists: `user.id`, once `Principal` has verified its caller, and `workspace.id`, once `Authorized<P>` has proven its caller a member (OBS-09). A name joins the list with the first code that writes it.

`check-instrument` reads the list's names, then every `tracing` event and span macro, every `#[instrument(fields(…))]` and every `.record("…")`, including calls nested inside other macros. It fails on:
- a name the list doesn't hold, or a `{ CONST }` name that isn't one of the list's constants
- a `record` name that is neither a listed name nor one of the list's constants
- a message that isn't constant (OBS-01)
- an `#[instrument]` without `skip_all` (OBS-04)
