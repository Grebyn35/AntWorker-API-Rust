# Spec: `files`

## Purpose

`files` keeps the files that users upload: a workspace's files, which its members share, and a user's own files, which only they reach. It keeps each file's bytes in object storage, and what the API knows of it in Postgres. It accepts only the types it can check, scans each upload for malware before storing it, and serves each file so that it can't run in a browser. A file is private, or public, which anyone may download without signing in. A private file's download also takes a signed URL, for a client that can't send a credential with it, such as an `<img>`. A download serves a range of bytes, so a client whose download was cut short asks for the rest. A file's bytes go only once no restore of the database can bring its row back. It also keeps each user's avatar, which `accounts` sets and removes (D120).

## Owns

| Table | Holds |

## Interface

`Contract`, the personal data contract for `workspace_files`, `user_files` and `avatars` (D31), which deletes a deleted user's files and avatar (ACCOUNTS-013). Their bytes go as every unreferenced object's do (FILES-011). A file they uploaded to a workspace stays the workspace's, and its foreign key sets its `uploader_id` to null as the user's row goes (ACCOUNTS-014).

What `accounts` uses to keep a user's avatar (Design: Avatars):

- `AVATAR_MAX_BYTES`: the avatar's limit (ACCOUNTS-009), with which the route of `accounts` reads an avatar's body.
- `upload_avatar(&Files, Bytes, record)`: finds the kind of an avatar's bytes from the bytes alone, has the scanner scan them, and writes their object, outside any transaction, then has `record` make the `NewAvatar` the user's avatar, in a unit of work of its caller's, so the upload counts as stored once that unit of work commits (ACCOUNTS-009, FILES-013).
- `record_avatar(uow, UserId, NewAvatar)`: makes the new image the user's avatar, deleting the row of the one it replaces, and gives the avatar's ID.
- `delete_avatar(uow, UserId)`: deletes the user's avatar's row, and gives its ID, if they had one.
- `avatar_urls(uow, &[UserId])`: the path of each avatar's public download (FILES-024), for the users that have one among a batch. Callers pass only IDs that came from a query filtered by tenant, or the caller's own (DATA-16).

## Design

### Accepted kinds

Requirement 5.1.1 of the Application Security Verification Standard (ASVS) asks each upload to document the types it accepts, their extensions, its size limit, and how the files are made safe to download. Every upload of a file accepts these kinds, at most `FILE_MAX_BYTES` each (D95, D107), and an avatar's the image kinds alone, at its own limit (Avatars), and the API never decompresses a file itself. The scanner unpacks the archives it scans, and refuses one that unpacks to more than 400 MiB or holds more than 10,000 files, before it unpacks past either, as requirement 5.2.3 asks (Scanning). Each kind is served as Downloading says, and a file the scanner finds infected is refused, never stored (FILES-005).

| Kind | Extensions | Stored media type | Its bytes | Served |
|---|---|---|---|---|
| PNG | `png` | `image/png` | start with PNG's signature | inline |
| JPEG | `jpg`, `jpeg` | `image/jpeg` | start with JPEG's signature | inline |
| GIF | `gif` | `image/gif` | start with GIF's signature | inline |
| WebP | `webp` | `image/webp` | start with the signature of the Resource Interchange File Format (RIFF), of the form `WEBP` | inline |
| PDF | `pdf` | `application/pdf` | start with `%PDF-` | attachment |
| Word | `docx` | `application/vnd.openxmlformats-officedocument.wordprocessingml.document` | a ZIP archive from its first byte, whose central directory names `[Content_Types].xml` and `word/document.xml` | attachment |
| Excel | `xlsx` | `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` | as Word, with `xl/workbook.xml` | attachment |
| PowerPoint | `pptx` | `application/vnd.openxmlformats-officedocument.presentationml.presentation` | as Word, with `ppt/presentation.xml` | attachment |
| Text | `txt` | `text/plain; charset=utf-8` | UTF-8, with no control character but tab, line feed and carriage return | attachment |
| CSV | `csv` | `text/csv; charset=utf-8` | as Text | attachment |
| Markdown | `md` | `text/markdown; charset=utf-8` | as Text | attachment |

The list lives in `model/kinds.rs` as one table, so a fork adds a kind as one row and its check, and every download documents its media type from the table (`routes/mod.rs`). A kind's first extension is the one a public download names it with (FILES-023). A kind is added only when its bytes can be checked: Scalable Vector Graphics (SVG) and HTML are left out, since a browser runs the scripts they hold, and a format that a check can't tell from any other bytes is left out too.

An image is stored as its bytes came, never decoded and written anew (D109). Writing it anew, which the cheat sheet on uploads of the Open Worldwide Application Security Project (OWASP) suggests beside the signature's check, would drop what a crafted image carries for a flaw in a viewer's decoder, and a photo's metadata, such as where it was taken. It would also cost a decode and an encode of every image on a replica's turn, lose quality in every JPEG, and in every lossy WebP, for which Rust has no lossy encoder, lose the animation of a WebP, and give its members other bytes than its uploader sent. A crafted image that the check, the scan and the download's headers leave is left to the viewer's own updates, and the scanner's signatures of known exploits. A fork whose product shows its users' photos to strangers adds the rewrite to its image kinds' check.

### Storage

`platform::storage` holds the client of an S3-compatible bucket, a provider's off the server in the reference deployment (D106), which the settings `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_URI_STYLE` and `S3_CA_PATH` configure, each required but the last two: `S3_URI_STYLE` is `host` unless it is `path`, and `S3_CA_PATH` names a file of certificates that a bucket of the operator's own may chain to (OPS-01, SEC-01, PLATFORM-076). The endpoint must be `https` outside development and test (SEC-10). The client reports a bucket that doesn't answer in time, or answers that it can't serve now, as unavailable, and every other failure as internal, neither naming the key (ERR-04), as the [platform spec's Storage](platform.md#storage) says. Readiness doesn't wait on the bucket: replicas that couldn't reach it would all leave the load balancer, and every route would fail with them, rather than only those of FILES-012. Only the API reaches the bucket: every byte a client receives comes through a download route, so the bucket needs no address that clients reach.

An object's key is 128 random bits from the operating system's source, in hexadecimal, under the prefix `workspaces/` for a workspace's file, `users/` for a user's and `avatars/` for an avatar, so it names no row and reveals nothing (DATA-08, CODE-06). An object is written once and never replaced.

### Uploading

1. The handler refuses a body whose `Content-Length` declares more than `FILE_MAX_BYTES` (FILES-004), and a `visibility` that is neither value (FILES-020). An upload to a workspace then checks that the caller may upload, in a short unit of work of its own that authorizes them and commits nothing, and records a refusal as any workspace route does (FILES-006, D96). An upload to the caller's own files has authenticated them already, as every user route does.
2. It reads the name from `Content-Disposition` (FILES-002), then the body, in one of the replica's turns (PLATFORM-074).
3. It finds the kind from the name's extension, and checks the bytes against it through `Workers`, since a text's check reads every byte (FILES-003, CODE-05), then has the scanner scan them (FILES-005).
4. It writes the object, outside any transaction (DATA-21).
5. The unit of work opens, claims the `Idempotency-Key`, inserts the row, records the entry and publishes the event, then commits (FILES-001, FILES-016). For a workspace's file, it opens with `Authorize<FilesUpload>`, which authorizes the caller again.

An upload that stops after its object is written, whether a refusal at step 5, a failed commit or a stopped replica, leaves an object no row names, which FILES-011 deletes. The handler doesn't delete it itself: when a commit's answer is lost, the row may exist, and deleting its object would leave a row without bytes. A retry whose `Idempotency-Key` already committed writes its object, then answers the first result, leaving its own object to FILES-011 too.

The fingerprint of a keyed upload covers a SHA-256 digest of its body, as of any keyed route, its query, which holds its `visibility`, and its `Content-Disposition`, so a retry under another name, or as another visibility, is another request (API-12). The stored result is the file without its links, which the route adds to each answer, the first and every replay, for the session that sent it (FILES-021).

### Scanning

The scanner is ClamAV's daemon, `clamd`, which `platform::scanner` reaches at `CLAMD_ADDRESS` ([platform spec](platform.md#scanner)). The upload has it scan the bytes it holds, after their kind's check and before their write, and clamd answers that it found nothing, or names the signature it found, which its own log writes with the replica's address, so an operator can tell which signature refused a file. A scan that names no signature lets the upload go on, and one that names any refuses it (FILES-005).

clamd scans what it can read of a file whole: each member of a Word, Excel or PowerPoint file, which are ZIP archives, and what a PDF holds. Its configuration in every environment sets `AlertExceedsMax`, so a file whose contents pass its limits, such as an archive whose members unpack to more than 400 MiB, hold more than 10,000 files, or nest archives more than 17 deep, gets one of ClamAV's `Heuristics.Limits.Exceeded` signatures, and is refused rather than stored with part of it unscanned. Content that clamd can't read, such as a PDF's streams encrypted with a password, is scanned as the bytes it is, as ClamAV does by default, since refusing it would refuse every document sent with a password; an Office file encrypted with one isn't a ZIP archive, so FILES-003 refuses it before the scan.

A scan's time grows with the file's size and kind: on the development server, with ClamAV's signatures, an image or a text scans at about 0.1 seconds a MiB, a PDF at about 0.3, and a Word, Excel or PowerPoint file at about 0.9, since clamd scans every member of its archive, so 10 MiB of one take about 9 seconds, and 20 MiB, the largest `FILE_MAX_BYTES`, about 19 (D107). A scan has 30 seconds to answer, so the upload route's 60 seconds hold a body of 20 MiB that comes at 7 megabits a second, its scan, and the bucket's 15 seconds for its write ([platform spec](platform.md#storage)), and a body of 10 MiB at 2.5 megabits a second.

The reference deployment runs clamd with ClamAV's signatures, which it keeps up to date ([deploy.md](../operations/deploy.md#the-scanner)). Development and the tests run it with one signature of the repository's own, which names the test file of the European Institute for Computer Antivirus Research (EICAR), the antivirus industry's standard harmless test, so it starts in seconds with little memory, and no test reaches ClamAV's mirrors (TEST-06).

### Visibility

A file is private or public, as its upload chose, and stays so: rows are never updated (FILES-020, D114). A private file reaches only those who may read it: a workspace's members with `files.read`, or the user whose file it is. A public file also reaches anyone who holds its public download's path, without signing in, under a name of its ID and its kind's extension rather than its own, which is personal data, and which reaches only those who may read the file (SEC-11, D115, D116). A public file's ID is a UUIDv7, whose 62 random bits no one guesses at the rate the bucket of public downloads allows, so its path is known only to those it was given to. The uses the template has in mind are a workspace's picture or a product's own page, whose images a page, or an email, shows to people who aren't signed in. An avatar is public too, through a download of its own (Avatars).

Whoever may upload a file may upload a public one: in a workspace, `files.upload` covers both (D114). A member who may download a private file can already pass its bytes to anyone, so a permission of its own to publish one would keep nothing from them that downloading doesn't give. Who may delete a public file is who may delete any file, so a workspace's owner and admins can take down what a member published (FILES-010).

The public downloads run under the prefix `/v1/public/`, whose requests the IP limit counts in a bucket of their own, `public`, rather than in the `ip` bucket of every other request (PLATFORM-082, D11). A page that shows many public images to a visitor uses up that bucket, never the one that their sign-in and every other request count in. Each public download reads the row by its ID and its visibility alone, an avatar's by its ID, the reads of a tenant's data by an ID alone that DATA-16 exempts for this, since public means that whoever holds the ID may read the file or the avatar.

A public download may stay in a shared cache, such as a content delivery network's, for 5 minutes (SEC-12): long enough that a page shown many times reads the file from the API once every 5 minutes, and short enough that a deleted public file is gone from every cache within 5 minutes of its deletion. Within that time a cache may also revalidate it with `If-None-Match`, which answers 304 without its bytes (PLATFORM-081).

### Links

Each file that a route answers carries `content_url`, the path of its bytes, which a client puts where it can't send a credential, such as an `<img>`'s `src` or a link the operating system opens, after the API's address, as it does a `Location` (FILES-021, D113). A public file's link is its public download, which never expires. A private file's is its download, signed for the session that read the file: `?expires=...&session=...&signature=...`, as PLATFORM-080 builds it, valid for an hour, the access token's default lifetime (AUTH-007). A client that needs a fresh link reads the file, or its list, again.

A signed URL only stands in for the session's credential. The download authenticates its session, which must still last, and authorizes its user as any caller of the route, so losing access ends a URL at once, as it ends a session's requests (FILES-022, SEC-06, D5). A URL that leaks, as into a log or a copied link, works for anyone only while its hour, its session and its user's access to the file all last, and for that one file. The hour is fixed, rather than a setting: it bounds what a leaked URL gives, and a client reads files often enough to replace a link before it expires.

### Downloading

The download reads the row through the workspace from the proof, or the caller's own ID, or, for a public download, its ID and its visibility alone (DATA-16). It then streams the object from the bucket, so a replica holds at most a chunk of it at a time. `Content-Disposition` gives the name twice: as `filename*`, the name in UTF-8 percent-encoded as RFC 8187 says, and as `filename`, an ASCII fallback in which every other character, `"`, `\` and `%`, which some browsers decode, become `_`, as RFC 6266 recommends (ASVS 5.4.2). A public download gives the name of the file's ID and its kind's first extension instead, which tells no one more than its path and its `Content-Type` do, so every browser saves it with its kind's extension (D116). Given no name, Chrome and Firefox take the path's last segment, the ID, and add an extension of their own for the media type, which Firefox leaves off a text file, and which for a Word, Excel or PowerPoint file comes from the platform's own types, so the saved file's extension would vary by browser and platform.

Every download serves byte ranges as RFC 9110 defines them, with its `ETag`, the file's ID, which names its bytes, since an ID's bytes never change (PLATFORM-081, D112). A download that a deploy's drain cuts short, as when it outlasts the drain's 60 seconds on a slow link, resumes with a `Range` for the bytes its client lacks, from another replica (OPS-06). A browser's download manager resumes such a download, and the API's own clients do too. The bucket reads only the range that a request asks for.

### Deleting bytes

The bytes of a file outlive its row, so that a restore of the database to a moment before the row's deletion finds them (D93). A restore of the bundled database reaches back `BACKUP_RETENTION_DAYS` days, and up to 7 more, since a full backup expires only once a newer one, of the next week's, is that old ([backups.md](../operations/backups.md#what-is-backed-up)), so the deployment sets the delay to the retention plus 7 days, and the default, 35 days, covers the default retention of 28. With a managed database, `FILE_DELETION_DELAY_DAYS` is set to its provider's recovery window or more.

No statement deletes bytes when it deletes a row: a row may also go with its workspace's or its user's deletion, which cascades (DATA-05), or never commit, and the schema holds no trigger that could record either (DATA-07). Instead, two periodic jobs compare the bucket with the rows of `workspace_files`, `user_files` and `avatars`:

- `files.find_unreferenced_objects`, every day, lists the bucket's objects under each of the three prefixes, and records in `object_deletions` each that no row names and that the bucket wrote an hour ago or more, by the database's clock (DATA-03), with `deletable_at` `FILE_DELETION_DELAY_DAYS` days from now. An object already recorded keeps its time. An object written within the hour may belong to an upload whose row hasn't committed yet: recorded then, its delay would start before its row's deletion, and a restore to a moment while the row existed could find no bytes. An upload commits its row within its route's 60 seconds, and the rest of the hour leaves room for the bucket's clock and the database's to differ, so a recorded object is one that no row named since an hour after it was written.
- `files.delete_unreferenced_objects`, every hour, takes the recorded objects whose time has passed, in batches of at most 1,000, deletes from storage each that still no row names, and removes each from `object_deletions`, whichever it did. An object that a row names again, as after a restore, stays.

Both span every workspace and user by nature, so they select objects by key alone (DATA-16), and scheduled maintenance isn't audited (DATA-22). A bucket with versioning keeps a deleted object's bytes as a noncurrent version, so every bucket of the deployment has versioning off, or expires each noncurrent version a day after it becomes one, as [deploy.md](../operations/deploy.md#what-a-server-needs) requires and `just server-check` checks (D102). After a restore to an earlier moment, the objects of uploads made since then have no row, and go after the delay; `object_deletions` may have lost what it recorded since then, which the next run records again.

### Recording and events

A workspace's routes are workspace routes, so `Authorized<P>` proves the caller's membership and gives the workspace's ID, by which every statement filters, a file's ID among them, so a file of another workspace is never found (DATA-16). A user's own routes filter every statement by the caller's ID, so another user's file is never found. An upload and a deletion each record their entry and publish their event in the unit of work that changes the row (D1): a workspace's file in the workspace's log, as `file`, and to its members with `files.read`; a user's own in their own log, as `user_file`, and to their own streams. A name is text a user writes, so it is personal data: the entries' `details` are empty, their resource being the file, and the events' payloads carry only IDs (SEC-18, API-19).

### Avatars

Each user has at most one avatar, a row of `avatars` and its object under `avatars/`, which `accounts` sets and removes, recording its entries and publishing its events in its own unit of work ([accounts spec](accounts.md#avatars), D120). `files` keeps the image as it keeps a file, with the checks of an upload, and serves it, but an avatar isn't a file of the user's own: it has no name, no visibility but public, and no place in their list of files, whose routes never find it, so the user replaces or removes it only through `accounts`, which records and publishes each change.

The route of `accounts` reads the body through `Upload`, in one of the replica's turns, with the avatar's limit (ACCOUNTS-009), and `upload_avatar` finds its kind among the image kinds of Accepted kinds alone, PNG, JPEG, GIF and WebP, as the kind whose check its bytes pass, since an avatar comes with no name to take an extension from, and each image kind's check is the signature its bytes start with, which no two image kinds share (D121). It then has the scanner scan them, as any upload's (Scanning), writes the object, and counts the upload in `files.uploads` as any upload is counted (FILES-013). `record_avatar` deletes the user's row and inserts the new one, so a new image gets a new ID, and with it a new link, which no cache holds an older image under. It runs in the unit of work of `accounts`, after its update of the user's row, whose lock makes two changes of one user's avatar take turns, so the unique `user_id` never refuses the second.

`avatar_urls` reads the avatars of the users it is given, which came from a query filtered by tenant, such as a workspace's member list, or are the caller's own (DATA-16), and gives each avatar's link: its public download, `/v1/public/avatars/{avatar_id}`, which needs no credential and never expires, since an avatar is shown to the user's fellow members, and wherever they show it, as by an `<img>` that sends no credential (FILES-024). Its ID is a UUIDv7, which no one guesses at the rate the bucket of public downloads allows, as a public file's. The bytes of a replaced or removed avatar, and of a user's avatar once their account is deleted, which deletes its row, go after the delay, as every unreferenced object does (FILES-011).
