# Operations rules (`OPS`)

Configuration, background jobs, runtime behavior, CI, releases, deploys, backups and local development.

## Configuration

### OPS-01 Configuration is strict and typed
`platform::config` loads every setting once at startup into typed values:
- Values are trimmed, and an empty value counts as unset.
- A setting can be read from a file named by `<NAME>_FILE` (SEC-01).
- Numbers are range-checked, a number that another setting bounds is refused beyond it, such as an access token's lifetime beyond its refresh token's (AUTH-007), and unknown values for a closed set are errors.
- Required settings have no defaults. `ENVIRONMENT` is required.
- Why: a misconfiguration fails at startup, never in the middle of a request (D9).
- Check: `test` (a test reads each whole number's range from `.env.example`, and refuses the values just outside it, and the test of each bounded pair, such as AUTH-007's, refuses a value beyond its bound), plus `review` (which settings another bounds).

### OPS-02 Every setting earns its place and is documented
A setting exists only if two deployments would set it differently, such as a URL, a credential, a capacity or a feature switch. A value every deployment would share is a constant in code. Every setting of the API appears in `.env.example`, but those that only the test environment may set, which the test support sets: the outbound clients' `OUTBOUND_TEST_ORIGIN`, which startup refuses in any other environment (SEC-10), and the stand-in provider's `STAND_IN_` settings, which only the tests' build reads ([auth spec](../spec/auth.md#signing-in-through-a-provider)). Every setting of the reference deployment appears in `deploy/settings.env.example`, each with its type, default and meaning. Compose passes each container only the settings it reads, and a fingerprint of files it mounts, by which a deploy recreates it.
- Why: a small configuration surface is one a fork can understand, and no container holds settings it doesn't use (D9, D15).
- Check: `test` (the settings the API's subcommands read, as `platform::config` is asked for them, are those of `.env.example` but `POSTGRES_PASSWORD`, the one that only Compose reads, for its two Postgres servers, and the test environment's own, both ways, and each service of `deploy/compose.yaml` that runs the API's image passes it exactly the settings its subcommand reads), plus `review` for the third-party containers, for `deploy/settings.env.example`, and for the "would two deployments differ" question.

### OPS-03 Startup failures have one format
A failure that ends a subcommand of the API binary, at startup or, for a one-shot subcommand such as `migrate`, in its work, is logged as one `ERROR` event, with the message `startup failed` and the fields `startup.area` and `exception.message`, through the configured logging setup (OBS-01, OBS-05). The process then exits with code 1. A failure before the logging setup exists, such as invalid configuration, or a failure of the logging setup itself, is written by `main` to stderr as one JSON line with the same message and fields. That is the one place in the API's crates where `print_stderr` is allowed (CODE-03). Nothing panics. A command line that the binary's parser refuses, such as `serve` given an option it doesn't take, ends before any setting is read, with the parser's usage on stderr and exit code 2.

A subcommand that an operator runs against the accounts, such as `remove-second-factor`, logs what it did as one `INFO` event, with the message `subcommand finished` and the fields `startup.area`, which names the subcommand, and `startup.outcome`, which says what it did, without personal data (OBS-04). The process then exits with code 0. What keeps it from doing anything is a failure that ends it, as above.
The subcommand that an operator runs against the files bucket, `restore-files`, logs what it did, and a failure that ends it, the same way (FILES-029). <!-- part: files -->
What such a subcommand shows the operator who ran it, because they asked to see it, as the list of the deployment's superadmins, `main` prints to the standard output, a line each, outside the logging setup: it may hold personal data that the operator asked for, which no log and no telemetry then holds (SUPERADMINS-008). <!-- part: superadmins -->
- Why: operators and scripts handle one shape (D9).
- Check: `test`.

### OPS-04 Disabled features say so
A route whose feature is turned off answers the 503 problem with code `request.feature_disabled`. The capabilities endpoint lists which features are on. That 503 is no failure of the deployment: the request's metric carries the code, the HTTP boundary writes no `ERROR` line for it (ERR-10), and the availability objective doesn't count it ([observability](../operations/observability.md#service-level-objectives)).
- Why: clients can tell "off" apart from "broken" (D9).
- Check: `test` (SYSTEM-001; PLATFORM-044, the 503's one `INFO` line; PLATFORM-067, the 503's code on its metric; and the 503 of a route whose feature is off, such as AUTH-028's and AUTH-100's), plus `ci: alert-rules` (a test in which a tenth of the requests answer that 503 expects no alert of the availability budget's fast burn).

## Runtime

### OPS-05 Health means something
- `GET /health/live` answers 200 while the process runs.
- `GET /health/ready` answers 200 only while the database answers the listener and the instance isn't draining.

The probes are answered before the rate limit, load shedding and request timeout, and they carry no trace context (OBS-15). Their body is `{"status": "<status>"}`, never a problem response (API-07).

While no replica is ready, such as during a restore, the reference deployment's proxy answers each request within two seconds with the 503 problem `request.unavailable` and `Retry-After`, whose trace ID leads to the proxy's span and log line of the request, and without telemetry to its line in `just logs` (D10, D53, D56), and a probe with a bare 503. Both carry the headers that the API sets on every response (SEC-12), and the problem its trace context in `server-timing` too (API-16).
- Why: the load balancer only routes to replicas that can serve, and a client gets the API's answer even when none can (D9, D20, D53).
- Check: `test` (PLATFORM-038, PLATFORM-061), plus `ci: e2e` (the proxy's answer while no replica runs, and its line in `just logs` without telemetry), plus `review` (a probe never runs long enough to show that no timeout applies to it).

### OPS-06 Shutdown is bounded and graceful
The instance installs its handlers for the shutdown signals before it connects to anything, and fails startup if it can't (OPS-03). On SIGTERM, the instance shuts down in this order:
1. Turn readiness off.
2. Wait one health-check interval, so the load balancer stops sending traffic.
3. Stop accepting connections, and close the open streams, so their clients reconnect to another instance.
4. Drain requests, up to a deadline no shorter than the longest timeout of a route, so a request that its route lets finish isn't cut short.
   An upload's is the longest. <!-- part: files -->
   A download's bytes stream for as long as its client takes to read them, so the deadline may cut one short, which its client resumes from another instance, asking for the bytes it lacks with a `Range` (PLATFORM-081).
5. Cancel jobs and release their leases.
6. Flush telemetry.

The whole sequence fits inside the container's grace period, with margin.
The end-to-end deploy scenario also holds an upload whose body is still coming when its replica stops, and a test resumes from another instance, with a `Range`, a download of which it holds the first bytes; that the deadline ends a request still in flight is the drain's own test (PLATFORM-062). <!-- part: files -->
- Why: deploys drop no requests, and SIGKILL never cuts a flush short (D20). An instance that can't receive SIGTERM is killed mid-request by every deploy.
- Check: `ci: e2e` (the deploy scenario), `test` (the sequence through `platform::lifecycle::serve`, and the deadline's default), plus `review` (the handlers are installed before anything connects, because no test can make installing them fail).

### OPS-07 Overload sheds load
Every request that a route serves, except the health probes, has a timeout. Each route group has a default, and a module spec may override it. A request that no route serves has no route group's timeout: once the IP limit has counted it and let it pass (PLATFORM-054, D64), a wait that the pool's and the database's own timeouts bound, it gets its 404 or 405 problem, or the cross-site check's 403 (PLATFORM-059). A listed origin's preflight is answered 204 before the IP limit, uncounted (PLATFORM-058). A concurrency limit rejects excess requests with the 503 problem and `Retry-After`. The health probes are exempt from it. CPU-heavy work, such as a password's hash, waits for one of the instance's turns, one per processor it may use (PLATFORM-060), so a burst of it takes no more memory than that many works do.
- Why: an overloaded instance degrades predictably, instead of queuing until it falls over (D20).
- Check: `test` (PLATFORM-042, a route's timeout; PLATFORM-039 and PLATFORM-038, the concurrency limit and the probes' exemption from it; PLATFORM-054, the IP limit's count of a request that no route serves; PLATFORM-060, the turns of CPU-heavy work).

### OPS-08 Postgres is the only shared state
Replicas share nothing except Postgres.
With `files`, they also share object storage. <!-- part: files -->
A request can be served by any replica, with no sticky sessions.
- Why: scaling out means adding replicas (D20).
- Check: `review`.

## Background jobs

### OPS-09 Jobs are declared once and are idempotent
Each job is declared in its module's `jobs.rs`, or, for a job of `platform`, in the area it belongs to, as `platform::jobs` declares its sweeps and `platform::mail` the job that sends an email, and is registered in the job registry, under a kind `<module>.<name>`, or `platform.<name>` for one of `platform`'s. It states its owner, its schedule or trigger, and the tables it touches. Running a job handler twice has the same effect as running it once, but for an effect outside the API that a run can't take back, such as an email's delivery, with what the API keeps of that effect, such as the hash-based message authentication code (HMAC) of the code an email carries (D128): the job's spec states what a second run causes, and how its receiver recognizes the repeat.
- Why: jobs are delivered at least once (D1, D13).
- Check: `ci: check-layout` (a job is declared in its module's `jobs.rs`, or in `platform`, with a kind that starts with its module's name, or `platform.`), plus `test` (each job's test runs its handler twice).

## Build, CI and release

### OPS-10 CI calls `just`
Every CI step that builds, checks, publishes or releases runs a `just` task, so CI's tests are `just test`, which starts the services they use through Compose, as on a developer's machine. The steps that prepare the runner, such as checking out the repository, installing tools, restoring a cache, and signing in to the registry, are the workflow's own, because `just` isn't installed, or the runner isn't ready for a task, until they run. So is the registry's upkeep, which a pinned action does. The workflows only orchestrate: `ci.yml` for pull requests and `main`, whose runs on `main` also publish and release, and `scheduled.yml` for scheduled jobs. The checks required for merging are listed in `docs/operations/ci.md`, which says how to require them, and why requiring them is the repository owner's choice.
- Why: local and CI runs are identical, and a repository that gates merging requires exactly the documented checks (D21).
- Check: `review`.

### OPS-11 Everything is pinned
Besides the toolchain, which CODE-01 pins, actions are pinned by commit SHA, images by digest, downloads by checksum, the crates the image's build installs by exact version with `--locked`, and the runner by version. The images the tasks run are pinned in `compose.yaml`, beside the services' images, or in the reference deployment's Compose files that `compose.yaml` extends, which name the ones a server runs too. The other tools the tasks use, such as cargo-deny and watchexec, are pinned by version in the justfile: `just setup` checks them, and CI installs them from it. `just` itself is the exception: CI installs it before any task can run, so the workflows pin its version too. The packages that `just server-setup` installs on a server from apt, Docker's among them, are the distribution's current ones, as the server's other packages are, so that the system's security updates reach them; Docker's repository is trusted by its key's fingerprint, which `deploy/server-setup.sh` holds. Dependabot proposes updates to the pins it can read, and `docs/operations/ci.md` lists the ones updated by hand.
- Why: a build today is reproducible tomorrow, and a pin moves only in a change that CI checks (D21); a server's packages take the system's security updates (D55).
- Check: `ci: check-pins`, plus `review` (an image or a download that a recipe or a workflow's `run:` step names, a download that a Dockerfile's `RUN` makes, and what a Dockerfile or a compose file pins under another name than `Dockerfile` or `compose.yaml`, which `check-pins` doesn't read, and the list in `docs/operations/ci.md` of the pins updated by hand).

### OPS-12 Build once, then promote that digest
Each pipeline run builds each image once, for linux/amd64 and linux/arm64, with its software bill of materials (SBOM) and its provenance attached: the API's image, and the reference deployment's Postgres (D44). Every later step scans, boots, tests and publishes those same digests: on `main`, as `sha-<commit>`, and as `edge` while the commit is the head of `main`. `just release` asks for a release: it sets the app's version, refusing one that doesn't come after every release, and commits it. Without a version, it shows the latest release, or the version that `main` asks for already, and the versions that can follow it, and changes nothing. The first run on `main` that then passes with that version releases it, unless a release has it already: it gives each digest the version's tag, `X.Y.Z`, or `X.Y.Z-rc.N` for a prerelease, signs it, and only then tags the commit `v<version>`, such as `v1.4.0` or `v1.4.0-rc.1`. A version that no `just release` asked for releases nothing. Nothing is rebuilt.
- Why: what ships is exactly what was tested, and a release is always a commit that passed every check (D15, D21).
- Check: `review` (the workflows' structure), `ci: e2e` (each platform's image boots), `ci: verify-release` (each image's version tag names the tested digest, signed by the run on `main`, whose image names that version as its own, with the SBOM and provenance of both platforms), plus `test` (what `just release` refuses, and the versions it shows without one).

### OPS-13 The image is minimal and unprivileged
One image serves every subcommand. It holds the API's static binary on a base with no shell, no package manager and no C library, which provides the operating system's certificate store and time zone data. It runs as a non-root user with a read-only root filesystem, and has a `HEALTHCHECK`, which runs the `health` subcommand (PLATFORM-063).
- Why: a small attack surface, and the same artifact everywhere.
- Check: `ci: image-scan` (no vulnerability that has a fix and is rated high or critical), plus `ci: e2e` (bootstrap, migrate and serve run from the image as its user on a read-only root, and the health check, which runs `health`, reports the serving instance healthy).

## Deploy and recovery

### OPS-14 Deploys roll without downtime and roll back on failure
A deploy takes a release by its version, the latest release unless the operator names another, and refuses a version that no release has. It applies the release's migrations, starts new replicas, waits until the load balancer finds every one of them ready, then stops the old replicas, which drain (OPS-06). If a new replica doesn't become ready, the deploy removes the new replicas, and the old ones go on serving, unless it stopped them to replace the network, below. A deploy that refuses, or ends before its replicas serve in place of the old ones, puts back the deployment's files that it replaced. When it can't, because it was stopped by force or the copy failed, which it reports, the next deploy, backup or restore puts them back before anything else (D50). The proxy and the bundled database, which the API's requests pass through and which each run as one instance, are restarted by a deploy only when the operator allows it, because restarting one interrupts requests. So is the network that the proxy and the replicas join replaced, when its subnet is another than the setting's (SEC-13): the deploy stops the proxy and every replica for it, so a request gets no answer until the deploy starts the proxy again, and the proxy's 503 from then until the release's replicas serve (OPS-05).
So is the malware scanner, whose restart interrupts uploads alone. <!-- part: files -->

A service that runs with a secret file it read as it started, which `just server-setup` or `just replace-key` replaced since, is recreated by the next deploy, so it reads the new one: the ones that run once only with the operator's consent. A service of the observability stack restarts, or reloads, when a deploy changes its configuration, which interrupts no request of the API. A deploy runs only the services that its settings choose (D42), and stops those an earlier choice started once no replica uses them. Nothing a deploy leaves grows without bound (D57): every container's log is capped and rotated, and once a deploy's replicas serve, it removes the files of every other release that the server holds, and the images of the deployment's repositories that no container uses and that neither its chosen services nor its tools name, so the previous release's API image stays for a rollback. One deploy, backup or restore runs at a time, and its lock goes when its processes end, however they end. The alert rules are the release's files, which a deploy installs as they are and the services read again, and which no deploy generates or rewrites.
- Why: deploying is routine, not a risk, an alert means the same whatever deployed the system (D15), a server's disk doesn't fill with what deploys left (D57), and a secret changes with one deploy (D103).
- Check: `ci: e2e` (each item below), plus `test` (what `just deploy` refuses, that it takes the latest release unless one is named, and that the files it sends keep the line endings the repository holds).
  - a deploy of the real images under continuous requests, none of which fails
  - the rollback, with the files it puts back
  - the services that a replaced secret recreates, Postgres only with consent
  - the files that the next task puts back after a deploy killed before its replicas serve, and after a put-back that failed
  - the files a deploy keeps when it ends after its replicas serve
  - the restart only with consent, and the replacement of the proxy's network only with consent
  - the services a change of settings stops
  - the images and the release files a deploy removes and keeps, and each container's capped log
  - the rules a deploy installs, also after a refused one
  - the refusal while another task runs

### OPS-15 Backups are continuous and restores are tested
The bundled Postgres archives its write-ahead log continuously, and takes base backups on a schedule, to an S3-compatible bucket off its server, encrypted before they leave it, with retention. A restore recovers the database into a fresh one, as it stood at any moment the retention covers, a moment that an earlier restore went back past, and one while an earlier restore ran, included. A moment that no commit or rollback the bucket holds follows on its timeline, such as one while an earlier restore ran, after the moment it named and before its timeline began, or one after the last change that a lost server archived, is recovered as of that timeline's end in the bucket: nothing the bucket holds changed after the moment, and what a lost server hadn't archived is lost. The restore then names the time of the last commit it replayed, or, when it replayed none, the backup it started from.

Before it stops Postgres, a restore records in the bucket when its timeline begins, by the server's clock, to the microsecond, on the newest full backup, which outlives every backup that reaches a moment before then, and a restore's plan reads from those records which timeline was live at a moment; a restore whose record fails, as when the bucket stops answering, starts again what it stopped, when Postgres runs the database it found, and refuses, whatever its options. A bucket that holds a timeline whose beginning no backup records, and a backup from before that timeline, as when a restore couldn't record the beginning of the timeline that Postgres began, can't tell which timeline was live at a moment before every later timeline's recorded beginning: a restore refuses such a moment before anything stops, and restores the latest state. A restore whose replay can't fetch a segment of the log that the bucket holds, as when the bucket stops answering, fails, rather than serving the database as it stood before that segment.

A restore that finds Postgres running the database the bucket backs up, with its log reaching the bucket, first commits a transaction of its own, which pgBackRest's check archives, so the bucket holds every change until it began, and names the moment that returns the database to how it found it: a restore that went back too far, or shouldn't have run, is undone by another. A restore that finds Postgres running the database the bucket backs up, with its log not reaching the bucket, as pgBackRest's check finds, refuses before anything stops, and one whose transaction, or the check that archives it, fails once the replicas have stopped starts them again and refuses, unless `--allow-unarchived` lets it go on: the changes that the bucket lacks would stay only in the data it replaces, while the API serves the restored database, and no restore would undo it.

Before the replicas stop, a restore marks the full backup it starts from in the bucket, which the retention keeps until a backup taken after the restore is as old as the retention, and a restore whose mark fails, as when the bucket stops answering, refuses with the API serving, whatever its options: without the mark, the retention could expire the backup that the restored timeline's first moments replay from. Postgres still replaying the log, as after a restore that failed during its replay, isn't running the database the bucket backs up: a database in recovery takes no writes, and holds only what the bucket gave it, so a restore that finds it checks nothing, commits nothing and names no moment that undoes it. A restore from the backups as their bucket held them at a time checks nothing either, commits no transaction, marks no backup and records no timeline's beginning, since what the bucket holds isn't what it restores from (OPS-22).

`just backup` takes a base backup on demand, and `just restore` restores the latest state, or the state at a given moment, and refuses a moment that the server's clock hasn't reached before anything stops. `docs/operations/backups.md` states the recovery targets, and requires a managed Postgres to provide point-in-time recovery of its own.
- Why: losing the server loses at most about a minute of data, a mistake can be undone up to the moment before it, a restore too, and an untested backup is not a backup (D30, D44, D59, D60, D85).
- Check: `ci: e2e` (each item below), plus `test` (the backup and the timeline that a restore to a moment plans from what the bucket records, the refusal of a moment that the server's clock hasn't reached, and `just restore`'s moment and option).
  - a restore to a moment, after which the restored database holds what was written before the moment and not what came after, and the API serves through the proxy
  - onto a new server, a restore of its latest state, and one of a moment after the lost server's last archived change, which names no moment that undoes it
  - restores after a deploy that failed, to a moment after the last change, to a moment while an earlier restore ran, before its timeline began, and to the moment just after, to a moment that an earlier restore went back past, to the moment that an earlier restore named, to one after an earlier restore, and to one on a restored timeline before its first backup, and of its latest state then
  - restores of the latest state while Postgres still replays the log, and while a one-off container of Postgres's service runs, as one that plans another restore does
  - while the log doesn't reach the bucket, a restore's refusal before anything stops, and a restore with `--allow-unarchived`; and a restore whose log stops reaching the bucket, or whose transaction fails, once the replicas have stopped, which serves again and refuses, and with `--allow-unarchived` restores
  - a restore whose replay can't fetch a segment that the bucket holds, which fails, with the API down
  - a restore's mark of the full backup it starts from in the bucket, which the retention keeps until a backup taken after the restore is as old as the retention, and a restore whose mark fails, which refuses with the API serving
  - a restore's record of when its timeline begins on the newest full backup, and a restore whose record fails, which serves again and refuses with `--allow-unarchived`

### OPS-16 Capacity is measured
`just load-test` runs one replica of the image, with the reference deployment's CPU and memory limits for a replica, and finds the highest constant rate of requests it serves with no request failed and the 99th percentile within the latency objective. That rate is the replica's capacity. The task runs before each final release, and the line it ends with is part of the release's notes, its section of `CHANGELOG.md` (DOC-11).
`just load-test streams` measures the replica's hub the same way: with 1,000 streams open on it, 10 for each of 100 users, it finds the highest constant rate of events, each to the 10 streams of one user, that the hub delivers with no event lost or repeated and the 99th percentile of their lag within the latency objective, while a second replica takes the requests that publish them, and it reports the memory each open stream holds; it runs before each final release too, and the line it ends with goes in the notes beside the other.
The scripts that k6 runs for them act at states they observe, never after a time they guess (TEST-06): a step reads the spans that the collector accepted once the API's spans have had the most time that they take to leave it, or, in a step of the capabilities, once they reach two for each request that the step was to send, and the hub's lag once Prometheus holds a sample that the replica took after the step's requests ended, without which, past a bound, the step fails.
- Why: capacity is a number, not a guess (D20).
- Check: `test` (the search for the highest rate, and the release's refusal of notes without the two lines), plus `review` (the lines are those of the release's image; [release.md](../operations/release.md#before-you-release)).

### OPS-17 Data is encrypted in transit and at rest
Every connection that the deployment opens beyond the server the API runs on uses TLS, and verifies the certificate of the service it reaches. What the operating system reaches for itself is the server's to configure: its package downloads, which carry none of the deployment's data, and which apt verifies by their repository's signature, since a distribution's mirrors may serve plain HTTP, its time source and its name servers. Clients reach the API over HTTPS only: the proxy answers plain HTTP at the API's address with nothing, and closes the connection, so a client that sends a request unencrypted fails at its first, and at Grafana's address, whose pages a browser opens, with a redirect to HTTPS. Two answers to plain HTTP remain at the API's address, each before the site handles the request: the bare refusal of one that Caddy's own server can't read (SEC-12), and Caddy's answer to its certificate authority's challenge, at the challenge's path, while it obtains a certificate for the address. The proxy takes TLS 1.2 and 1.3 alone, and for 1.2 only cipher suites that agree on a key by an ephemeral elliptic curve exchange and encrypt with authentication, and the keys of its certificates are on the curve P-256. A managed database is reached with `sslmode=verify-full`, which a deploy requires of each of its URLs, and the backup bucket and a managed observability backend over HTTPS. A deploy refuses email without encryption to a mail server that isn't at one of the server's own addresses. Stored data is encrypted below the API: the deployment's volumes are on encrypted disks, a managed database and a bucket encrypt what they store, and backups are encrypted before they leave the server. The API itself encrypts only secrets (SEC-02).
- Why: TLS and storage-level encryption protect personal data in transit and at rest, without application-level encryption of every column (D14, D55). A client that sends plain HTTP learns it at its first request (D184), and the proxy's TLS doesn't change with its defaults (D185).
- Check: `ci: e2e` (each item below), plus `review` (the proxy's TLS settings, and what `docs/operations/deploy.md` requires of a server and its providers).
  - the proxy answers no plain HTTP at the API's address, answers it at Grafana's with a redirect to HTTPS, and answers HTTPS with HTTP Strict Transport Security (HSTS)
  - the Postgres image holds the certificate authorities that a bucket's certificate is checked against by default
  - a deploy refuses a managed database's URL that doesn't set `sslmode=verify-full`, and unencrypted email to another address than the server's own
  - the end-to-end tests' managed database is reached with `sslmode=verify-full`, under an authority of the tests' own

### OPS-18 The connection budget fits
An instance opens at most `DATABASE_MAX_CONNECTIONS` pooled connections, plus the listener, and `serve` logs that number once it connects. A deploy refuses to start replicas when every replica it would run at once, at that number each, together with the connections of the one-shot subcommands and of the backups, would exceed the connections Postgres allows. An operator's subcommand takes one connection, and refuses to run while another of them runs, so the budget counts one for them.
- Why: replicas can't exhaust the database's connections, even while a deploy runs two sets of them (D20).
- Check: `test` (PLATFORM-007; and an instance whose every pooled connection is in use, while the database stops answering on the listener's, keeps to that number across the checks that time out), plus `ci: e2e` (the deploy's refusal, and that of an operator's subcommand while another runs).

### OPS-19 The server is operated from the developer's machine
Every task on the reference deployment's server runs from a developer's machine, through `just` over Secure Shell (SSH), and none needs a shell on the server. A runbook or an operations document may also name a command that the operator runs on the server over `ssh <user>@<address>`, or over `ssh <host>` with the server's `Host` (below): to read what no task shows, such as `docker stats`; to free disk space, such as `docker image prune` or the removal of the data a restore moved aside; or to undo a restore that failed, as `docs/operations/backups.md` says. None of them changes the deployment's settings, secrets or services.

The settings and the secrets stay on the server, in one place. `just server-setup` installs Docker, prepares the user the deployment runs as, logs it in to the registry, and writes the settings and the secrets the operator holds, the credentials of the alert integrations among them, asking for each one that the settings' choices need, and generates the key ring that encrypts the secrets the database holds, the backups' passphrase and the bundled database's superuser password, which it shows once, unless the operator gives a lost server's, or, for the key ring, a ring with a new key; no deploy writes them. `just replace-key` writes a new key in place of one of the two that a deploy generates, the key of the API's keyed hashes or the one under which Grafana encrypts what it stores, and refuses another secret's name; the next deploy gives the new key to the services that read it. `just server-setup` ends with the `Host` of `~/.ssh/config` that names the server, its address and the deployment's user, unless the server it was given is such a `Host` already, so the other tasks name the server alone.

`just server-check` checks what a deploy needs, and, where systemd reports it, that the server's clock is synchronized, and changes nothing of the deployment but the object that it writes to each bucket and deletes (OPS-22). `just status` shows which color serves, each of the deployment's containers with its state and its image's version, when the backups last succeeded, the data that each restore moved aside, which stays until the operator removes it, and the server's free disk and memory, and changes nothing. `just logs` shows the services' last log lines, with the proxy's lines of the requests it answered itself, and follows them on request.
- Why: one place to operate a deployment from, and a server set up and checked the same way every time, also by a developer who has never set one up (D51, D54).
- Check: `ci: e2e`, plus `test`, plus `review`, each for what its item below says.

### OPS-20 Two commands from clone to running
`just setup` checks the required tools and the versions the justfile pins, and writes `.env` with generated development secrets, once. Both it and `just dev` warn of each setting of `.env.example` that `.env` lacks, and of each that `.env` still sets to a value that `.env.example` once had and has since changed, as git's history of it shows, but for a generated secret's value, which differs by design, naming the setting, with the example's value unless it is a generated secret's placeholder, and never `.env`'s, since later commits add settings and change development values that an existing `.env` doesn't get. A value that `.env.example` never had is the developer's choice, and draws no warning. `just dev` starts Postgres and the local stand-in for email, then runs the API with auto-reload, and `just dev observe` also starts the observability stack and exports the API's telemetry to it.
`just dev` also starts the local stand-in for object storage, and the malware scanner. <!-- part: files -->
Both work on Windows, macOS and Linux, with Docker available. Development secrets are never committed.

After a change, the tasks read what changed without a step by hand, in two places where a running container or a built image would otherwise go on as it was. Each task that starts the development services first restarts each running service whose configuration changed since it started: a file that the service mounts from `deploy/`, such as the collector's or a dashboard, which Compose leaves as its container read it. And `just e2e` and `just load-test` refuse to run the API's image in `target/image` unless it is built from the files of the working tree that an image is built from, as the image's label says, and name `just image`, which builds it. A change of `.env` is the one that waits for a step: `just dev` reads `.env` as it starts, so the API gets a changed setting once `just dev` is started again.
- Why: a fork is productive within minutes (D28).
- Check: `ci: setup-smoke`, plus `review`, plus `test`, plus `ci: e2e`, each for what its item below says.
  - `ci: setup-smoke`: on Linux, in every run, `just setup`, then `just dev` until the API it starts answers ready; on Windows, whose hosted runners can't run Linux containers, every week, `just setup` and a build of every target.
  - `review`: macOS, whose hosted runners have no Docker, which `just setup` requires: it runs the same recipes as Linux, which `check-shell` reads.
  - `test`: the warnings of a `.env` that `.env.example` has moved past, read from a repository's history, that never hold `.env`'s value, and none for a value the developer chose; which of a service's mounts are its configuration, and how the image's label is read.
  - `ci: e2e`: the image's label is the working tree's, in every run.

### OPS-21 The tasks bound what they leave on the machine
What the tasks leave on the machine that runs them stays within a bound, however many times they run, rather than growing until someone removes it by hand:
- A run of the end-to-end tests, or of `just load-test`, holds the machine, and fails at once while another holds it, since each counts the machine's memory as its own (D84). The containers it starts for a test go when the test ends, and before it starts any, it removes those that an earlier run of either left, as one stopped by hand leaves its servers, with their volumes. Compose's services that they use, the registry, the mirror and the observability stack, are the repository's own, and run between runs.
- A run of the end-to-end tests, or of `just load-test`, empties the registry that it pushes the images under test to before it pushes them, and then removes every image that earlier runs of either pulled from it onto the machine but those under test.
- The store of the mirror, from which the servers of the end-to-end tests pull Docker Hub's images, holds the images of one list for one platform: a run of the end-to-end tests empties it before it fills it, unless the store names the run's platform and list as what filled it.
- `just image` leaves BuildKit's builder at most 10 gigabytes of cache, the least recently used going first.
- A run of the tests drops each test's database, with the roles the test created, as the test ends, and, before it creates any, those that an earlier run left: its last tests', when it ended before they were dropped, and every one of a run stopped by hand. A test waits to create its database while more than 32 that earlier tests left are yet to be dropped, so what the tests' Postgres holds in memory, which Compose bounds at 2 gibibytes, doesn't grow with the number of tests.
  A test's bucket goes with its database, and a run removes, by their own names, the buckets that an earlier run left, whether their database stays or has gone. <!-- part: files -->
- A task that needs a database of its own creates it on the development Postgres and drops it as it ends: `check-schema`, `sqlx-check` and `just new-module`, for the schema that the migrations build, and `just load-test`, for what its replica writes. Before it creates one, it drops each that its name shows such a task created more than an hour before, which a run that was stopped before its end left.
- Docker keeps the output of each service of `compose.yaml` that runs between the tasks, such as Postgres, the registry and the observability stack, in at most five files of 20 megabytes each, as the reference deployment's Compose file has it keep its services', where Docker's default keeps one file that grows for as long as the container lives.
- An image that a pin of `compose.yaml` named before an update moved it is the one thing that the tasks leave for the developer to remove, with `docker image prune`: another project on the machine may run an image of the same repository, so no task removes one that it didn't pull from the repository's own registry.
- Each task that builds the API's code into the build directory of the dev and test profiles, `just lint`, `check-doc-links`, `test`, `e2e`, `prepare`, `sqlx-check`, `check-schema`, `openapi`, `new-module`, `setup-smoke` and `bootstrap`, which `dev`, `run`, `migrate` and `seed` run first, first removes that directory once it holds more than 40 gibibytes, the repository's or that of a copy that a check makes, so the build after it starts afresh: Cargo removes none of the artifacts of earlier dependencies and settings. The other tasks build only `xtask` there, which the next of those removes with the rest.
  `just keep` and `just remove` build the API's code there too, to write `openapi.json` again, and remove the directory first as those tasks do. <!-- part: removal -->
- Before a check makes a copy of the repository, as `check-new-module` and `check-rename` do, it removes the copies made longest ago, each with its build directory, while the copies hold more than 60 gibibytes together, the one it is about to make going last. A copy builds without incremental compilation, whose caches would roughly double what its build directory holds.
- Why: a machine that runs the tasks every day fills its disk within days, and a hosted server whose provider limits its writes, as this repository's development server's did, stops being usable (D84, D86, D162, D163).
- Check: `ci: e2e`, plus `test`, plus `review`, each for what its item below says.
  - `ci: e2e`: a run that holds the machine, the removal of the containers that an earlier run left, and the label of each container the tests start in the background.
