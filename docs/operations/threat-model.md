# Threat model

What the API and its reference deployment protect, from whom, and which rules and behaviors stop each threat. The bar is Level 2 of version 5.0.0 of the Application Security Verification Standard (ASVS), but for the requirements that it leaves out, 6.3.3 and those of [Relaxed requirements](#relaxed-requirements), as [the security rules](../standards/security.md) say (D26, D63, D198). Each mitigation is stated in its home, a rule or a behavior, which this file cites by ID rather than restating it (DOC-07), and a change that adds a threat, or changes what stops one, changes this file in the same commit. [The map of the bar's requirements](asvs.md) says how each one stands.

## What it protects

- **Accounts and sessions:** password hashes, authenticator apps' secrets and recovery codes, and the tokens of sessions, which act as their user.
- **Workspaces:** what each holds, who belongs to it, and with which role.
- **Files:** the bytes of the files that a workspace's members upload, in the files bucket off the server, and their names, which are personal data ([files spec](../spec/files.md)). <!-- part: files -->
- **Personal data:** email addresses and names, and the client IP addresses and user agents that audit entries record (SEC-18).
- **The audit logs:** who did what, which an attacker would want to change or erase.
- **Secrets:** the keys, the passwords and the credentials of the deployment, which [Keys and algorithms](#keys-and-algorithms) lists, each with what it protects (SEC-01).
- **The backups**, which hold the database, and so all of the above but the secrets, in a bucket off the server ([what is backed up](backups.md#what-is-backed-up)).
- **The deployment's server**, its Postgres, and its observability stack.

## Protection levels

Each kind of data has one of five levels, and each level its requirements, which the rules beside them state (requirements 14.1.1 and 14.1.2 of ASVS). A value has the level of what it holds, however it is written: a value that is only encoded, such as a list's cursor, which holds its last item's sort key and ID ([lists](../spec/platform.md#lists)), protects nothing, and keeps the level of the list that gave it.

| Level | What has it | In transit | Stored | In logs and telemetry | Who reads it | Kept |
|---|---|---|---|---|---|---|
| Secret | What proves who a caller is, or opens other data: passwords, a session's and a device's tokens, codes, recovery codes, authenticator apps' secrets, and the secrets of the settings, which [Keys and algorithms](#keys-and-algorithms) lists | Over TLS (OPS-17), in a body, a header or a cookie, never in a URL (SEC-01, SEC-07) | Only as a hash, or, where the API must read it again, encrypted with authentication and bound to its row (SEC-02, SEC-03, SEC-04, PLATFORM-087); a setting's secret as a file that only the deployment's user reads ([the files on the server](deploy.md#the-files-on-the-server)) | Never (SEC-01, OBS-04) | No one: the API compares it, and shows a user their app's secret and their recovery codes once (AUTH-055, AUTH-056, AUTH-063) | A token until its session ends or stops lasting (AUTH-047), a code for 10 minutes (AUTH-030, AUTH-036, AUTH-050), a setting's secret until its operator replaces it |
| Personal | What identifies a person directly ([glossary](../architecture.md#11-glossary)): email addresses, names, devices' names, and the client address and user agent of an audit entry | Over TLS (OPS-17); in a URL only as a list's `search` (API-20), which no log line, span or metric holds (PLATFORM-044, OBS-04) | In the database, whose disk or provider encrypts it, and in the encrypted backups (OPS-17); the API encrypts no column of it | Never (OBS-04); an audit entry holds none of it but its client's address and user agent (SEC-18) | Its user, and the members whom a workspace's permissions let see a member (SEC-08, DATA-16); an audit entry's client only its user and a reader with `audit.read_clients` (AUDIT-010) | Until its user changes it or deletes their account, whose erasure and export every module's contract covers (DATA-23); an audit entry for `AUDIT_RETENTION_DAYS` (AUDIT-011); a backup for `BACKUP_RETENTION_DAYS` ([backups.md](backups.md#what-is-backed-up)) |
| Workspace | What a workspace's members share: its name, its members and their roles, its audit log and its events; and the IDs of users and workspaces, which are pseudonymous | Over TLS (OPS-17) | As the personal level's | Its IDs alone (OBS-04) | Its members, each by their role's permissions (SEC-08, SEC-09, SEC-19, DATA-16) | Until a member with the permission deletes it, or the workspace (WORKSPACES-017); an event for 24 hours (PLATFORM-019); a backup as above |
| Operational | The logs, traces and metrics, which hold nothing of the levels above but IDs (OBS-04) | Over TLS where it leaves the server (OPS-17) | On the server's disk, or at a managed backend ([observability.md](observability.md#how-telemetry-flows)) | It is the telemetry | Grafana's viewers, who each sign in (SEC-14) | Metrics for 15 days, logs and traces for 14 ([observability.md](observability.md#how-telemetry-flows)) |
| Public | What anyone may read: the capabilities, the probes' answers, and the API's own document, `openapi.json` | Over TLS (OPS-17) | In the code | Freely | Anyone | With the release |

A file's name is of the personal level, as are the bytes of an avatar and of a user's own file; a workspace's files and its picture are of the workspace level, in the files bucket, whose provider encrypts them and is trusted with them (D106); and a public file's bytes, an avatar's and a picture's are public to whoever holds their address ([files spec](../spec/files.md#visibility)). <!-- part: files -->
What a user's clients report of themselves is of the operational level once the collector has kept of it only what its configuration lists (CLIENT_TELEMETRY-011, CLIENT_TELEMETRY-015), and only for a user who consents (CLIENT_TELEMETRY-005). <!-- part: client_telemetry -->

The integrity of what the levels hold rests on the database, whose constraints and transactions the data rules state (DATA-04, DATA-05, DATA-20), on the authentication of each encrypted secret (PLATFORM-087), on an audit log that the API's own role can only add to (AUDIT-005), and on backups that restore the database to any moment of their retention (OPS-15).

## Trust boundaries

| Boundary | What crosses it | What guards it |
|---|---|---|
| The internet to Caddy | Every client's requests, and Grafana's viewers | HTTPS (OPS-17); only the API and a Grafana that signs viewers in are exposed (SEC-14); security headers (SEC-12) |
| Caddy to the replicas | The requests, with the client's address in `X-Forwarded-For` | The client IP is read only from a configured trusted proxy (SEC-13, PLATFORM-053) |
| A client to the API | Credentials, tokens, and every request's input | Authentication (SEC-06, SEC-07, API-14), authorization (SEC-08, SEC-09), strict input (API-08, API-09, API-10), rate limits (SEC-13) and load shedding (OPS-07) |
| The API to Postgres | Every query, as the role `app` | Two roles, the API's with least privilege (DATA-12, DATA-13, DATA-19); queries checked at compile time (DATA-14); every query filters by tenant (DATA-16) |
| The API to other systems | Email, and the exchanges of OAuth providers' codes, whose answers name a user | One of two outbound clients (SEC-10); TLS that verifies the certificate (OPS-17); no provider's token kept (AUTH-079, D139) |
| The API to the address of a provider's picture | A request to an address that a third party gives, and the bytes it answers | The untrusted client: HTTPS alone, to the hosts alone that the providers name for their users' pictures (AUTH-097), at public addresses alone, each redirect checked alike, with no credential, capped in size and time (SEC-10); the bytes are checked and scanned as an upload's, in a job, outside any request (ACCOUNTS-028) <!-- part: files --> |
| The replicas to the files bucket | Files' bytes, written, read and deleted by keys that name no row | The object storage adapter's client, with its endpoint from configuration (SEC-10); TLS that verifies the certificate (OPS-17); a key pair that reaches only that bucket ([the files bucket](deploy.md#the-files-bucket)) <!-- part: files --> |
| The replicas to the scanner | Each upload's bytes, before they are stored | The deployment's private network, which only the replicas and the scanner join, since clamd speaks no TLS (PLATFORM-079, OPS-17); the scanner runs as its image's own user on a read-only root, keeping what it scans in memory ([the scanner](deploy.md#the-scanner)) <!-- part: files --> |
| The scanner to ClamAV's mirrors | The signatures, downloaded | HTTPS that verifies the certificate (OPS-17), and ClamAV's own signature of each database, which freshclam checks before it keeps it ([the scanner](deploy.md#the-scanner)) <!-- part: files --> |
| Postgres to the bucket | The write-ahead log and the base backups | Encrypted before they leave the server (OPS-17); a key pair that reaches only the bucket ([the bucket](backups.md#the-bucket)) |
| The collector to an observability backend | Logs, traces and metrics | No personal data or secret in telemetry (OBS-04); TLS (OPS-17) |
| The collector and Grafana to the self-hosted stack's stores and Alertmanager | Logs, traces and metrics, written and read, and the alerts' silences | A private network that only they join: Prometheus, Loki, Tempo and Alertmanager ask no credential, so the replicas, the proxy and the one-shot subcommands reach none of them (SEC-14); Grafana signs each viewer in (SEC-14) |
| The replicas to the collector's receiver of clients' batches | Each batch of telemetry that the client of a user who consents sends the API, which the API doesn't parse | The deployment's private network: the receiver's port is published nowhere (SEC-14); the relay sends the batch and its media type alone, none of the caller's credentials (PLATFORM-091); the collector keeps the telemetry of the services it lists alone, of the resource of a span or of a log record only what names the client, its version and, on spans, its installation, and of the metrics what it lists (CLIENT_TELEMETRY-011, CLIENT_TELEMETRY-012, CLIENT_TELEMETRY-015) <!-- part: client_telemetry --> |
| CI to the registry to the server | The images, and the deploy's tools | Everything pinned (OPS-11); one build whose digest is tested, signed and promoted (OPS-12); advisories block the build (SEC-15); a minimal, unprivileged image (OPS-13) |
| The operator to the server | Deploys, backups, restores, settings, and the removal of a user's lost second factor (AUTH-072, D135) | Secure Shell (SSH) from the developer's machine (OPS-19); secrets in files, one per secret ([the files on the server](deploy.md#the-files-on-the-server)), held so that nothing prints them (SEC-01) |

## Threats

### Authentication and sessions

| Threat | What stops it |
|---|---|
| Guessing one account's password online | The sign-in limits ([below](#sign-in-limits)), and a slow hash (SEC-04, AUTH-014) |
| Credential stuffing: one guess each at many accounts, from leaked lists | The IP limit (SEC-13, PLATFORM-054), as [below](#sign-in-limits) says; a password on the breached-password list is refused when set (AUTH-003) |
| Locking an account's owner out by failing their sign-ins | The sign-in limits, and the device tokens of the devices the owner signed in on (AUTH-019, [below](#sign-in-limits)) |
| Learning which emails have accounts | One answer, after the same hashing work, for an unknown email, an account without a password and a wrong password (SEC-05, AUTH-005); a reset answers alike whether or not an account holds the address: its request does the same work, and its check the same hashing work (AUTH-034, AUTH-038); registration's answer is the exception SEC-05 accepts, under the IP limit, and so is a request to change one's address, which needs the password proved just before (AUTH-048) |
| Cracking a stolen password hash | Argon2id at the parameters that the Open Worldwide Application Security Project (OWASP) recommends, rehashed when they rise (SEC-04, AUTH-014) |
| Using a stolen session token | Tokens are random and stored only as hashes (SEC-03, AUTH-007); an access token is short-lived, and every session has an absolute lifetime (SEC-06, AUTH-007); a refresh token works once, and its reuse ends the session (AUTH-012); each proof of who its user is gives the session new tokens, with which a copied pair stops working (AUTH-095); signing out ends it at once, streams included (AUTH-013); its user sees it among their sessions, whose other devices learn when it starts, and ends it from another (AUTH-043, AUTH-044, AUTH-046); and the operator ends every session of an account, or of every account (AUTH-094) |
| A script on a page reading a browser's tokens | Browsers get their tokens only in `HttpOnly` cookies (SEC-07, AUTH-015) |
| Another site's page acting with a browser's cookies | `SameSite=Strict` cookies, and the cross-site check of requests whose method isn't safe (SEC-07, PLATFORM-059); the headers of cross-origin resource sharing (CORS) only for listed origins (PLATFORM-058) |
| A stolen session deleting its user's account, or guessing their password to do so | Deleting the account needs its user proved just before, by the password or a provider (AUTH-023, AUTH-080), and every check of a signed-in user's password counts in one bucket of theirs, whatever checks it (AUTH-022, SEC-13), with each wrong one in the user's log (AUTH-021) |
| Claiming an address one doesn't hold, by registering with it and guessing the code sent to it, which with email on would give the account what the API gives only an address's owner | A code of 6 random digits, stored only as its hash-based message authentication code (HMAC), that lasts 10 minutes and works once (SEC-03, AUTH-030, AUTH-031); 10 checks a day per account, whatever codes it asks for, about one chance in 270 a year (AUTH-033); the API serves an account nothing but proving its address until it has (AUTH-025) |
| Claiming an address one doesn't hold by asking to change an account's address to it, from as many accounts as one makes, and guessing the codes sent to it | A code of 80 random bits, whose HMAC covers the address, that lasts 10 minutes and works once (SEC-03, AUTH-050, AUTH-051), so the number of accounts that ask doesn't matter, as D132 says; each account's checks count in its own bucket (AUTH-033) |
| Flooding an address with codes' emails, or keeping its owner from asking for a code | 3 registrations and 3 requests for a code per 15 minutes per address, each in a bucket of its own, so registrations, which anyone who knows the address may send, never fill the owner's (AUTH-029), 3 requests for a reset per 10 minutes, in a third (AUTH-035), and 3 requests to change an account's address to it per 10 minutes, in a fourth (AUTH-049), beside the IP and user limits |
| Taking an account over through a reset, by guessing the code sent to its address | A code of 80 random bits, stored only as its HMAC, that lasts 10 minutes and works once (SEC-03, AUTH-036, AUTH-037); each check counts per email from its client address, and costs an Argon2id hash (AUTH-038, AUTH-039), as [below](#password-reset) says; a code holds only for the address it was sent to, so one sent before a change of the address resets nothing after it (AUTH-038) |
| Keeping an account's owner from resetting, by failing checks of their email or filling its requests | The checks of an email count per client address alone, a count no other address fills (AUTH-039); each request that fills the address's bucket sends its owner a code of its own, which works for longer than the bucket's window lasts (AUTH-035, AUTH-036, [below](#password-reset)) |
| A stolen session ending its user's other sessions, to keep the owner out | Ending a session other than the request's own needs its user proved just before, as deleting the account does (AUTH-044, AUTH-045, AUTH-023) |
| A stolen session changing its user's password | The current password is required, and each check of it counts in the user's one bucket (AUTH-022, AUTH-040); the address is told, and its owner's reset ends every session (AUTH-041, AUTH-037) |
| A stolen session taking a copy of everything its user keeps | Requesting an export needs the session to have proved who its user is within the last 5 minutes (ACCOUNTS-020, D137), and a user requests one a day (ACCOUNTS-021); its email carries no link, and its download needs a session of the user's (ACCOUNTS-025, ACCOUNTS-026) |
| A stolen session moving its account to an address the thief reads, to take the account through resets | Asking for the change needs its user proved just before (AUTH-048, AUTH-023), whose checks count in the user's one bucket (AUTH-022); the new address must prove itself with the code sent to it (AUTH-051); the address before is told, with the new one named, so its owner signs in with it, or from a device still signed in, changes it back (AUTH-053) |
| Signing in through a provider as another user, by giving the provider an account with their address | A user is identified by the provider and its ID for them, never by an address (AUTH-073); a provider's sign-in never joins an account that holds its address (AUTH-076) |
| Registering with a victim's address before they first sign in through a provider, so that their sign-in joins an account whose password the attacker holds | A provider's sign-in never joins an account that holds its address, and answers 409 (AUTH-076); the owner takes the account through a reset, which ends every session (AUTH-037), with email on |
| Claiming an address through a provider that verified it once, after it changed owner | A provider proves only an address it is the authority for (AUTH-075, D140); any other is a claim, which a code proves with email on (AUTH-025) |
| Signing in to another user's account once the deployment names another provider, which gives one of its users the ID that the first gave them | The subject of a provider that the settings name holds its issuer, so a sign-in under another issuer reaches no account of the first's (AUTH-084) <!-- part: openid_connect --> |
| A provider's code, exchanged by someone other than the client that asked for it, or sent to the other provider | Proof Key for Code Exchange (PKCE) and `state`, which the client makes for each request (the auth spec's Signing in through a provider); a redirect uniform resource identifier (URI) names one provider, and the API exchanges a code only with it (AUTH-078, AUTH-081) |
| Reading providers' tokens from a copy of the database or of a backup | None is kept: each reads the identity once, and one that doesn't lapse is deleted, or refused where the API knows no way of its provider's to delete it (AUTH-079, D139) |
| Signing in with a password alone | Accepted for users who add no authenticator app, with the controls that [Second factors](#second-factors) lists, unless the deployment requires one of every user (AUTH-070, D133) |
| Guessing an authenticator app's code with a stolen password | Each step's code works once, and only two steps' codes work at a time (AUTH-057); each check counts in a bucket of 10 a day, its user's or its device token's, so a guesser with the password finds a code with a chance of about 1 in 140 a year, and keeps no known device of the owner's from completing its sign-in (AUTH-061); each wrong code is recorded in the user's log (AUTH-060, AUTH-065) |
| Reading authenticator apps' codes from a copy of the database or of a backup | Each app's secret is encrypted under a key that the database never holds (SEC-02, AUTH-066); recovery codes are stored only as SHA-256 hashes of their 120 bits (AUTH-062) |
| A stolen session adding a way in of the thief's, a password or their account at a provider, or removing the owner's | Each change of an account's identities needs its user proved just before (AUTH-086 to AUTH-088), and counts in one bucket of the user's (AUTH-090); each tells the address, which tells its owner to reset the password, which ends every session, and to remove the way in they didn't add (AUTH-091, AUTH-037); the account keeps its last identity (AUTH-088) |
| A stolen session, with the password, adding or removing a second factor, or taking new recovery codes | Each needs the password, and the app's code when there is one, proved just before (AUTH-055, AUTH-063, AUTH-064, AUTH-065); each tells the address, which tells its owner what to do (AUTH-068) |
| Getting past a second factor through a reset, or through a challenge issued before the password changed | A reset of an account with an app needs the app's code or a recovery code beside the reset code, so whoever reads the mailbox alone sets no password (AUTH-037, D136); a reset starts no session, so the next sign-in asks for the factor (AUTH-069); a reset, a change of the password and a removal of the app delete the user's sign-in challenges (AUTH-069) |
| Getting past a second factor with the password and the mailbox, as an account recovery would | No route removes a factor; only the operator does, once they have checked who the person is (AUTH-072, D135) |

### Access control

| Threat | What stops it |
|---|---|
| Reading or changing another workspace's data | The workspace is in the path, and the route's permission in its type (API-02, API-14); only `access` authorizes (SEC-08); every query filters by tenant (DATA-16); the permission matrix is tested for every route and role, with IDs from another workspace (TEST-08) |
| A member raising their own role, or acting on a higher one | Role rank limits who may change whom (SEC-09): a member changes only the roles of members below them, to roles below their own (WORKSPACES-013), and the owner's role moves only by the owner's transfer, to an admin (WORKSPACES-015) |
| A stolen session of a workspace's owner deleting the workspace, or handing it to another account | A deletion and a transfer each need the session to have proved who its user is within the last 5 minutes, as deleting the account does (WORKSPACES-018, AUTH-023, D148) |
| Registering with the address of a workspace's owner before the operator sets the workspace up, to own it | With email on, the setup subcommand takes an account that holds the address only when it has proved the address, or has no identity, as one that an earlier run created; with email off, where nothing proves an address, the owner registers first, so whoever holds the address is the one who told the operator so (WORKSPACES-024, WORKSPACES-026, D150) <!-- part: workspace_setup --> |
| A member extending, changing or withdrawing an offer of a role they couldn't make, such as an admin's of the owner's invitation of another admin | An invitation offers its role, so a member invites, invites an address again, changes, sends again and cancels only an invitation at a role below their own, as they act on members (SEC-09, INVITATIONS-014) <!-- part: invitations --> |
| A member whose role was lowered still receiving what the role held | A change of a role closes the member's streams at commit, as a removal does, and each opens again under the new role (WORKSPACES-012, SEC-06) |
| A removed member, or an ended session, still receiving events | Access changes close the affected streams at commit, and a re-check closes what a missed signal left (SEC-06, PLATFORM-031) |
| Events reaching a member who may not see them, or from before they joined | Each event reaches only the streams whose memberships hold its permission, and had committed when it did (SEC-19) |
| A member telling which events another user's request published, or sending requests of their own under its trace | An event's frame carries the trace ID of the request that published it only on the streams of that request's user, so no member reads another's (SEC-19, D201) |
| Making oneself a superadmin, to read across workspaces, or to delete them | No route makes a superadmin: only the subcommand that an operator runs on the deployment's server does, and, with email on, only of an account that has proved its address (SUPERADMINS-001, SUPERADMINS-002); a superadmin's route refuses every other caller, whatever they own, and records it (SUPERADMINS-004) <!-- part: superadmins --> |
| A superadmin's account taken over, through its password alone | A superadmin's routes serve an account only while it has an authenticator app, whatever the deployment requires of its users (SUPERADMINS-005, D63), and show a workspace's name, creation time, member count and owner, never its content (WORKSPACES-029, D62) <!-- part: superadmins --> |
| A superadmin's stolen session deleting workspaces | A superadmin's deletion of a workspace needs the session to have proved who its user is within the last 5 minutes, as an owner's does, and is recorded in the superadmin's own log, which outlasts the workspace (WORKSPACES-030, D148) <!-- part: superadmins --> |
| Forging an audit entry's actor | The actor and scope come from the unit of work's proof, never the request (AUDIT-002) |
| A private file's signed URL leaking, as into a copied link | It reaches one file, for an hour at most, and only while its session lasts and its user may still read the file, whom the download authorizes again (FILES-022, PLATFORM-080); no log or trace of the API or of Caddy holds a URL's query (OBS-04) <!-- part: files --> |
| Learning a public file's name, or finding public files by guessing their IDs | A public download names the file by its ID and its kind's extension alone (SEC-11, FILES-023); a public file's ID, an avatar's or a workspace's picture's, holds 62 random bits, and the bucket of public downloads bounds each IP's guesses (PLATFORM-082, FILES-024, FILES-027) <!-- part: files --> |

### Input and output

| Threat | What stops it |
|---|---|
| SQL injection | Queries are checked at compile time, and the functions that take SQL text are banned (DATA-14) |
| A value that changes the structure of what it is written into: a JSON document, an email, a URL, a header or a task's command | Each value is encoded where it is written, by that format's own writer, and the API starts no process (SEC-20) |
| Malformed, unexpected or oversized input | Strict bodies and query parameters (API-08, API-09), domain types at the boundary (API-10), and body limits (PLATFORM-048, PLATFORM-050) |
| An oversized upload | Its limit, which refuses it by its declared length before anything reads it (PLATFORM-074, FILES-004) <!-- part: files --> |
| A batch of telemetry that inflates far beyond what was sent | The batch's limit, 1,048,576 bytes as sent and once inflated, of which the API inflates no more than one byte past it (PLATFORM-090, CLIENT_TELEMETRY-006) <!-- part: client_telemetry --> |
| A client's telemetry that passes for the API's or Caddy's own, or that names services without end, each a stream of Loki's | The collector drops the telemetry of every service that its configuration doesn't list, reads the first name of a resource that names its service twice, and stores what it keeps under that name alone (CLIENT_TELEMETRY-012, CLIENT_TELEMETRY-015) <!-- part: client_telemetry --> |
| A client's metrics that name series without end, each one more in Prometheus | The collector keeps the metrics that its configuration lists, each with the attributes and the values listed for it, and adds every installation's points into one series for each set of those values (CLIENT_TELEMETRY-014, CLIENT_TELEMETRY-015) <!-- part: client_telemetry --> |
| A client that reports numbers of its own making in its metrics | The clients' series inform, on a dashboard of their own, and no alert reads them (OBS-14) <!-- part: client_telemetry --> |
| An uploaded file that runs in a browser | Only kinds whose bytes a check reads are accepted, never Scalable Vector Graphics (SVG) or HTML (FILES-003), and each is served so that it can't run (SEC-11, FILES-009) <!-- part: files --> |
| An uploaded file that carries malware | Every upload is scanned before it is stored, and refused when the scanner names a signature, or when its contents pass what the scanner scans whole, such as a decompression bomb (FILES-005); signatures that age past 2 days raise ScannerSignaturesOutdated ([runbooks](runbooks.md#scannersignaturesoutdated)) <!-- part: files --> |
| An image crafted for a flaw in a viewer's decoder | Stored as it came, never decoded on the server; left to the scanner's signatures of known exploits and the viewer's own updates ([files spec](../spec/files.md#accepted-kinds)) <!-- part: files --> |
| A public file that serves others content from the API's address, such as a phishing document | Only the accepted kinds, each scanned, never HTML or SVG (FILES-003, FILES-005), served sandboxed, with every kind but images as an attachment (SEC-11); a workspace's owner and admins delete what a member published (FILES-010), and shared caches drop it within 5 minutes (FILES-023) <!-- part: files --> |
| Errors that leak internals | Internal errors expose nothing, and `detail` never carries internals (ERR-08, ERR-09) |
| Framing, sniffing and caching of responses | Security headers on every response (SEC-12) |
| Server-side request forgery | Outbound requests go through one of two clients, the one that reaches addresses a user gives refusing private ones (SEC-10) |

### Data protection

| Threat | What stops it |
|---|---|
| Secrets leaking through settings, logs or debug output | Secrets arrive by environment or file, and stay wrapped (SEC-01); telemetry holds no secret (OBS-04) |
| A database dump giving away secrets | Secrets at rest are encrypted with associated data (SEC-02); tokens and codes are stored as hashes (SEC-03) |
| Personal data in telemetry, audit details or rate-limit keys | No personal data in telemetry (OBS-04); audit entries hold only IP address and user agent (SEC-18); bucket keys are HMACs (PLATFORM-057) |
| A client sending what its user didn't agree to send, or more than they know | The telemetry proxy forwards nothing of a user who doesn't consent (CLIENT_TELEMETRY-005), and the collector keeps of the resource of a span or of a log record only what names the client, its version and, on spans, its installation (CLIENT_TELEMETRY-011), and of the metrics the client's name and what its configuration lists (CLIENT_TELEMETRY-015); what a client's spans and log records hold besides is the client's to keep free of personal data (OBS-04) <!-- part: client_telemetry --> |
| Data read in transit, or from a stolen disk | TLS for every connection that leaves the server, and encryption at rest (OPS-17) |
| The bucket's provider reading the backups | They are encrypted before they leave the server (OPS-17) |
| The files bucket's provider reading the files | Nothing in the API: the provider encrypts them at rest with keys of its own (OPS-17), and is trusted with their bytes, as a managed database's provider is with its data (D106) <!-- part: files --> |
| A bucket keeping what the deployment deleted, such as an expired backup, as a noncurrent version | Every bucket of the deployment has versioning off, or expires each noncurrent version a day after it becomes one, which `just server-check` checks ([deploy.md](deploy.md#what-a-server-needs), D102) |
| Losing data, or a change that shouldn't have happened | Continuous backups, restores to any moment the retention covers, and a restore that another undoes (OPS-15) |

## Sign-in limits

Requirement 6.1.1 of ASVS asks how the controls defend against credential stuffing and password guessing, how they are configured, and how they keep an attacker from locking an account's owner out. A password sign-in passes the IP limit, then the sign-in limits, which count every attempt before the account is read (SEC-13, AUTH-006). `.env.example` gives each setting below its range and its default:

- **The IP limit** of each client address (PLATFORM-054): `RATE_LIMIT_IP_REQUESTS` requests in each `RATE_LIMIT_WINDOW_SECONDS`.
  Public downloads, of files, avatars and workspaces' pictures, count apart (PLATFORM-082). <!-- part: files -->
- **The email from one address** (AUTH-006): `SIGN_IN_ATTEMPTS` attempts at one email from one client address in each `SIGN_IN_WINDOW_SECONDS`.
- **The email from every address** (AUTH-006): `SIGN_IN_EMAIL_ATTEMPTS` attempts at one email in the same window, which counts only what the limit of the email from one address lets through.
- **A device token** (AUTH-019): a sign-in that brings one valid for its email counts only in that token's own limit, `SIGN_IN_ATTEMPTS` in each window, and in neither of the two above (AUTH-006).

**Guessing.** An attacker at one address gets `SIGN_IN_ATTEMPTS` guesses at an account in each window. Spread over many addresses, they get at most `SIGN_IN_EMAIL_ATTEMPTS`, each costing an Argon2id hash (AUTH-014), against a password that can't be on the breached-password list (AUTH-003). A device token opens no more: one is valid for one email, so a token from the attacker's own account opens nothing of another's, and a stolen one gives its thief that token's own limit, until the owner's next sign-in on the device ends it.

**Credential stuffing.** One guess at each of many accounts passes the per-email limits, so the IP limit bounds it: an address that keeps trying is refused once it has sent its requests of the window, and a botnet's addresses are each bounded so.

**Lockout.** The two counts of an email alone can't prevent it. An attacker at one address fills only that address's count, but filling the email's shared count takes no more addresses for many accounts than for one: each address is bounded by the IP limit alone, whose window holds attempts at many accounts, so a few addresses can keep the shared counts of many accounts full, window after window. So a device that has signed in to the account before brings its device token, whose own count no attempt from elsewhere fills: the owner signs in on each device that signed in within `DEVICE_TOKEN_SECONDS` and kept its token, whatever an attack does to the email's counts, as OWASP's "device cookies" do. A browser keeps one token for each account it signs in to (AUTH-015). A session the owner already holds goes on refreshing meanwhile (AUTH-010), which no sign-in limit counts. A 429 says how long to wait (API-15).

**What remains.** An attacker with enough addresses can keep the accounts they target refusing password sign-ins from every device that holds no valid token for them: a new device, or one whose token expired, waits for a window that the attack leaves, while the owner's known devices sign in as before. The API asks no challenge that tells a person from a program, such as a CAPTCHA (Completely Automated Public Turing test to tell Computers and Humans Apart), which a client that isn't a browser can't show; a product that needs more can lower the limits, or add a second factor, which every user may (D63). And each attempt the limits let through costs the replica an Argon2id hash, so an attack on many accounts at once costs processor time, which the concurrency limit and the timeouts bound (OPS-07), at the cost of refusing other requests while it lasts.

## Password reset

A reset is the other way in with a password, so requirement 6.1.1 of ASVS asks of it what it asks of a sign-in. Its limits are fixed, beside the IP limit (PLATFORM-054): 3 requests per 10 minutes to an address (AUTH-035), and 5 checks per 15 minutes of an email from one client address (AUTH-039).

**Guessing.** A reset code has 80 random bits and lasts 10 minutes (AUTH-036), and each check that the limits let through costs an Argon2id hash (AUTH-038), so the replicas' processors bound how many codes an attacker tries, from however many addresses: 10,000 a second, all at one account, for a year, have about one chance in 10^12 of finding one of the few codes it holds at once, 3 for its requests of a window. A guess at one account is no guess at another, since a code's HMAC covers its account (SEC-03).

**Lockout.** The checks of an email count per client address alone: an attacker who fails confirmations fills the counts of their own addresses, never the owner's. An attacker who asks for resets fills the address's bucket, which every client address shares, but cancels no code of the owner's, since each request's code is its own (AUTH-036), and each of theirs sends the owner a code too, which lasts 10 minutes, at least as long as the bucket's window: while the bucket is full, a code it let through in that window still works, so an owner whose request the bucket refuses finds a working code in their inbox. A user who shares a client address with an attacker, such as behind one carrier's network address translation, shares their count of checks, as with the sign-in limits.

**The second factor.** An account with an authenticator app resets only with the app's code, or a recovery code, beside the reset code (AUTH-037, D136), so a reset gives whoever reads the mailbox no way past the factor, nor a password that keeps the owner out. The confirmation checks the factor only once its reset code matched, and counts it in the bucket of the user's completions of a sign-in (AUTH-061), so only someone who reads the mailbox fills that bucket, and a code that matches nothing counts in none.

**What remains.** Each request sends the address an email its owner didn't ask for, up to 3 in 10 minutes, which says that ignoring it changes nothing. Each check costs a replica an Argon2id hash, which the concurrency limit and the timeouts bound, as they bound a sign-in's (OPS-07).

## Second factors

Requirement 6.3.3 of ASVS asks every user to sign in with more than one factor, and asks an application that relaxes it for a documented rationale and a comprehensive set of mitigating controls.

**The rationale.** The template is the start of products whose users must be able to sign in without setting a factor up: requiring one of every user would turn away the products for which a password, or a provider's sign-in, is the expected bar. So every user may add an authenticator app, with recovery codes (D134).
Every superadmin, who acts across workspaces, must have one (SUPERADMINS-005, D63). <!-- part: superadmins -->
A deployment whose product needs the requirement in full turns `SECOND_FACTOR_REQUIRED` on, which requires an app of every user (D133).

**The mitigating controls,** each in its home:

- Passwords: of a length that AUTH-003 bounds, refused when breached or guessable (AUTH-003), hashed with Argon2id (SEC-04, AUTH-014).
- Guessing and lockout: the [sign-in limits](#sign-in-limits) and those of a [password reset](#password-reset), and failures that reveal nothing (SEC-05, AUTH-005, AUTH-038).
- Sessions: random tokens stored as hashes (SEC-03), bounded lifetimes (SEC-06, AUTH-007), a refresh token that works once and whose reuse ends the session (AUTH-012), new tokens at each proof of who the user is (AUTH-095), signing out that ends it at once (AUTH-013), a sign-in that ends the session its device or its browser held (AUTH-008, AUTH-096), a user's list of their sessions, any other of which they end once they prove their password again (AUTH-043 to AUTH-045), and browsers' tokens in cookies no script reads (SEC-07, AUTH-015).
- Detection: each failed sign-in of an existing account is recorded in its audit log (AUTH-005), with the client's address and user agent (AUDIT-003), as is the reuse of a refresh token (AUTH-012).
- Access: lost access ends open streams (SEC-06), and authorization is checked on every workspace request (SEC-08).
- A second factor for whoever wants one: an authenticator app, which a sign-in, a reset, a re-authentication and a change of the password then ask for (AUTH-058, AUTH-037, AUTH-065), with its secret encrypted at rest (AUTH-066).

## Session lifetimes

Requirement 7.1.1 of ASVS asks that the lifetimes of a session be documented, that they fit the other controls, and that the reasons be given where they depart from Special Publication 800-63B of the National Institute of Standards and Technology (NIST). Its fourth revision recommends that a session which one factor started be authenticated again within 30 days, and one which two factors started within 24 hours, and after an hour without activity (its sections 2.1.3 and 2.2.3).

**The lifetimes.** A session of the API ends 30 days after its last refresh, `REFRESH_TOKEN_SECONDS`, and 90 days after it started, `SESSION_LIFETIME_SECONDS`, whichever comes first, and its access token lasts an hour, `ACCESS_TOKEN_SECONDS` (AUTH-007, AUTH-010, AUTH-011). A viewer's session of Grafana's ends after 7 days without a request, and after 30 days (SEC-14), which is what the publication recommends of one factor.

**The departure.** The API's defaults are longer than the publication recommends: 90 days where it recommends 30, for a session that a password or a provider's sign-in started, and where it recommends 24 hours, with an hour without activity, for one that an authenticator app's code completed.

**The reasons.** The template's clients are applications that their users leave signed in, on devices of their own, and a session that ended each day, or after each hour away, would send those users through a sign-in far more often than such products do. The publication's limits are recommendations, there to confirm that the user is still present, and the API confirms it where it matters instead of by the clock:

- A change of what the account rests on, the end of another session and the deletion of the account each need their user proved within the last 5 minutes, with the second factor of an account that has one ([re-authentication](../spec/auth.md#re-authentication), AUTH-021, AUTH-065).
- A refresh gives a session new tokens, with which the old ones stop working (AUTH-010), as each proof of who its user is does (AUTH-095), and a refresh token that is used a second time ends the session (AUTH-012), so a copied token works until its owner's client next refreshes, which a client in use does within the hour, when its access token ends.
- A user sees their sessions, and ends any other once they prove who they are again (AUTH-043 to AUTH-045), and signing out ends a session at once (AUTH-013).
- A product that needs the publication's limits sets them: `SESSION_LIFETIME_SECONDS` to 86,400, and `REFRESH_TOKEN_SECONDS` to 3,600, with which a session ends an hour after its last refresh.

| The key of the keyed hashes, `HMAC_KEY` | The first deploy: 32 random bytes | `secrets/hmac_key` | With HMAC-SHA-256: the stored hash of each code that an email carries, and of a device token's email, the keys of the rate limits' buckets, and the name of the cookie that holds a browser's device token (SEC-03, AUTH-019, PLATFORM-057, AUTH-015) | By `just replace-key` and a deploy, which ends what the old key made ([the keys that a deploy generates](deploy.md#the-keys-that-a-deploy-generates)) |
| The backups' passphrase | `just server-setup`: 24 random bytes, unless its operator types one | `secrets/backup_cipher_pass`, and its operator's copy off the server | The backups, which pgBackRest encrypts under it ([what is backed up](backups.md#what-is-backed-up)) | No task replaces it |
| The bundled database's passwords | `just server-setup`, the superuser's, unless its operator types one, and the first deploy, those of the roles `owner` and `app`: 24 random bytes each | `secrets/postgres_password`, and the three URLs, `secrets/database_admin_url`, `secrets/database_owner_url` and `secrets/database_url`; Postgres stores of each a verifier of the Salted Challenge Response Authentication Mechanism (SCRAM), with SHA-256 and 4,096 iterations (SEC-16) | Each role's connections (DATA-12) | `bootstrap` sets the passwords of `owner` and `app` from their URLs at each deploy (PLATFORM-002); no task writes new ones, or changes the superuser's |
| Caddy's keys | Caddy: a key on the curve P-256 for each certificate, and the key of its account at Let's Encrypt | The volume `caddy-data` | The TLS of the API's address and of Grafana's, under certificates that Let's Encrypt issues (OPS-17, [TLS and proxies](deploy.md#tls-and-proxies)) | Caddy renews each certificate on its own; no task replaces a key |
| Grafana's key | The first deploy that runs Grafana: 24 random bytes | `secrets/grafana_secret_key` | The hashes of Grafana's sessions' tokens, and what Grafana stores encrypted (SEC-14) | By `just replace-key` and a deploy, which ends its viewers' sessions ([the keys that a deploy generates](deploy.md#the-keys-that-a-deploy-generates)) |
| The password of Grafana's administrator | Its operator, at `just server-setup` | `secrets/grafana_admin_password`, which Grafana reads the first time it starts | The administrator's sign-in (SEC-14) | In Grafana ([Grafana](deploy.md#grafana)) |
| The credentials that other systems issue: the key pair of the backups' bucket, a managed database's URLs, the mail server's password, the OAuth providers' client secrets, a managed backend's tokens, the alert integrations' credentials, and the registry's token | Each system | `secrets/`, and the registry's token in Docker's configuration of the deployment's user | The deployment's access to each system | At the system; then `just server-setup` writes the new one, and the next deploy applies it ([setting up a server](deploy.md#setting-up-a-server)) |
| The key pair of the files bucket | Its provider | `secrets/files_s3_key` and `secrets/files_s3_key_secret` | The replicas' access to the bucket ([the files bucket](deploy.md#the-files-bucket)) | As another system's credential is <!-- part: files --> |
| The key of a release's signature | cosign, in the run on `main` that releases: a key on the curve P-256, for that one signature | Nowhere: its certificate and the signature are in Sigstore's log, and beside the image in its registry | That a release's images are the ones the run built and tested (OPS-12, [signing](release.md#signing)) | None is kept to replace |
| The operator's SSH key | Its operator | Their machine, and its public half among the keys that the server's SSH admits | Every task's way to the server (OPS-19) | By its operator |

The certificates are those that Let's Encrypt issues Caddy, above, and those of the private authorities that a deployment trusts, which hold no key: `just server-setup` writes each into `certs/` ([the files on the server](deploy.md#the-files-on-the-server)).

**The algorithms.**

| Use | Algorithm | Stated in |
|---|---|---|
| The secrets that the database holds | AES-256-GCM, with a nonce of 96 random bits, bound to the secret's row | SEC-02, PLATFORM-087 |
| The tokens of sessions, of devices and of sign-in challenges, and recovery codes, as the database stores them | SHA-256 | SEC-03, AUTH-007, AUTH-019, AUTH-058, AUTH-062 |
| The codes that emails carry, as the database stores them, a device token's email, and the rate limits' bucket keys | HMAC-SHA-256 under `HMAC_KEY` | SEC-03, PLATFORM-057 |
| Passwords | Argon2id | SEC-04, AUTH-014 |
| An authenticator app's codes | HMAC-SHA-1, as RFC 6238 computes them, under a secret of 160 random bits | SEC-16, AUTH-055, AUTH-057 |
| The tokens, the codes and the nonces that the API makes | The operating system's secure random source | SEC-03, PLATFORM-087 |
| TLS where the API is the client | TLS 1.2 and 1.3, with the cipher suites and the certificates' signatures that SEC-16 names | SEC-16, OPS-17 |
| TLS at the proxy | TLS 1.2 and 1.3, with the cipher suites that the Caddyfile names for 1.2 | OPS-17 |
| A role's sign-in to the bundled database | SCRAM, with SHA-256 | SEC-16, PLATFORM-002 |
| The backups | AES-256 in cipher block chaining (CBC) mode, with no message authentication code, under keys that one round of SHA-1 derives, each from a passphrase and a salt | [What is backed up](backups.md#what-is-backed-up) |
| A release's signature | The Elliptic Curve Digital Signature Algorithm (ECDSA), on the curve P-256 | [Signing](release.md#signing) |
| The digests that pin an image, and that name a release's | SHA-256 | OPS-11, OPS-12 |
| What names a thing and authenticates nothing: an idempotency record's fingerprint, the tag of a cursor's route, and the fingerprint of the secret files that a deploy gives a service | SHA-256, of which the tag and the fingerprint keep the first bytes | PLATFORM-036, [lists](../spec/platform.md#lists), [setting up a server](deploy.md#setting-up-a-server) |
| A private file's signed URL | HMAC-SHA-256 under `HMAC_KEY` | PLATFORM-080 <!-- part: files --> |
| The requests to the files bucket | Signature Version 4 of Amazon Web Services (AWS), an HMAC-SHA-256 under a key that the key pair's secret derives, in each request's URL | SEC-16, PLATFORM-094 <!-- part: files --> |
| A file's checksum, which tells a copy that changed by accident, and protects against no one | CRC-32 (cyclic redundancy check) | FILES-025 <!-- part: files --> |
