# CI

CI runs on GitHub Actions, in workflows that only orchestrate `just` tasks (OPS-12). Every action, image, runner and tool they use is pinned (OPS-13).

## The pipeline

`ci.yml` runs on every pull request and on every push to `main`. Its jobs:

| Job | Runs | Needs |
|---|---|---|
| `checks` | `just setup`, then `just checks`: every check of the code in the table below that doesn't need the image | |
| `image` | `just image`: the API's image and the reference deployment's Postgres, each built once for linux/amd64 and linux/arm64 with its software bill of materials (SBOM) and its provenance, into an image layout of the Open Container Initiative (OCI), which the later jobs download (OPS-14) | |
| `scan` | `just image-scan`, against the digests that `image` built, on a runner of its own, so the scanner's database takes none of `verify`'s disk | `image` |
| `verify` | `just e2e` against the digests that `image` built, as four jobs side by side, two for each platform, which each names in `E2E_PLATFORM`, each on a runner of its platform: `verify (linux/amd64, backups)` and `verify (linux/arm64, backups)` run the tests whose names hold `backups::`, and `verify (linux/amd64, others)` and `verify (linux/arm64, others)` every other test, so each test runs in exactly one job of each platform, and a platform's tests take about the time of its longer half. Each first deletes its runner's preinstalled toolchains that no task uses, for their disk | `image` |
| `publish` | On `main` only: `just publish`, which pushes those digests to the GitHub Container Registry as `sha-<commit>`, and moves `edge` to them while the commit is the head of `main` | `checks`, `scan`, `verify` |
| `release` | On `main` only: `just release-image`, which releases from those digests the version that `just release` asked for, if no release has it yet, as [release.md](release.md) describes | `publish` |

A newer push to a pull request cancels the older run. On `main`, a run that has started finishes, and the registry takes one write at a time, so `edge` never moves to an older commit. While a run on `main` goes on, a newer push replaces a run that is still waiting, so a commit pushed in between gets no run, and no image, of its own; the newer run builds a commit that holds it. BuildKit's cache of the build tools and the compiled dependencies is kept between runs, keyed by the files that change them, and the build writes it back only when the key missed.

`scheduled.yml` runs every day at 05:17 UTC, every Monday at 04:43 UTC, and on demand:
- Every day, `just deny`, so an advisory published against a locked dependency fails CI without waiting for a push (SEC-13).
- Every Monday, `just image-rescan`, which scans `edge`, the newest final release and the newest prerelease of each image again (SEC-13).
- Every Monday, the registry's upkeep, in both images' packages: it deletes the tags older than [release.md](release.md#where-it-is-published) keeps them, then the images left with no tag, and the signatures of images that are gone. A pinned action does it, and keeps each platform's image of an index it keeps. If GitHub refuses the deletions, the package's settings grant the repository the Admin role under "Manage Actions access".

`just setup` writes `.env` with generated passwords, and the tests start Postgres through Compose with them, as they do on a developer's machine (TEST-11). A job that only runs the tools Compose holds runs `just env` instead, which writes `.env` alone, because Compose reads it.

On a developer's machine, `just ci` runs what CI runs: `just checks`, `just image`, `just image-scan`, and `just e2e` on the machine's platform.

`check-test-map`, `check-docs`, `check-openapi`, `check-instrument`, `check-metrics`, `check-telemetry-config`, `check-pins`, `check-shell`, `check-sql-bans`, `check-layers`, `check-deps`, `check-schema` and `check-tenancy` are subcommands of the `xtask` crate (ARCH-01). `alert-rules` runs the `xtask` subcommand of the same name, then promtool, from the Prometheus image that `deploy/observability/compose.yaml` pins, through Docker Compose. `check-shell` runs shellcheck from the image that `compose.yaml` pins, through Docker Compose. `just` lists only the recipes of the platform it runs on, so `check-shell` reads the justfile itself, and checks the same recipes on every platform: it writes each one as a script whose lines stand on the justfile's line numbers, so a finding names the justfile's line. `check-test-map` prints how many of each module's behaviors a test proves. A behavior that no test proves fails it once `docs/MIGRATION.md` is deleted, and is reported until then (DOC-10).

`check-openapi` covers the parts of the rules that name it whose subjects exist. An operation with `workspace` access is under `/v1/workspaces/{workspace_id}`, which names the workspace nowhere else, no header names one, and an operation under `/v1/users/me` isn't public (API-02). A method is one that API-03 lists: `GET` and `DELETE` take no body, `PATCH` takes `application/merge-patch+json`, `PUT` takes a body, and a `POST` doesn't end at an item's ID (API-03). The success statuses are those of API-04's table that the method's outcomes allow: a 201 with a `Location` header and a body, a 200 with a body, and a 204 without one (API-04). An ID is a property or a parameter named `id` or `<name>_id`, and a timestamp a property named `<event>_at`, as DATA-01 names their columns; a trace ID, which API-11 names, and a device ID, which its client chooses ([auth spec](../spec/auth.md#device-ids)), aren't UUIDs. A closed set is a string `enum` other than a problem's codes, and a string of a request body is bounded by its `maxLength`, or by its closed set (API-11, API-17). A success body that holds `items` is a list, which holds exactly `items`, an array, and `next_cursor`, a string or `null`, both required, of an operation that takes `limit` and `cursor`; an operation that takes `cursor` answers a list; and no success body is a bare array (API-05, API-06). It checks the breaking-change diff (API-18, ERR-02) from the first release on. Tests, not this check, compare the committed document with the one the code writes, every documented path's methods with the ones it serves, and each request and response of an integration test with the document (API-17).

`check-docs` doesn't cover two of the rules that name it: the names of other codebases (DOC-04), and accepted architecture decision records (ADRs), whose check waits for the first ADR (DOC-11). Review enforces both until then.

`image-scan` and `image-rescan` run Grype, which reads the packages of each image's base, the crates that cargo-auditable records in the API's binary, and the modules that the Go binaries of the Postgres image record. `e2e` pushes both image layouts to the registry that Compose runs on 127.0.0.1:5001, and the tests run the images from there by the digest of their platform's image, against the Postgres that `just services` starts. The tests of the reference deployment deploy to a server of their own: Docker in a privileged container, from the image that `compose.yaml` pins as `server`, joined to Compose's network, where it pulls the API's and the deployment's Postgres from that registry, and reaches a Postgres server of its own as the deployment's managed database: another server of Compose's Postgres, as a provider's would be, since `bootstrap` changes the roles, which every database on a server shares ([platform spec](../spec/platform.md#database-roles)), so deployments that shared one would have to take turns. It pulls every other image, all of them Docker Hub's, through `mirror`, a cache of Docker Hub that Compose runs, and can't reach Docker Hub itself. Before the tests run, `just e2e` fetches every image they pull: the server's and the stack's on this machine, and, through `mirror`, the ones that `deploy/compose.yaml`, `deploy/observability/compose.yaml`, the import into a managed Grafana and the stand-in bucket name, for this machine's platform, so no test reaches a registry outside (TEST-07). `mirror` keeps what it fetched between runs. Each test runs `deploy/deploy.sh` there, as `just deploy` does on a real server, and sends its requests to Caddy through the ports the server publishes on 127.0.0.1. A server's store holds the images it pulls, and goes with the server when its test ends. A server that runs the self-hosted stack holds 3.4 gigabytes of them, so those tests run one at a time, which bounds the disk the suite takes. Even so, the suite, its build and its tools need more disk than a runner has free, so `verify` first deletes the toolchains it has no use for. They compile only with the `e2e` feature of the `app` crate, which `just e2e` and `just lint` turn on, so `just test` needs no image. `E2E_PLATFORM=linux/arm64 just e2e` runs the arm64 image on a machine that can run its binaries: an arm64 machine, as CI's arm64 runner is, or another through QEMU, which Docker Desktop provides, and `docker compose run --rm binfmt --install arm64` installs on Linux. The suite runs as many tests at once as the machine has processors: GitHub's runners have two for a private repository, and four for a public one. The tests start in the order of their names, in which most of the tests that run the self-hosted stack come last, so their turns set how long the suite takes on a machine that runs many tests at once, and on CI how long the job that runs them takes. Through QEMU, the images' programs take many times the processor time they take natively, so the suite waits on the machine's processors more than on its servers: a program the servers run often, such as a health check, costs every test its time under QEMU. `publish`, `release-image` and `image-rescan` sign in to the registry with the runner's credentials, so they run only in CI. `verify-release` needs a checkout, `just env` and a sign-in to the registry, so anyone who can pull the images can run it, on Linux or macOS. It runs `deploy/verify-release.sh`, which a server can run without a checkout.

Builds check queries against the query cache committed in `.sqlx/` (DATA-20), so a query missing from the cache fails `lint` and `test`. `just prepare` rewrites the cache from the migrated database.

`check-sql-bans` reads the sources of the sqlx that the workspace depends on, where `cargo metadata` finds them, with the features it resolves for the workspace with every feature, as clippy builds it; an item that those features leave out doesn't count. sqlx exposes what a path from its root reaches through public modules and re-exports, those of `sqlx-core` and `sqlx-postgres` among them, and the public methods of the types and traits such a path reaches. A function takes SQL text through a parameter typed with sqlx's SQL types: `SqlStr`, `AssertSqlSafe`, or a bound of `SqlSafeStr` or `Execute`. It also takes SQL text through a text parameter that sqlx names `sql`, `query`, `statement`, `init` or `separator`, when the function has a receiver, or another parameter or a result of a sqlx type, to keep the text in or run it with. The SQL types' own functions only make or read SQL values. A macro takes SQL text outside the checked macros when its body passes `checked = false` to the macro that expands queries, as the `_unchecked` macros do, or names such a function. The check resolves each ban as clippy does, and fails on a ban of a sqlx crate that reaches nothing, which clippy only warns about, and `-D warnings` doesn't make an error.

`check-layers` and `check-deps` read the Rust of `platform` and `app` as token streams, so they find a path inside a macro or an attribute too, and follow each file's `use` declarations to what they import. A module's routes are its `routes.rs` or the files of its `routes/`, and its service likewise. An HTTP type is a path into a crate of HTTP, such as `axum`, `http` or `tower`, into `platform::http`, to `platform::errors::Problem`, or into the module's own routes. An error of a library that reaches another system is a type of such a library, such as `sqlx` or `reqwest`, whose name ends in `Error`, or its `Result`. An HTTP client is a path into a library whose job is HTTP requests, such as `reqwest`, or a TCP stream, which only the health probe in `platform::lifecycle` opens. `check-deps` reads the graph from the Mermaid block of [architecture.md](../architecture.md#dependencies). A module's error types are the names its `mod.rs` re-exports from its `error.rs`, and its public signatures are those of its `pub` functions, with the fields its `pub` types expose.

`check-tenancy` reads the migrations' `CREATE TABLE` and `ALTER TABLE ... ADD COLUMN` statements as text, and the SQL of each macro as its words outside quoted strings: a query names its tenant when the column is compared with `=` after its `WHERE`, or is among the columns its `INSERT` writes. It prints how many tables it placed and how many queries of workspace data it checked.

`check-schema` reads a database's catalog rather than the migrations' SQL, so it checks what Postgres made of them, with the privileges the roles get. It creates a database of its own on the Postgres that `just services` starts, runs the API binary's `bootstrap` and `migrate` on it with the URLs in `.env`, as an operator runs them, reads the catalog with psql in Postgres's container, and drops the database. A finding names the last migration that mentions its object. A table's rows are edited when `app` may update them, `platform`'s bookkeeping tables are those that [architecture.md](../architecture.md#what-each-module-owns) gives `platform`, and a check constraint's name holds some of the columns it reads.

A `ci:` check that a rule names but that isn't listed in the table above doesn't exist yet. Until it is built, the rule is enforced by review. A check is built when the code it checks exists, and a check that never catches a real problem is removed.

## Dependency updates

Each week, Dependabot opens pull requests for the pins it can read, as `.github/dependabot.yml` configures: the crates, the actions, the images in both Dockerfiles and in every Compose file, at the root and under `deploy/`, and the toolchain in `rust-toolchain.toml`. Each runs the whole pipeline, as every pull request does. `compose.yaml` holds the images the tasks run, such as Grype's and BuildKit's, so that these updates reach them.

These pins are updated by hand, and `check-pins` checks their form:
- the versions of the tools in the justfile, and of `just` in the workflows;
- the runner's version in the workflows, such as `ubuntu-24.04`;
- in the Dockerfiles, the frontend on their first line; in the API's, the zig download with its checksums and the versions of the crates it installs; in `deploy/postgres/Dockerfile`, the versions of pgBackRest and of the certificate authorities' package.

## Checks required for merging

These are the jobs of `ci.yml` to require before a pull request merges: `checks`, `image`, `scan`, and the four of `verify`: `verify (linux/amd64, backups)`, `verify (linux/amd64, others)`, `verify (linux/arm64, backups)` and `verify (linux/arm64, others)`. `publish` and `release` run only on `main`, so no pull request has them.

To require them on GitHub, open the repository's Settings, then either:
- Rules, Rulesets, New branch ruleset: target the default branch, turn on "Require status checks to pass", and add those seven.
- Branches, Add branch protection rule: for `main`, turn on "Require status checks to pass before merging", and add the same seven.

GitHub offers both for a private repository only on a paid plan, and a fork doesn't inherit either, so requiring them is the repository owner's choice (OPS-12).
